# 第 0 章 · 三个必须先建立的心智模型

刚开始学会犯的错，几乎都是"没有模型，只有命令"。先建立这三个模型，后面所有知识都有地方挂。

## 0.1 模型一：分层（每一层只解决自己的问题）

一个网页请求进来，会依次穿过很多层。**每层只干一件事，出问题时先判断是哪一层坏了**。

```
浏览器
  │  ① DNS：域名 → IP
  ▼
公网 ── ② 云安全组（云平台的防火墙）
  │
  ▼
服务器 ── ③ 系统防火墙 firewalld
  │
  ▼
Nginx（④ 监听 80 端口，⑤ 决定转给谁）
  │  ⑥ 反向代理，转给上游
  ▼
PHP-FPM（⑦ 执行 PHP 代码）
  │  ⑧ 查数据库 / 查缓存
  ▼
MySQL（⑨ 执行 SQL，读磁盘）   Redis（⑩ 内存里取数据）
```

**这个模型的价值**：当用户说"网站打不开"，你可以从 ② 一路往下问：
- 安全组放行了吗？→ 不通就是这一层
- 端口在监听吗？→ `ss -tlnp`
- Nginx 返回什么码？→ 502 说明上游（⑦）挂了，504 说明上游慢
- PHP 日志有报错吗？
- SQL 慢不慢？→ 慢查询日志

**记住一句话**：**502 是"下游挂了"，504 是"下游慢了"，500 是"下游自己报错了"。** 光这一条就能覆盖一半排障。

## 0.2 模型二：网络（IP、端口、子网、网关）

新手最容易晕的就是网络。只需要搞懂四个词：

| 概念 | 类比 | 项目里的例子 |
|---|---|---|
| **IP** | 门牌号 | `172.20.0.10` |
| **端口** | 门牌号上的第几个房间 | `80`（HTTP）、`3306`（MySQL） |
| **子网（网段）** | 同一个小区 | `172.20.0.0/24` = 172.20.0.1 ~ 172.20.0.254 |
| **网关** | 小区的出口 | `172.20.0.1` |

**关键规则（必须背）**：
- `127.0.0.1` = **本机自己**，只有这台机器内部能访问。
- `0.0.0.0` = **本机所有网卡**，外面能访问。
- 服务监听在 `127.0.0.1` 时，外面**永远连不上**——这是最高频的坑（php-fpm 默认就这样）。
- `172.16~172.31.x.x`、`10.x.x.x`、`192.168.x.x` 是**内网地址**，公网访问不到。

**项目一用了四个网段**，记住这张表就够了：

| 网段 | 谁在上面 | 谁能访问谁 |
|---|---|---|
| `172.20.0.0/24` front | lb + 两个 web | 对外服务，用户可以进 |
| `172.21.0.0/24` net-node1 | node1 的 web/app/db | 只有节点 1 内部 |
| `172.22.0.0/24` net-node2 | node2 的 web/app/db | 只有节点 2 内部 |
| `172.23.0.0/24` net-db | 两个 MySQL | 只有主从之间 |

## 0.3 模型三：进程与端口

- **进程** = 正在运行的程序。`ps aux` 看，`top` 看谁占 CPU。
- **端口** = 进程对外提供服务的"房间号"。一个端口同一时刻只能被一个进程占用。
- **监听（listen）** = 进程在某个端口上"等人来连"。

```bash
ss -tlnp          # 看谁在监听：t=TCP l=listen n=数字 p=进程
# 输出里 0.0.0.0:80 表示所有网卡都能访问，127.0.0.1:9000 表示只有本机能访问
```

**这个模型的价值**：容器起不来时，第一件事就是 `ss -tlnp | grep 端口`——端口被占，或者根本没监听，两个完全不同的原因。

# 第 1 章 · 底座：Linux 与网络

这一章只讲项目里**真的用到**的部分，不铺开。

## 1.1 一个请求的完整旅程（把 0.1 的图展开成故事）

假设用户在浏览器输入 `http://你的公网IP/`：

1. **DNS**：如果是域名，浏览器先问 DNS"这个域名对应哪个 IP"。（项目里直接输 IP，跳过这步）
2. **TCP 三次握手**：浏览器和服务器 80 端口建立连接。SYN → SYN+ACK → ACK。
3. **HTTP 请求**：浏览器发 `GET / HTTP/1.1`。
4. **到达安全组**：云平台检查"这条入站流量允许吗"。没放行 → 包被丢弃，浏览器一直转圈到超时。
5. **到达 firewalld**：系统防火墙再检查一遍。没放行 → 同样被丢弃。
6. **Nginx 收到请求**：看 `location /`，决定 `proxy_pass http://web_cluster`。
7. **Nginx 选一个上游**：轮询算法选 `node1-web` 或 `node2-web`，建立新连接转发过去。
8. **节点上的 nginx**：收到请求，发现是 `.php`，交给 php-fpm（FastCGI 协议，走 9000 端口或 unix socket）。
9. **php-fpm 起一个 worker**：执行 index.php。
10. **PHP 查缓存**：先问 Redis"这个数据有吗"。有 → 直接返回（0.4ms）。没有 → 下一步。
11. **PHP 查数据库**：连 MySQL 执行 SQL（58ms）。
12. **结果回写**：MySQL → PHP → 写入 Redis（TTL 60 秒）→ 返回 HTML。
13. **响应回传**：PHP → nginx → 浏览器。Nginx 顺手把 `up=节点地址 urt=耗时` 记进 access.log。

**这就是两个项目的全貌**。你现在看不懂第 6-12 步没关系，后面每一章拆一层。

## 1.2 监听地址：`0.0.0.0` 和 `127.0.0.1` 的区别（第一个大坑）

**是什么**：进程启动时可以指定"只在哪个网卡上监听"。

| 地址 | 含义 | 谁能访问 |
|---|---|---|
| `127.0.0.1:9000` | 只有本机回环网卡 | **只有这台机器自己** |
| `0.0.0.0:9000` | 所有网卡 | 任何能路由到这台机器的人 |

**为什么项目里踩过**：`php:8.2-fpm` 镜像默认监听 `127.0.0.1:9000`。但 nginx 在**另一个容器**里，对它来说 php 容器是"另一台机器"，连 `127.0.0.1` 连到的是自己 → 必然失败，报 502。

**项目里怎么改**（`php/Dockerfile`）：
```dockerfile
RUN { \
      echo '[www]'; \
      echo 'listen = 0.0.0.0:9000'; \
    } > /usr/local/etc/php-fpm.d/zz-docker.conf
```
- `[www]` 是进程池的名字（php-fpm 可以有多个池）。
- 文件名叫 `zz-docker.conf`，**`zz` 前缀保证它最后加载**，覆盖掉默认配置。

**怎么验证**：`ss -tlnp | grep 9000`，看到 `0.0.0.0:9000` 才对，看到 `127.0.0.1:9000` 就是没改成功。

## 1.3 uid 与权限：为什么是 `chown 999:999`

**是什么**：Linux 用数字标识用户。`/etc/passwd` 里 `mysql:x:999:999::` 表示 mysql 这个用户的 **UID 是 999**。

**关键原理（这是最容易误解的一点）**：
> **内核只认数字 UID，不认用户名。**
> 宿主机上可能根本没有叫 `mysql` 的用户，但只要有 UID 999 这个数字，权限就对得上。

**为什么项目里会报错**：项目二用 bind mount 把宿主机目录挂给 MySQL 容器。容器内的 mysqld 以 UID 999 运行，要往目录里写文件；宿主机目录属主是 root（UID 0），999 没有写权限 → 启动失败：

```
mysqld: Can't create/write to file '/var/lib/mysql/...' (Errcode 13 - Permission denied)
```

**怎么修**：
```bash
chown -R 999:999 data logs/mysql    # 必须写数字
chown -R mysql:mysql data           # 错！宿主机没有 mysql 用户 → invalid user
```

**怎么确认镜像是 999**：
```bash
docker run --rm mysql:8.0 id mysql          # uid=999(mysql) gid=999(mysql)
docker image inspect mysql:8.0 --format '{{.Config.User}}'   # 999:999
```

**为什么用 named volume 就没这问题**：volume 是 Docker 创建的，它会按镜像里的属主初始化目录，权限天然正确。所以**数据库优先用 volume，代码和配置用 bind mount**。

## 1.4 三个时间戳：为什么改了文件 `ls -l` 不显示

| 时间 | 含义 | 什么时候变 |
|---|---|---|
| `atime` | 访问时间 | 读文件时（现代系统用 relatime，不每次更新） |
| **`mtime`** | 内容修改时间 | 写内容时，`ls -l` 默认显示这个 |
| `ctime` | 元数据变更 | `chmod`/`chown`/改名时，**无法伪造** |

**项目里哪里用到**：备份脚本用 `find -mtime +7` 找 7 天前的旧备份删除；日志备份用 `-newermt "-7 days"` 找一周内的日志。**都是 `mtime`**。

## 1.5 日志都在哪（排障的弹药库）

| 位置 | 内容 | 项目里用途 |
|---|---|---|
| `journalctl -u nginx` | systemd 管的服务日志 | 宿主机上的服务 |
| `docker logs 容器` | 容器的 stdout/stderr | 看容器启动失败原因 |
| `/var/log/messages` | 系统综合日志（RHEL 系） | OOM、磁盘错误 |
| `/var/log/secure` | 登录认证 | SSH 爆破、sudo 记录 |
| `/var/log/cron` | 定时任务执行记录 | 排查 cron 不跑 |
| `./logs/nginx-lb/*.log` | bind mount 出来的 nginx 日志 | **容器日志看不到，只能看这里** |

**这里有个必须理解的区分**（项目二第 25 坑）：
- 容器里进程打印到**屏幕**的内容 → 被 Docker 收集 → `docker logs` 能看。
- 进程**自己写进文件**的内容（nginx 的 `access.log`）→ Docker 不管 → 只能去挂载出来的目录看。

## 1.6 systemd：服务怎么开机自启

```bash
systemctl start/stop/restart/reload nginx
systemctl enable --now nginx     # 开机自启 + 立即启动
systemctl status nginx -l
systemctl daemon-reload          # 改了 .service 文件必须执行
```

- **`enable`** 建软链接，管"开机自启"；**`start`** 管"现在启动"。两个都要就 `enable --now`。
- **`restart` vs `reload`**：restart 停掉再起（断连接）；reload 让进程重读配置（Nginx 平滑换 worker，不断连接）。

**项目里对应**：Docker 化之后，容器自己的"自启"由 `restart: unless-stopped` 管，不再靠 systemd 的 enable——但 Docker 守护进程本身要被 systemd 拉起。

# 第 2 章 · Docker：两个项目的运行底座

## 2.1 为什么用容器，而不是直接在服务器上装软件

**先想一个问题**：如果直接在 2C2G 上装 Nginx + PHP + MySQL + Redis + 两套节点，会怎样？

| 问题 | 直接装 | 用容器 |
|---|---|---|
| 版本冲突 | 两个节点要不同 PHP 版本？装不了 | 每个容器独立环境，互不干扰 |
| 隔离 | 一个服务改崩了全局配置，全挂 | 进程、网络、文件系统都隔离 |
| 复制 | 换台机器要重装一遍，容易漏 | `git clone` + `compose up` 一模一样 |
| 清理 | 卸载残留一堆 | `down -v` 全清 |
| 网络模拟 | 一台机器只有一个 IP，模拟不出"两个节点" | 每个容器一个 IP，能造出多节点 |

**项目一的核心诉求就是最后一条**：只有一台服务器，但要模拟"两个机房节点"。容器给了每个节点**独立的 IP、独立的进程空间、独立的文件系统**，这在物理上就是两台机器的样子（除了内核是共享的）。

## 2.2 镜像、容器、分层、可写层（最重要的四个词）

**类比**：
- **镜像（image）** = 一张装好系统的光盘，只读，不能改。
- **容器（container）** = 用这张光盘启动的一台机器，可以随便折腾。
- **分层（layer）** = 光盘是一层一层压出来的：底层是操作系统，中间是装好的软件，上层是你的代码。
- **可写层** = 容器启动时在最上面加一张"草稿纸"，所有修改都写在这张纸上。

```
容器 = 镜像只读层（共享，多个容器共用一份）
     + 可写层（每个容器独有，删容器就没了）★
     + 挂载（volume / bind mount，独立存在，删容器也不丢）★
```

**这条推出三个结论（面试常问）**：
1. 删容器 = 丢可写层里的所有修改，所以**数据必须放挂载**，不能写在容器里。
2. 多个容器用同一个镜像，**磁盘上只有一份镜像**，启动很快。
3. 镜像层一旦生成就不再变，所以 `Dockerfile` 里"装了又删"必须写在**同一个 RUN** 里，否则删不掉（见 2.3）。

**常用命令（先记住这五个）**：
```bash
docker images                  # 本地有哪些镜像
docker ps -a                   # 所有容器（-a 包含已退出的）★
docker logs -f --tail 100 容器  # 看日志
docker exec -it 容器 sh        # 进容器
docker inspect 容器            # 看全部元数据（IP、挂载、重启策略）
```

## 2.3 Dockerfile 逐行精读（项目二的 PHP 镜像）

Dockerfile 就是"怎么造这张光盘"的说明书。逐行看：

```dockerfile
FROM php:8.2-fpm-alpine
```
**基础镜像**。`php:8.2-fpm-alpine` 有三层含义：PHP 8.2 + 自带 php-fpm（不是 CLI 版）+ alpine（精简 Linux，几十 MB）。

> **为什么用 alpine**：镜像小、启动快、攻击面小。代价是没有 bash（只有 sh）、没有常用工具（`ps`、`vi` 都要自己装）。

```dockerfile
RUN sed -i 's#dl-cdn.alpinelinux.org#mirrors.tuna.tsinghua.edu.cn#g' /etc/apk/repositories
```
**换 apk 源**。alpine 的包管理叫 `apk`，默认从境外 CDN 下载。国内服务器不换源，装个编译工具链要 **951 秒（我实测过）**，换完几十秒。

> **注意**：Docker 的镜像加速器（`registry-mirrors`）**只加速镜像拉取，管不到 apk 的包源**。这是两个不同的东西。

```dockerfile
RUN apk add --no-cache --virtual .build-deps $PHPIZE_DEPS \
 && apk add --no-cache libzip-dev icu-dev \
 && docker-php-ext-configure opcache --enable-opcache \
 && docker-php-ext-install -j$(nproc) pdo_mysql mysqli opcache \
 && pecl install redis \
 && docker-php-ext-enable redis \
 && apk del .build-deps
```
这一大段干的事：**装编译工具 → 编译 PHP 扩展 → 再把编译工具删掉**。

| 片段 | 作用 | 为什么这么写 |
|---|---|---|
| `--virtual .build-deps` | 把一堆包打成一个"虚拟包组" | 方便最后一句 `apk del .build-deps` **整组删掉** |
| `$PHPIZE_DEPS` | 官方镜像提供的变量，含 autoconf/gcc/make | 编译扩展必需 |
| `docker-php-ext-install` | 官方镜像的脚本，编译内置扩展 | 比手动 `phpize` 简单 |
| `pecl install redis` | 装第三方扩展（redis 不在 PHP 源码里） | **必须和上面同一个 RUN**，否则删了工具后 `phpize: not found` |
| `apk del .build-deps` | 删编译工具 | **关键：只有和安装写在同一个 RUN（同一层），才能真正减小镜像**。分成两个 RUN 的话，工具还在下层里，镜像一点没小 |

> **这就是"镜像分层"的实际意义**：每一行 `RUN` 生成一层，层是只读的。你在第 5 层删掉第 3 层装的东西，第 3 层依然占空间——所以"装和删必须同层"。

```dockerfile
RUN { \
      echo '[www]'; \
      echo 'listen = 0.0.0.0:9000'; \
      echo 'pm.max_children = 8'; \
      ...
    } > /usr/local/etc/php-fpm.d/zz-docker.conf
```
**用 shell 命令生成配置文件**。`{ ... }` 是命令组，把一堆 `echo` 的输出重定向到一个文件。

**两个坑都真实踩过**：
1. `echo` 行尾写注释 `# ... \` → `#` 把续行符 `\` 一起吞掉，命令组断裂，构建报 `syntax error: unexpected end of file (expecting "}")`。**注释必须写在 RUN 之前单独成行。**
2. `zz-` 前缀：php-fpm 按文件名字典序加载 `php-fpm.d/*.conf`，`zz` 排在最后 → 覆盖前面的默认值。

## 2.4 网络：为什么必须自定义 bridge

**Docker 默认有三种网络**：

| 网络 | 说明 |
|---|---|
| `bridge`（默认 docker0） | 容器能上网，但**容器之间不能用名字互访**，只能用 IP |
| `host` | 容器直接用宿主机网络，没有隔离 |
| `none` | 没网络 |

**自定义 bridge 的关键差别**：Docker 会给它跑一个**内嵌 DNS**，容器之间可以用**服务名**互访。

```yaml
services:
  app:
    networks:
      net-node1:
        ipv4_address: 172.21.0.12
        aliases:
          - app          # ★ 给这个容器起个别名
```

于是 nginx 里写 `proxy_pass http://app:8080` 就能找到它——**不用写死 IP**。

**alias 的妙用（项目一的关键设计）**：
node1-app 和 node2-app 都起了别名 `app`，它们各自在自己网段里。node1-web 在 `net-node1` 里解析 `app` 得到 node1 的 IP，node2-web 在 `net-node2` 里解析 `app` 得到 node2 的 IP。

**结果：两个节点可以共用同一份 nginx 配置**，改一次两边都生效。

**端口映射 `-p 80:80`**：
```
宿主机 80 端口  →  容器 80 端口
```
只有映射了，外面才能访问。**数据库一般不映射**（项目二 MySQL 就是这样，只在容器网络内可见），防止被公网扫到爆破。

## 2.5 数据卷：三种挂载方式

| 类型 | 写法 | 谁管理 | 适合放什么 | 项目里用在哪 |
|---|---|---|---|---|
| **named volume** | `db-node1:/var/lib/mysql` | Docker | 数据库数据 | 两个 MySQL 的数据目录 |
| **bind mount** | `./nginx/lb.conf:/etc/nginx/conf.d/default.conf:ro` | 你自己 | 配置、代码、日志 | nginx 配置、www 代码、日志 |
| **tmpfs** | `tmpfs: /tmp` | 内存 | 临时敏感数据 | 项目没用（可选） |

**怎么选（一句话口诀）**：
> **"数据要活过容器"用 volume，"文件我要在宿主机上直接改"用 bind mount。**

**`:ro` 是什么意思**：read-only，容器内只能读不能写。配置文件加 `:ro` 有两个好处——① 防止容器意外改配置 ② 明确"配置以 git 里的为准"。

**为什么日志用 bind mount**：要能在宿主机上直接 `tail -f`，也要让 logrotate 去切它（Docker 管不到应用写的文件）。

## 2.6 `docker-compose.yml`：把一堆容器描述成一份文件

**结构只有四块**：`services`（有哪些容器）、`networks`（有哪些网络）、`volumes`（有哪些卷）、顶部的 `name`（项目名）。

```yaml
name: cluster-p1            # 项目名，决定容器名和卷名前缀

x-mysql-base: &mysql-base   # ① YAML 锚点：定义一段可复用的配置
  image: mysql:8.0
  restart: unless-stopped
  environment:
    MYSQL_ROOT_PASSWORD: "Root@123456"

services:
  node1-db:
    <<: *mysql-base         # ② 把上面那段"合并进来"
    container_name: node1-db
```
**YAML 锚点（`&` 定义、`*` 引用、`<<:` 合并）**：两个 MySQL 配置 90% 相同，用锚点只写一遍，差异只体现在各服务的少量字段。**这是"能复用就复用"的具体落地**。

**`name` 字段的作用**：不写就用目录名。目录一改，容器会变成"新的一套"，很坑。

**环境变量注入**：`environment` 里的值会变成容器内的环境变量。PHP 代码里 `getenv('DB_HOST')` 就能拿到——这样**同一份代码可以跑在两个节点上**，只是连的库不同。

## 2.7 启动顺序与健康检查（项目一第一个坑的根源）

**`depends_on` 有三种写法，语义完全不同**：

| 写法 | 保证什么 | 什么时候用 |
|---|---|---|
| `depends_on: [db]`（短语法） | 只保证**启动顺序**（先起 db 再起 app） | 基本不用，容易误解 |
| `condition: service_started` | 等对方**容器创建完成** | 对方是"起来就能服务"的 |
| `condition: service_healthy` | 等对方**健康检查通过** | 数据库、缓存这类启动慢的 |

**为什么"启动了"不等于"能用了"**：MySQL 容器 `Up` 之后，内部还要经历：

```
① 起一个临时实例（只监听 socket，root 还没密码）
② 执行 /docker-entrypoint-initdb.d/ 里的初始化脚本（建库、导数据）
③ 关掉临时实例
④ 正式实例启动，开始监听 3306
```
这四步可能要 20-60 秒。这期间 `docker compose ps` 显示 `Up`，但你去连它就是连不上。

**健康检查写法**：
```yaml
healthcheck:
  test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p$$MYSQL_ROOT_PASSWORD --silent"]
  interval: 10s      # 每 10 秒查一次
  timeout: 5s        # 单次超时 5 秒
  retries: 8         # 连续失败 8 次才判定 unhealthy
  start_period: 60s  # 启动后给 60 秒宽限期，这期间的失败不算
```
> `$$` 是 compose 的转义：`$$` 会传给容器变成 `$`，否则 compose 会当成自己的变量去替换。

**注意**：这个 `mysqladmin ping` 只判断"服务器在应答"，**认证失败也返回成功**——用来做启动依赖够用，但拿来判断"能不能导数据"就会翻车（项目里真翻过，见 3.19）。

## 2.8 日志：`docker logs` 只能看到一部分

```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"     # 单个文件最大 10MB
    max-file: "3"       # 最多保留 3 个
```
- 不设上限，`json-file` 会一直追加，**把 40G 系统盘写满**是小机器的常见死法。
- `10m × 3 = 30MB/容器`，四个容器封顶 120MB，可控。
- **但这个上限只管容器的 stdout/stderr**。nginx 写进 `/var/log/nginx/access.log` 的内容是普通文件，Docker 完全不管——这就是"两个出口"（4.17）。

## 2.9 排查容器问题的固定顺序

遇到"服务起不来"，**按这个顺序，别乱跳**：

```bash
docker compose ps -a           # ① 状态：Up / Exited / Created / Restarting
docker logs --tail 100 容器     # ② 日志：Exited 一定有原因，Created 可能没有
docker inspect 容器 | grep -A5 State   # ③ 退出码、OOMKilled
ss -tlnp | grep 端口            # ④ 端口有没有在监听、被谁占
docker exec -it 容器 nginx -t   # ⑤ 配置对不对（配置类服务）
```

**状态码的含义（关键）**：

| 状态 | 含义 | 该怎么办 |
|---|---|---|
| `Up` | 进程在跑 | 不代表能服务，要 `curl` 试 |
| `Created` | 容器建好了但**进程一次都没跑过** | 日志是空的，查配置/依赖 |
| `Exited (0)` | 正常退出 | 主进程执行完就退了（不该是常驻服务的行为） |
| `Exited (1)` | 报错退出 | 看日志，有明确原因 |
| `Restarting` | 反复重启 | `logs` 看每次崩的原因 |
| `Up (unhealthy)` | 活着但健康检查不过 | 看健康检查命令本身对不对 |

**退出码速记**：`137` = 128+9（被 SIGKILL，常见于 OOM 或超时强杀）；`143` = 128+15（收到 SIGTERM，正常优雅停止）；`127` = 命令找不到。

# 第 3 章 · 项目一：高可用集群

## 3.1 这个项目在模拟什么真实场景

真实公司里，一个网站通常长这样：

```
用户 → 负载均衡（LB）→ 应用节点1 ┐
                     → 应用节点2 ├→ 数据库（主）→ 数据库（从）
                     → 应用节点3 ┘
```

- **为什么要有多个节点**：一个节点挂了还有别的；请求多了可以加节点扛。
- **为什么要有 LB**：用户不知道有哪些节点，也不该知道。LB 是唯一入口，负责分发和摘除坏节点。
- **为什么数据库要主从**：主库负责写，从库负责读 + **备份/容灾**；主库挂了能从从库切。

**我只有一台 2C2G，怎么模拟？** 用 Docker 网络把一台机器切成两个"逻辑节点"：每个节点有独立 IP、独立进程、独立文件系统。**机制是真的，只有物理隔离是假的**——这句话必须主动说，因为它决定了你是不是诚实。

## 3.2 拓扑：7 个容器，4 个网络

| 容器 | 镜像 | 网络与 IP | 作用 |
|---|---|---|---|
| `lb` | nginx:1.27-alpine | front `.10` | 唯一入口，监听 80，轮询分发 |
| `node1-web` | nginx:1.27-alpine | front `.11` + net-node1 `.11` | 节点1 的静态资源 + 反代 app |
| `node1-app` | build（Python/自定义） | net-node1 `.12`，alias `app` | 节点1 的业务进程，端口 8080 |
| `node1-db` | mysql:8.0 | net-node1 `.13` + net-db `.11` | **主库** |
| `node2-web` | nginx:1.27-alpine | front `.12` + net-node2 `.11` | 节点2 入口 |
| `node2-app` | build | net-node2 `.12`，alias `app` | 节点2 业务 |
| `node2-db` | mysql:8.0 | net-node2 `.13` + net-db `.12` | **从库** |

**三个设计要点，每一条都要能说出"为什么"**：
1. **两个 db 都不在 front 网络** → 从公网/前端容器根本访问不到数据库。
2. **主从复制走独立的 net-db** → 复制流量不和业务流量抢带宽、也便于单独做访问控制。
3. **app 加 alias `app`** → 两个节点共用一份 nginx 配置。

## 3.3 Nginx 是什么：master-worker 与 epoll

**是什么**：一个 HTTP 服务器 + 反向代理。既能直接返回静态文件，也能把请求转给别的程序。

**进程模型（必懂）**：
```
master 进程（1 个）
  ├─ 读配置、管生命周期、平滑升级
  └─ fork 出 N 个 worker（N 通常 = CPU 核数）
        └─ 每个 worker 是单线程，用 epoll 同时处理上千个连接
```
**为什么这样设计**：一个 worker 崩了不影响别人（master 会补一个）；单线程 + epoll 避免了多线程加锁和上下文切换的开销——这就是 Nginx 高并发能力的来源。

**epoll 是什么（一句话）**：内核提供的事件通知机制。你把 1000 个连接交给它，哪个有数据了它告诉你，不用一个个轮询。**对比**：Apache 的 prefork 是"一个连接一个进程"，1000 个连接就是 1000 个进程，内存直接爆。

**reload 的原理**：给 master 发 `HUP` 信号 → master 校验新配置 → 起新的 worker 用新配置 → 老 worker 处理完存量请求后退出。**全程不断连接**，这就是为什么改配置用 `nginx -s reload` 而不是 restart。

## 3.4 正向代理和反向代理（名字像，方向相反）

| | 正向代理 | 反向代理 |
|---|---|---|
| 代理谁 | **代理客户端** | **代理服务端** |
| 谁知道谁 | 服务器不知道真实客户端 | 客户端不知道真实服务器 |
| 例子 | 科学上网、公司统一出口 | Nginx 把请求转给后端集群 |

**一句话记**：**正向代理帮客户端"出去"，反向代理帮服务器"挡住"**。项目里的 LB 和每个节点的 web 都是反向代理。

## 3.5 upstream：把多个后端定义成一个组

```nginx
upstream web_cluster {
    server node1-web:80 max_fails=2 fail_timeout=10s;
    server node2-web:80 max_fails=2 fail_timeout=10s;
    keepalive 32;
}
```

**四种常用调度算法**：

| 算法 | 写法 | 特点 | 适用 |
|---|---|---|---|
| 轮询（默认） | 不写 | 按顺序轮流，weight 可加权 | 节点配置相同 |
| 加权轮询 | `weight=3` | 配置好的多分点 | 机器配置不同 |
| `ip_hash` | 加一行 | 同一 IP 固定落到同一节点 | 解决 session 问题（但会倾斜） |
| `least_conn` | 加一行 | 分给当前连接数最少的 | 请求耗时差异大 |

**项目为什么用轮询**：两个节点配置完全一样，且 session 已经放 Redis（无状态），不需要粘滞。

## 3.6 被动健康检查与"6 秒 → 2 秒"的算式（本项目核心）

**先分清两类健康检查**：

| | 主动健康检查 | 被动健康检查 |
|---|---|---|
| 做法 | 定期发探测请求 | 靠**真实用户请求**踩雷后统计 |
| 谁有 | Nginx Plus（商业版）、tengine | **开源版 Nginx 只有这个** |
| 缺点 | — | 第一个用户当小白鼠；流量小的时候发现慢 |

**被动检查的三个参数**：

| 参数 | 含义 |
|---|---|
| `max_fails=2` | **连续**失败 2 次就标记为"坏" |
| `fail_timeout=10s` | ① 统计失败的时间窗口 ② 标记坏之后**多久不再选它** |
| `proxy_connect_timeout` | 单次"连不上"最多等多久 |

**为什么"节点死了"要等超时，而不是立刻知道？** 这是本题的灵魂：

> 容器被 `docker stop` 之后，它在网桥上的 veth 和 IP **直接消失**。之后 nginx 发给它的 SYN 包**既不会收到 RST（拒绝），也不会有任何响应，是静默丢弃**。
> 所以 nginx 无法"立刻"感知，只能一直等到 `connect_timeout` 到期，才判定这次失败。

**于是摘除时间的算式是**：
```
摘除总耗时 = max_fails × proxy_connect_timeout
原配置：2 × 3s = 6s      ← 用户要连续被坑 6 秒
现配置：2 × 1s = 2s      ← 只坑 2 秒
```

**为什么敢砍到 1 秒**：所有容器在同一宿主机、同一个 bridge，RTT < 1ms，1 秒已经是极其宽松的上限。
**什么时候不能砍**：后端跨机房、RTT 几十毫秒，或者后端偶发慢连接——砍太短会**误杀健康节点**，反而制造故障。

## 3.7 两种"超时"，两种病（一句话显出功力）

日志里会出现两种 `upstream timed out`，**它们是完全不同的问题**：

| 日志 | 卡在哪 | 对应参数 | 根因 | 修法方向 |
|---|---|---|---|---|
| `timed out (110: Connection timed out) while **connecting** to upstream` | TCP 都没建起来 | `proxy_connect_timeout` | 节点死了、端口没开、网络不通 | **缩短**超时，快速摘除 |
| `timed out (110: Connection timed out) while **reading** response header from upstream` | 连上了，但后端不回话 | `proxy_read_timeout` | 应用卡住、SQL 慢、死锁 | **延长**超时 + 去查后端为什么慢 |

**为什么必须分开**：一个要"快刀斩乱麻"，一个要"给后端时间"。混在一起调，必然治好一边、恶化另一边。

**面试时的杀手锏**：当面试官说"超时怎么调"，反问一句——**"您说的是连接超时，还是读取超时？"**

## 3.8 `proxy_next_upstream`：为什么"切换期间请求不失败"

```nginx
proxy_next_upstream error timeout http_500 http_502 http_503 http_504;
proxy_next_upstream_tries 2;
```
**含义**：遇到这些情况，nginx **在同一个请求内**立刻换下一个节点重试。

- `error`：连不上（拒绝、超时等）
- `timeout`：超时
- `http_500/502/503/504`：后端活着但报错，也该换

**所以用户体感是**：
```
第 1 个请求：打到死节点 → 等 1s → 重试到好节点 → 返回 200（慢了 1 秒，但没失败）
第 2 个请求：又打到死节点 → 再等 1s → 累计 2 次失败 → 节点被摘除
第 3 个请求起：直接走好节点，不再有延迟
```

**必须主动交底的边界**：
> `proxy_next_upstream` 默认**不重试非幂等请求**（POST）。我**故意没加 `non_idempotent`**——加了的话，超时会把"下单"重发一次，可能重复下单。所以极少数写请求在切换瞬间会返回 502，我宁可让它失败一次让用户重试。

**`tries 2` 的坑**：集群只有 2 个节点，试 2 次刚好。**如果扩到 3 个节点，这里必须同步调大**，否则第 3 个节点永远轮不到。

## 3.9 location 匹配优先级（坑 5 的根源）

```nginx
location = /health      { return 200 "ok"; }      # ① 精确匹配，优先级最高
location ^~ /static/    { ... }                   # ② 前缀匹配，且不再试正则
location ~ \.php$       { ... }                   # ③ 正则匹配
location /              { ... }                   # ④ 普通前缀，兜底
```

**优先级**：`=` > `^~` > 正则（按书写顺序）> 普通前缀（最长匹配）。

**坑是怎么发生的**：健康检查写成 `location /health`（普通前缀），被更宽松的 `location /` 或 `location ~ \.php$` 抢走，请求被转到业务页面，返回 HTML 而不是 200 → 健康检查永远失败 → 节点全被摘除。

**修法**：`location = /health`，精确匹配，谁也抢不走。

## 3.10 自定义日志格式：可观测性

```nginx
log_format lb_main '$remote_addr ... $status '
                   'up=$upstream_addr ust=$upstream_status '
                   'urt=$upstream_response_time rt=$request_time';
```

| 变量 | 含义 | 什么时候看 |
|---|---|---|
| `$upstream_addr` | 实际打到哪个上游 | 验证轮询、定位是哪个节点出问题 |
| `$upstream_status` | 上游返回的码 | **为空 = 根本没拿到响应**（连接层问题） |
| `$upstream_response_time` | 上游耗时 | 后端慢不慢 |
| `$request_time` | 整个请求耗时 | 与 `urt` 对比：差值大 = 时间花在 nginx 或客户端 |

**为什么必须自定义**：官方默认格式**不含上游信息**。出事时你只知道"返回了 200"，不知道"打到哪、用了多久"——那次真实用户慢请求就是这么瞎的（日志里没记 `urt`，事后无法回溯）。

**配套**：`add_header X-Upstream-Node $upstream_addr`，这样 `curl -I` 就能看到打到了哪个节点，肉眼验证轮询。

## 3.11 keepalive：长连接为什么重要

```nginx
upstream web_cluster {
    keepalive 32;          # 保持 32 条空闲长连接
}
location / {
    proxy_http_version 1.1;      # ★ 必须
    proxy_set_header Connection "";   # ★ 必须
}
```
- 没有长连接：每个请求都要三次握手（+ 四次挥手），高 QPS 下握手开销很可观。
- **两个必须配套**：HTTP/1.0 默认短连接，必须显式用 1.1；`Connection ""` 是清空默认的 `close` 头，否则还是短连接。

## 3.12 MySQL 主从复制：完整链路

**目标**：主库的数据自动同步到从库。

```
主库
 ├─ 执行 SQL → 写 redo log（保证崩溃可恢复）→ 写 binlog（记录变更）
 │
 └─ 从库的 IO 线程 → 连主库 → 请求 binlog → 写入本地 relay log（中继日志）
        │
        └─ 从库的 SQL 线程 → 读 relay log → 重放（re-execute）→ 从库数据一致
```

**两个线程的分工（定位口诀）**：

| 线程 | 挂了的含义 | 查什么 |
|---|---|---|
| **IO 线程** | 拿不到 binlog | 网络、认证、主库 binlog 是否开启、`Last_IO_Error` |
| **SQL 线程** | 拿到了但重放失败 | 数据冲突、GTID 冲突、库表不存在，`Last_SQL_Error` |

**口诀**：**IO 挂查网络，SQL 挂查数据。**

**一条常用命令**：
```sql
SHOW SLAVE STATUS\G        -- 8.0.22+ 也可以 SHOW REPLICA STATUS\G
```
重点看四个值：`Slave_IO_Running`、`Slave_SQL_Running`、`Seconds_Behind_Master`（8.0.23+ 改名 `Seconds_Behind_Source`）、`Last_Errno`。

## 3.13 GTID：为什么会卡住（面试高频）

**binlog 传统方式是"位点（position）"**：告诉从库"从主库 binlog 的第 1234 字节开始复制"。问题是主从切换后位点全变，容易错。

**GTID（Global Transaction ID）**：给每个事务一个**全局唯一编号**，形如 `3E11FA47-71CA-11E1-9E33-C80AA9429562:1-100`。从库只需说"我执行过哪些 GTID"，剩下的都要——**不用记字节位置**。

**坑是怎么发生的**：
1. 用 `mysqldump` 导主库全量数据，备份文件里**带着主库的 GTID 历史**。
2. 导入从库时，从库把这些 GTID 记成"我已经执行过"。
3. 之后从库去主库拉 binlog，发现"这些 GTID 我都有"，就直接跳过——**数据看起来对，但复制状态是停的**（或者重放时冲突）。

**修法**：
```bash
mysqldump --single-transaction --set-gtid-purged=OFF ... > backup.sql
```
`--set-gtid-purged=OFF` = 导出时不带 GTID 信息，让从库"从零开始"。

## 3.14 主从延迟与监控字段改名

**延迟从哪来**：主库写入快，从库重放慢（单线程重放、从库还有读查询抢资源）→ 数据不同步，`Seconds_Behind_Source` 变大。

**为什么要监控**：读写分离后，用户刚下单就去读从库，可能读不到自己的订单。

**坑（项目里的第 7 坑）**：从 **MySQL 8.0.23** 起，`Seconds_Behind_Master` 改名 `Seconds_Behind_Source`。监控脚本还在 grep 老名字 → 取到空值 → **条件永远不成立 → 告警永远不响，而且不报错**。

**修法**：正则写 `Seconds_Behind_(Source|Master)` 兼容两版；**并且加一条"取不到值就告警"**——取空值本身就是故障。

## 3.15 Zabbix：监控告警的四层链路

```
① item（采集什么）→ ② trigger（什么算异常）→ ③ action（触发后干什么）→ ④ media（从哪发出去）
```

| 层 | 例子 | 漏了会怎样 |
|---|---|---|
| item | CPU 使用率、磁盘使用率、复制延迟 | 没数据，后面全空 |
| trigger | `磁盘 > 85%`、`延迟 > 60s`，带 severity 分级 | 有数据但不判断，等于没监控 |
| action | 状态从 OK → PROBLEM 时执行 | 判断了但没人知道 |
| media | Webhook → 钉钉机器人 | 发不出去 |

**链路验证怎么做（不能只看界面绿）**：
1. 手动制造异常（占满磁盘 / 停掉从库）
2. 看 trigger 是否变成 PROBLEM
3. 看 action log 有没有执行
4. 看钉钉有没有收到
5. 恢复后有没有 RESOLVED

**项目里的坑（第 20 坑，最阴的一个）**：媒介的**收件人为空**时，Zabbix 会**静默丢弃**——不投递、不写日志、连失败记录都没有。所以"配置全对但没发出去"是可能的。**每一层都要发一条真实告警验证。**

## 3.16 备份与恢复：为什么"备份不验证等于没备份"

**mysqldump 的四个关键参数**：

| 参数 | 作用 | 不加会怎样 |
|---|---|---|
| `--single-transaction` | 在 RR 隔离级别下开一个一致性快照，**不锁表** | 备份期间业务写不进去 |
| `--quick` | 逐行读，不把整个表加载进内存 | 大表直接把 2G 内存吃爆 |
| `--set-gtid-purged=OFF` | 不带 GTID 历史 | 恢复/搭从库时冲突（3.13） |
| `--routines --triggers` | 带上存储过程和触发器 | 恢复后功能缺失，很难发现 |

> `--single-transaction` 的前提是**全 InnoDB 表**。有 MyISAM 就只能 `--lock-all-tables`，那才会锁业务。

**备份四件套（缺一不可）**：
```
① 备份（dump + gzip）
② 校验（非空 + gzip -t 能解开）
③ 保留策略（find -mtime +7 -delete）
④ 恢复演练（起临时库灌进去，对账）
```

**恢复演练里踩的坑（第 24 坑，最值钱的一个）**：
- 用 `mysqladmin ping` 判断临时库"就绪"→ 它**认证失败也返回 0**（只问服务器在不在，不问密码对不对）。
- 于是脚本在 MySQL 还没初始化完时就开始导 → 报 `Access denied`。
- 但脚本的判定是"语句执行完就算成功"→ 报告写着"**恢复完成，耗时 0 秒**"。
- **8M 的库不可能 0 秒恢复完**——0 秒就是"根本没干活"的铁证。
- 修法：改用 `mysql -e 'SELECT 1'` 验到业务层；就绪等待从 0 秒变成真实的 16 秒。

**对账三件套**：表数量、`orders` 行数（300000）、索引数量。

## 3.17 故障演练：怎么设计判定口径

**演练做什么**：手动 `docker stop` 一个节点，观察服务是否还能用、多快恢复。

**演练最容易错的地方：判定标准**。

项目里第一次演练，20 次里"失败"9 次，全是 `000`，每次卡约 3 秒。看着像服务挂了，实际**一次都没挂**：

| 现象 | 真相 |
|---|---|
| `000`（curl 连接没建立） | 切换瞬间连接被重置，是切换的**必然代价** |
| 每次卡 3 秒 | curl 的 `-m` 超时撞上了 nginx 的 connect_timeout |
| 日志里有 499 | 499 = **客户端**在服务端响应前主动断开，不是服务端错误 |

**修法**：判定标准从"curl 退出码 0"改成"**后端是否产生了 2xx/3xx 响应**"；499 不计失败；演练脚本允许一次重试（真实用户也会重试）。

**这条的普适道理**：**先用错误的标准测，会得到错误的结论**。压测（4.15）、监控（3.15）、备份（3.16）都是同一个问题。

# 第 4 章 · 项目二：LNMP 与性能

## 4.1 LNMP 四个字母是什么

| 字母 | 软件 | 干什么 |
|---|---|---|
| **L** | Linux | 操作系统 |
| **N** | Nginx | 收 HTTP 请求，静态文件自己返回，PHP 请求转给下游 |
| **M** | MySQL | 存数据 |
| **P** | PHP（php-fpm） | 执行 PHP 代码 |

**为什么不是 Apache**：Nginx 用 epoll + 少量进程处理海量连接，内存占用低；Apache 的 prefork 模型一个连接一个进程，2G 机器扛不住。

## 4.2 Nginx 怎么把请求交给 PHP（FastCGI）

关键配置：
```nginx
location ~ \.php$ {
    fastcgi_pass   php:9000;          # ★ 转给谁（服务名 php，端口 9000）
    fastcgi_index  index.php;
    include        fastcgi_params;    # 一堆标准参数
    fastcgi_param  SCRIPT_FILENAME $document_root$fastcgi_script_name;  # ★ 要执行哪个文件
    fastcgi_connect_timeout 5s;
    fastcgi_send_timeout    30s;
    fastcgi_read_timeout    30s;
}
```

**四步理解**：
1. `location ~ \.php$`：正则匹配，凡是 `.php` 结尾的 URL 都走这里。
2. `fastcgi_pass php:9000`：**不是 HTTP 转发**，是 FastCGI 协议（一种二进制协议），默认走 TCP 9000。
3. `SCRIPT_FILENAME`：告诉 php-fpm"要执行哪个文件"。这一行最容易漏，漏了 php-fpm 会报 `Primary script unknown`。
4. `fastcgi_read_timeout 30s`：PHP 跑超过 30 秒就断，报 **504**。

**为什么 502 几乎总是这里的问题**：
- `php:9000` 解析不到（服务名写错、容器没起来）→ 502
- php-fpm 监听在 `127.0.0.1:9000` 而不是 `0.0.0.0` → 502（1.2 的坑）
- php-fpm 进程崩了 → 502

## 4.3 php-fpm 的进程模型与 `pm` 参数

**php-fpm 是什么**：PHP 的 FastCGI 进程管理器。它预先起好一堆 PHP 进程（worker），nginx 把请求交给它，它挑一个空闲 worker 干活，**干完不退出，继续等下一个**——这就是"进程池"。

```ini
pm = dynamic                    ; 动态调整
pm.max_children = 8             ; 最多 8 个 worker
pm.start_servers = 2            ; 启动时先起 2 个
pm.min_spare_servers = 1        ; 最少保留 1 个空闲
pm.max_spare_servers = 4        ; 最多保留 4 个空闲
pm.max_requests = 500           ; 每个 worker 处理 500 个请求后重启
```

| 参数 | 作用 | 设错会怎样 |
|---|---|---|
| `max_children` | **并发上限**：同时能处理几个请求 | 太小 → 请求排队，QPS 上不去；太大 → 内存爆 |
| `max_requests` | worker 处理 N 个请求后自杀重建 | 不设 → PHP 内存泄漏慢慢累积，最后 OOM |
| `request_slowlog_timeout` | 超过 N 秒记一条慢日志 | 不设 → 慢请求查不到是谁 |

**`max_children` 怎么估算（这是 2G 机器的核心）**：
```
单个 PHP 进程约 30MB
max_children = 可用内存 / 30MB
我给 php 容器 384M → 384 / 30 ≈ 12，取 8 留余量
```
**为什么不能贪大**：8 个 worker 全忙 = 8 × 30 = 240MB，再加上 opcache 和基础开销，接近 384M 上限。再大就会撞 `mem_limit` 被 OOM Kill。

**这就是为什么"QPS 到 800 就上不去了"**：不是缓存不够快，是 **worker 用完了在排队**。缓存解决"单次请求多快"，不解决"同时能处理多少"。

## 4.4 慢查询日志：先能看见，才能优化

```ini
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 0.5                        ; 超过 0.5 秒就算慢
log_queries_not_using_indexes = 1            ; 没走索引的也记（关键）
log_throttle_queries_not_using_indexes = 10  ; 同类语句每分钟最多 10 条，防刷屏
min_examined_row_limit = 1000                ; 扫描行数少于 1000 的不记，减噪音
```

**每个参数为什么这么设**：
- `long_query_time=0.5`：生产常用 1-2 秒，测试环境要"压得狠一点"才能抓到问题。
- `log_queries_not_using_indexes=1`：**这条比慢查询本身更有价值**——它抓的是"没走索引"的查询，哪怕现在很快，数据量涨了就会慢。
- `log_throttle...`：不加的话，一个没索引的查询每秒执行 100 次，日志瞬间几十 G，把磁盘写满。
- `min_examined_row_limit`：小表全表扫也很快，没必要记。

**怎么读**：
```bash
docker exec lnmp-mysql tail -50 /var/log/mysql/slow.log
# 关键三行：Query_time（总耗时）、Lock_time（等锁）、Rows_examined（扫描行数）
```
**判断标准**：`Rows_examined` 远大于返回行数 → 索引不合适。

## 4.5 索引与 B+ 树：为什么能快 1000 倍

**先说没有索引会怎样**：`SELECT * FROM orders WHERE user_id=100 LIMIT 20` → 数据库从第一行扫到最后一行（30 万行），逐行判断，取前 20 个。**全表扫描，O(n)**。

**有了索引**：数据库维护一棵 **B+ 树**，按 `user_id` 排好序。查找变成"从树根往下走 3 层，直接定位到 `user_id=100` 的位置，往后读 20 行"。**O(log n)**。

**为什么是 B+ 树**（三个理由）：
1. **矮胖**：一个节点存几百个 key，3 层就能装几千万行 → 磁盘 IO 只要 3 次。
2. **叶子节点是链表**：范围查询（`BETWEEN`、`>`）顺着链表扫就行。
3. **数据只在叶子节点**：内部节点只存索引，能装更多 key，树更矮。

**四个必须理解的概念**：

| 概念 | 含义 | 项目里的例子 |
|---|---|---|
| **聚簇索引** | InnoDB 的主键索引，叶子节点存**整行数据** | 按主键查最快，因为一次就到数据 |
| **二级索引** | 别的索引，叶子节点存**主键值** | `(user_id,status,created_at)` 索引进叶子后，还要拿主键**回表** |
| **回表** | 二级索引 → 主键 → 再去聚簇索引取整行 | 多一次查找，所以 `SELECT *` 比只查索引列慢 |
| **覆盖索引** | 要的列全在索引里，**不用回表** | `EXPLAIN` 的 `Extra: Using index` |

**复合索引的最左前缀原则**（最容易考）：
```sql
CREATE INDEX idx_user_status_time ON orders(user_id, status, created_at);
```
这棵索引相当于同时提供了：`(user_id)`、`(user_id,status)`、`(user_id,status,created_at)` 三种前缀。
- `WHERE user_id=1` ✅ 用到
- `WHERE user_id=1 AND status=2` ✅ 用到
- `WHERE status=2` ❌ **用不到**（跳过最左列）
- `WHERE user_id=1 AND created_at>'...'` ⚠️ 只能用到 `user_id`

**列序原则：等值条件在前，范围/排序在后**。因为范围条件之后的列在 B+ 树里是"局部有序"，排序用不上。

## 4.6 EXPLAIN 每个字段（优化必看）

```sql
EXPLAIN SELECT * FROM orders WHERE user_id=1 AND status=2 ORDER BY created_at DESC LIMIT 20;
```

| 字段 | 看什么 | 好 / 坏 |
|---|---|---|
| `type` | 访问类型 | `const` > `eq_ref` > `ref` > `range` > `index` > **`ALL`（全表扫，最差）** |
| `key` | 实际用了哪个索引 | `NULL` = 没用索引 |
| `rows` | 预估扫描行数 | 30 万 → 20 就是优化成功 |
| `filtered` | 扫描后剩余百分比 | 越低说明扫了很多没用的 |
| `Extra` | 附加信息 | `Using index`（覆盖索引，好）、`Using where`、**`Using filesort`（排序没走索引，坏）**、`Using temporary`（用了临时表，坏） |

**项目里的前后对比**：`type` 从 `ALL` → `ref`，`rows` 从 30 万 → 20，服务端耗时 **133ms → 0.11ms**。

## 4.7 四个查询，为什么只有一条变快（这才是真正的收获）

| 查询 | 优化前 | 优化后 | 倍数 | 为什么 |
|---|---|---|---|---|
| Q1 分页（`LIMIT 20`） | 133ms | **0.11ms** | ~1200× | 索引直接定位起点，只读 20 行 |
| Q2 分组统计（`GROUP BY`） | 145ms | 65.8ms | 2.2× | 索引减少了**回表**，但**减少不了必须扫的行数** |
| Q3 范围 + 排序 | — | — | 1.24× | `filesort` 还在，索引解决不了 |
| Q4 简单查询 | 本来就快 | 未优化 | — | **判断"不需要优化"也是能力** |

**两个结论**：
1. **索引的本质是"减少扫描行数 + 减少回表"**，不是"让所有查询变快"。
2. 聚合类查询如果必须扫 6 万行，索引只能帮你少回表；真正的解法是**预聚合**（提前算好存一张表）或**缓存**（Redis）。

## 4.8 测量陷阱：你测的是数据库，还是测量工具

**现象**：四条无关查询，优化前后 JOIN 那条**都是 66ms**，看起来"索引完全没用"。

**关键怀疑**：四个完全不同的查询，耗时**收敛到同一个值**——这不符合常理，说明测的不是查询。

**根因**：命令是 `date; docker exec mysql -e "SQL"; date`。**`docker exec` 启动一个进程要 30-70ms**，把 0.1ms 的查询差异彻底淹没了。**测量工具成了瓶颈。**

**修法**：用 `EXPLAIN ANALYZE` 看服务端的 `actual time`，或者在库内开 profiling。JOIN 那条实际只要 **0.14ms**，根本不用优化。

**普适道理**：当多个不同的东西测出同一个数字，先怀疑工具。

## 4.9 Redis 是什么，为什么快

**是什么**：内存里的 key-value 数据库。常用作**缓存**（也做 session、队列、分布式锁）。

**为什么快（四点）**：
1. **纯内存操作**：内存微秒级，磁盘毫秒级。
2. **单线程执行命令**：没有锁竞争、没有线程切换。
3. **IO 多路复用（epoll）**：一个线程同时盯大量连接。
4. **数据结构高效**：跳表、压缩列表、哈希表。

> 6.0 之后有"多线程"，但**只用于网络读写**，命令执行仍然是单线程。这点常被考。

## 4.10 cache-aside 模式：项目里的缓存怎么设计

```php
$data = redis.get("orders:$userId");
if ($data) return $data;                // 命中，0.4ms
$data = mysql.query("SELECT ...");      // 未命中，58ms
redis.setex("orders:$userId", 60, $data);   // 回填，TTL 60 秒
return $data;
```

**名字**：cache-aside（旁路缓存）——业务代码自己管缓存，Redis 只是旁边的一个加速层。

**四个设计决定，每个都要能说理由**：

| 决定 | 值 | 为什么 |
|---|---|---|
| TTL | 60 秒 | 缓存是**副本不是真相**，TTL 是"能容忍多久脏数据"的窗口 |
| maxmemory | 64m | 不设上限 Redis 会把 2G 机器吃光 |
| 淘汰策略 | `allkeys-lru` | 到顶时淘汰最久未用的，**而不是拒绝写入**（拒绝写入会让缓存变成故障源） |
| 持久化 | **关掉 RDB** | 缓存丢了可以回源重建；`fork` 的写时复制在 2G 机器上很伤 |

**降级**：连不上 Redis 就直接查 MySQL。**缓存是性能组件，不能变成可用性单点**。

## 4.11 缓存三大问题（面试必问）

| 问题 | 场景 | 后果 | 解法 |
|---|---|---|---|
| **穿透** | 查一个**不存在**的 key，每次都打到数据库 | 恶意攻击能打垮数据库 | 缓存空值（短 TTL）、布隆过滤器 |
| **击穿** | **热点 key 过期瞬间**，大量并发同时回源 | 数据库瞬间被打爆 | 互斥锁（只让一个去查）、逻辑过期 |
| **雪崩** | **大量 key 同时过期** 或 Redis 整体挂了 | 数据库被洪峰打垮 | TTL 加随机值、多级缓存、限流降级 |

## 4.12 为什么 session 要放 Redis（水平扩展的前提）

**问题**：PHP 默认把 session 存成**本地文件**（`/var/lib/php/sessions/`）。两个节点各自存一份 → 用户在 node1 登录，下次请求轮到 node2 → **不认识这个人，直接掉登录**。

**两种解法**：
| 方案 | 做法 | 缺点 |
|---|---|---|
| 会话粘滞（sticky） | LB 把同一用户固定到同一节点 | 节点挂了会话全丢；负载不均 |
| **会话共享** | session 存 Redis，两个节点都读同一份 | 需要 Redis（单点） 

**项目选第二种**，因为这是**无状态化**：应用节点不再保存任何"用户状态"，随时可以加节点、停节点。**这也是为什么压测到 800 QPS 后可以直接加 PHP 副本**——如果不是无状态，加副本反而会出问题。

## 4.13 压测：ab 的指标怎么看

```bash
ab -n 500 -c 20 "http://IP/index.php"                 # 走缓存
ab -n 500 -c 20 "http://IP/index.php?nocache=1"       # 强制回源（对照组）
```

| 指标 | 含义 | 怎么看 |
|---|---|---|
| `Requests per second` | **QPS** | 核心指标，12.6 → 794 |
| `Time per request`（第一行） | 所有请求的平均耗时 | 它的倒数 ≈ QPS |
| `Time per request`（第二行） | 每个连接的平均耗时 | ≈ 第一行 × 并发数，**看错列数字差 20 倍** |
| `Failed requests` | 失败数 | **要看构成，不只看数字** |
| `Non-2xx responses` | 非 2xx 响应数 | **这个才是真错误** |

**`Failed requests` 的陷阱**：压测显示几百个失败，拆开看：
```
Connect: 0   Receive: 0   Length: 861   Exceptions: 0
```
**全是 Length** —— 页面里有实时耗时和 session id，每次响应长度不同，ab 把"长度变化"也记成 failed。**这不是错误。**

**结论**：判断压测是否干净，看 `Non-2xx responses` 是不是 0，不看 `Failed` 总数。

**可信度怎么证明**：同一台机器、同一份数据、只差一个参数，每组跑两次——回源 12.62/12.63，缓存 819.74/793.93，**偏差 < 3%**。

## 4.14 瓶颈转移：缓存不会让 QPS 无限涨

```
回源组 79ms/请求  → 1000 ÷ 79 ≈ 12.6 QPS   （瓶颈：3 条 COUNT 聚合扫 30 万行）
缓存组 1.26ms/请求 → QPS 794                （瓶颈：PHP-FPM 的 8 个 worker + 2 核 CPU）
```

**这条认知比数字重要**：优化只是把瓶颈**从这一层推到下一层**。所以"QPS 到 800 之后想再加"的答案是：调 `pm.max_children`（受内存约束）→ 加 opcache → 加 PHP 副本 → 再往后是数据库和网络。

## 4.15 日志治理：为什么"配了上限还在涨"（第 25 坑）

**先理解日志有两个出口**：

| 出口 | 内容 | 谁管 |
|---|---|---|
| 容器 stdout/stderr | 进程打印到屏幕的内容 | **Docker** 的 `max-size`/`max-file` |
| 应用写的文件 | `access.log`、`slow.log` | **没人管**，就是宿主机上的普通文件 |

**所以只配 `max-size` = 只锁了前门**。两层都要做：
1. **容器层**：compose 里 `10m × 3`（实测灌 40MiB 进去，停在 3 个文件共 28M——因为 Docker 写入前检查，每个停在 9.6M 左右）。
2. **文件层**：`logrotate` 按天 + 20M 上限 + 留 7 份。

## 4.16 logrotate：为什么 nginx 和 mysql 的写法必须不同（最硬的一个点）

**切割日志的本质**：把 `access.log` 改名成 `access.log.1`，然后**让进程重新打开一个新的 `access.log`**。如果进程还握着旧文件的 fd，它会**继续往改名后的旧文件里写**，新的永远是 0 字节。

**两种让进程"重开"的方式**：

| 方式 | 做法 | 适用 |
|---|---|---|
| **信号重开** | 发信号让进程自己重开 fd | **nginx**：`USR1` |
| **copytruncate** | 先复制一份，再把原文件**清空**（`> access.log`） | **mysqld**：没有重开日志的信号，只能这样 |

```conf
# nginx
postrotate
    /usr/bin/docker kill --signal=USR1 lnmp-nginx >/dev/null 2>&1 || true
endscript

# mysql
copytruncate
```
**为什么 `docker kill` 而不是 `kill -USR1 $(cat nginx.pid)`**：
宿主机上拿不到**容器内**的 pid（两套 pid 命名空间）。`docker kill --signal=USR1 容器` 是直接给容器内的 PID 1 发信号，效果一样。

**如果给 mysql 照抄 nginx 的写法**：mysqld 不认 USR1，会一直写那个已改名的旧文件，新的 `slow.log` 永远 0 字节——**目录结构看着完全正常，日志却全丢了**。

**验证方式（不能只看 `.1` 出现）**：轮转之后**再发一次请求**，看新的 `.log` 有没有内容。没有 = 信号没送到。

## 4.17 内存预算：为什么必须按"理论峰值"算

**错误做法**：看 `docker stats` 当前 RSS，mysql 只占 190M，那给 256M 就够了。
**为什么错**：`innodb_buffer_pool_size` 配的是 256M，业务跑起来它会**逐渐吃满**。空载数字做不了规划。

**正确算法**：
```
mysql = buffer pool 256 + log buffer 16 + 基础开销 200 + 连接 buffer ≈ 480  → 给 768
php   = max_children 8 × 30M                                              → 给 384
nginx                                                                      → 128
redis                                                                     → 96
小计 1376M
系统常驻（含云厂商 agent 295M）
1376 + 295 = 1671M ≈ 总内存 1975M 的 85%，留 15% 余量
```

**为什么要留余量**：`gzip` 压缩备份、MySQL 临时排序、PHP 一次性上传大文件——这些都会临时吃内存。**没有余量 = 等 OOM**。

**OOM Killer 是什么**：内存耗尽时，内核按 `oom_score` 挑一个进程杀掉保系统。它挑的是 **RSS 最大的进程**，2G 机器上很可能就是 mysql。

## 4.18 `restart` 策略与 `live-restore`（验证重启自愈的坑）

```yaml
restart: unless-stopped
```
| 值 | 语义 |
|---|---|
| `no` | 不重启（默认） |
| `always` | 总是重启，包括手动 stop 的（daemon 重启后也会拉起） |
| `on-failure` | 非 0 退出才重启 |
| **`unless-stopped`** | 除了"手动 stop 过的"，其他情况都拉起 |

**为什么选 `unless-stopped`**：服务器重启、docker daemon 重启都会自动拉起；但你**主动 `docker stop` 的服务不该自己回来**——这个语义正好符合运维直觉。

**验证时的坑**：我先用 `systemctl restart docker` 验证，结果容器根本没停，restart 策略没机会触发——因为 `daemon.json` 里配了 `live-restore: true`（daemon 重启时容器继续跑）。

**正确验证**：直接 `reboot` 整机。四个容器全部自动拉起、页面 200、数据 30 万行完好——**这才是真的验证过**。

# 第 5 章 · 贯穿两个项目的方法论

技术点会忘，方法不会。这一章是整份文档最值钱的部分。

## 5.1 五段式排障法（所有故障通用）

```
① 现象：看到什么（哪个界面、哪个日志、哪一行报错、耗时多少）
② 排除：我先怀疑了什么，用什么命令否掉的
③ 根因：机器为什么会这样（原理）
④ 修法：怎么改，每步为什么
⑤ 验证：怎么证明真修好了
```

**为什么"排除"这一段最重要**：修法网上搜得到，**判断过程只能自己长出来**。面试官判断你是"做过"还是"背过"，就看你能不能说出"我先怀疑 A，用 B 命令排除了，又怀疑 C，也排除了"。

**反面例子**：
> "报错了，我搜了一下，改了这个参数就好了。" ← 不可信，且无法应对追问。

## 5.2 四种"假阳性"：看起来好了，其实没好

这是两个项目里最反复出现的一类问题，值得单独记。

| # | 假象 | 真相 | 怎么识破 |
|---|---|---|---|
| 1 | `docker ps` 显示 `Up` | 只代表进程活着，MySQL 还在初始化 | 用 `healthy` 或真的 `curl`/`SELECT 1` |
| 2 | `mysqladmin ping` 返回 0 | 认证失败也返回 0 | 用 `mysql -e 'SELECT 1'` |
| 3 | 恢复演练"耗时 0 秒" | 数据一条都没进去 | **找那个"不可能为 0"的指标** |
| 4 | 演练"9/20 失败" | 判定标准错了，服务一次没挂 | 看失败是否交替、看日志里有没有 499 |

**归纳成一句**：
> **"服务活着" ≠ "服务可用" ≠ "业务正确"。验证要验到你关心的那一层。**

- 关心"进程在不在" → `ps` / `Up`
- 关心"能不能接请求" → `curl -I` / 健康检查
- 关心"数据对不对" → 对账（行数、表数、索引数）
- 关心"用户能不能用" → 真实链路的端到端请求

## 5.3 验证的三层（这是你简历上"闭环意识"的实质）

| 层 | 例子 | 只做到这一层的后果 |
|---|---|---|
| **配置层** | `docker inspect` 看到 `mem_limit=768m`；`nginx -t` 通过 | 配置对了但没生效（改完没 reload、容器没重建） |
| **行为层** | 灌 40MiB 内存看会不会被 OOM；轮转后再发请求看新文件有没有内容 | 行为对了但结果可能不对 |
| **数据层** | 恢复后 orders 行数 = 300000；主从两边 count 一致 | — |

**项目里每一个"配置类"改动，我都补了行为层验证**：
- 日志上限 → 灌 40MiB 实测停在 28M
- 内存上限 → 起临时容器灌内存看会不会被杀
- 重启自愈 → 真 reboot 一次
- 告警 → 真制造一次故障收一条消息
- 备份 → 真的恢复一次并对账
- 日志轮转 → 轮转后再发请求

**这就是"闭环"**：配置改完不算完，行为验证过才算完，数据对得上才算真的完。

## 5.4 数字口径管理

面试里最容易被抓的不是"数字不好看"，而是**前后矛盾**。

**规则**：
1. **同一类数字只用一个来源**：`docs/05-验收记录` 里写多少，简历和口头就说多少。
2. **数字必须绑定环境**：`QPS 794` 是"单机 LNMP + 缓存"环境下的；合并成双节点后这组数字失效，必须重测或说明。
3. **给区间不如给"两次测量"**：12.62 / 12.63 比"大约 12.6"可信。
4. **主动说边界**：`133ms→0.11ms` 只对分页那条成立，另外三条只有 2.2 倍 / 1.24 倍。

## 5.5 交底：把"没做到"变成"想清楚了"

任何项目都有短板。**主动说出来**比被追问出来强十倍。

| 短板 | 标准交底话术 |
|---|---|
| 单机模拟双节点 | 只有一台 2C2G，用容器网络模拟双节点，**机制是真的，物理隔离是假的**；跨机才有网络分区和时钟漂移 |
| LB 是单点 | 明确知道，解法是 keepalived + VIP 或云 CLB，当前预算内没做 |
| 没有主动健康检查 | 开源版没有，只能被动摘除，第一个用户当探针；进阶用 tengine 或移到 K8s readinessProbe |
| Redis 是单点 | 2G 跑不了哨兵，所以设计成"连不上就降级查库" |
| K8s 不了解 | 只到能看 Pod 状态，原理还在学，不装懂 |

**一句总结**：
> **能力 = 做过的部分 + 清楚知道没做的部分。** 只说得清前半句的人，一追问就崩。
