# 第一部分：启动顺序与依赖就绪

## 1. 三个 nginx 容器启动即退出

### 现象

```bash
$ docker compose ps
NAME        IMAGE                  STATUS
node1-app   cluster-p1-node1-app   Up 2 minutes
node1-db    mysql:8.0              Up 3 minutes (healthy)
node2-app   cluster-p1-node2-app   Up 2 minutes
node2-db    mysql:8.0              Up 3 minutes (healthy)
```

7 个服务只活了 4 个，`lb`、`node1-web`、`node2-web` 不见了。
加 `-a` 才能看到它们其实是 **Exited (1)**：

```bash
$ docker compose ps -a
lb          nginx:1.27-alpine   Exited (1) 2 minutes ago
node1-web   nginx:1.27-alpine   Exited (1) 2 minutes ago

$ docker logs node1-web
nginx: [emerg] host not found in upstream "app" in /etc/nginx/conf.d/default.conf:23
```

### 原理：nginx 到底什么时候解析主机名

这是整条故障的核心，必须理解透：

**nginx 在「读配置」阶段就把 upstream 里的主机名解析成 IP，写进共享内存。**
不是在收到请求时才去查 DNS。

为什么要这么设计？因为 nginx 追求极致性能——如果每个请求都做一次 DNS 查询，
高并发下光是解析就能把 CPU 打满。代价是：**后端 IP 变了必须 reload 才能生效**。

而容器里的 DNS 是 Docker 内嵌的（`127.0.0.11`），它的规则很朴素：

> **只有「已经启动并接入网络」的容器，才有对应的 A 记录。**

于是就有了这个经典时序问题：

```
t0   compose 同时创建 node1-web 和 node1-app
t1   node1-web 先跑起来，nginx 开始读配置
t2   nginx 解析 "app" → 问 127.0.0.11 → 此时 app 还没注册 → NXDOMAIN
t3   nginx: [emerg] host not found in upstream "app" → 进程直接退出
t4   node1-app 才启动完成，但已经没人等它了
```

同理 `lb` 解析 `node1-web`/`node2-web` 时，两个 web 容器刚创建，也可能还没注册。

### 定位：为什么能确定是「抢跑」而不是配置写错

三个判断依据：

1. **报错是 `host not found`，不是 404/502** —— 说明 nginx 压根没起来，不是转发逻辑错
2. **只有 nginx 挂，app 和 db 都活着** —— 说明网络本身通，否则 app 连 db 也会失败
3. **手动 `docker start node1-web` 就能起来** —— 因为此时 app 已经在跑了，DNS 有记录

第 3 点最关键：**同样的配置，换个时间点就能成功**，那问题一定在「时序」而不是「配置内容」。

### 修法：两道保险

**第一道：用 `depends_on` 保证顺序**

```yaml
node1-web:
  depends_on:
    node1-app: { condition: service_started }   # app 先创建、先入网
```

`service_started` 只保证「容器进程已启动」，不保证「服务能响应」——
但对 DNS 注册来说够了，因为**容器一启动就会接入网络、注册 DNS**。

> 如果依赖的是 MySQL 这种「起来了但还要初始化」的服务，就要用
> `condition: service_healthy`，见第 2 条。

**第二道：`restart: unless-stopped` 兜底**

```yaml
restart: unless-stopped
```

即使某次还是抢跑了，容器退出后 Docker 会自动重启它——**这时 app 早就就绪，第二次一定成功**。

注意 Docker 的重启不是死循环狂刷，而是有退避的（100ms → 200ms → … 最长 1 分钟），
所以不会把 CPU 打满。

### 换别的做法会怎样

| 方案 | 为什么不选 |
|---|---|
| 配置里写死 IP（`172.21.0.12:8080`） | 容器重建 IP 会变，等于埋雷 |
| `extra_hosts` 写死主机名映射 | 同样怕 IP 变化，且要手工维护 |
| `resolver 127.0.0.11 valid=10s` + 变量 `proxy_pass http://$backend:8080` | **这是最彻底的方案**：变量形式让 nginx 在请求时才解析。但代价是——**用了变量就不能再用 upstream 块**，会丢掉负载均衡、`max_fails` 被动摘除、`keepalive` 连接池。项目一的重点是 LB，所以不采用 |

**结论**：要 LB 能力就保留 upstream + 保证启动顺序；要动态后端就牺牲 LB 换 resolver。
**这是设计取舍，不是谁对谁错**——面试时这么答，比背命令高一档。

### 一句话记住

> **nginx 的 upstream 是「启动期解析」，Docker DNS 是「运行中才注册」——两者天然有时序冲突。**

### 面试怎么讲

> 「第一次 `docker compose up` 时三个 nginx 全退了，日志是 `host not found in upstream`。
> 我一开始怀疑是配置写错，但手动 `docker start` 又能起来——同样的配置换个时间点就成功，
> 说明是时序问题。想明白后确认：nginx 在启动阶段就解析 upstream 主机名，
> 而 Docker 内嵌 DNS 只收录已运行的容器，web 容器抢跑到 app 前面了。
> 修法是 `depends_on` 排顺序，再加 `restart: unless-stopped` 兜底。」

## 2. 应用起来就连不上数据库

### 现象

`node1-app` 日志刷屏：

```
[app] waiting DB (1/40): (2003, "Can't connect to MySQL server on 'node1-db'")
[app] waiting DB (2/40): ...
```

### 原理：MySQL 容器「Up」的三个阶段

`docker compose ps` 显示 `Up` 只代表**容器里的主进程在跑**。而 MySQL 官方镜像的启动是这样的：

```
阶段 1  临时 server 初始化数据目录（建系统表）        ← 端口可能已监听，但不对外服务
阶段 2  关闭临时 server
阶段 3  启动正式的 mysqld，加载我们的 cnf，开始接受连接
```

2G 内存的机器上，这一套要 **40~60 秒**。这期间：

- 容器状态是 `Up`（进程在跑）
- 但 3306 还连不上，或者连上了立刻被拒

### 定位：怎么确认「是在等」而不是「永远连不上」

乱猜是没用的。用三个动作把「慢」和「错」分开：

```bash
# ① 看 app 有没有在重试（有重试说明它在等，不是直接崩）
docker logs -f node1-app | head
#   看到 waiting DB (1/40)、(2/40)… 逐秒递增 → 在等
#   看到 Traceback 直接退出          → 代码/配置错，等也没用

# ② 看 db 到底是什么状态（Up 不够，要看健康）
docker compose ps
#   Up (healthy)   → 真的好了，那问题在 app 侧（密码/库名/主机名）
#   Up (health: starting) → 还在初始化，正常，继续等
#   Up (unhealthy) → 初始化失败了，去看 db 日志

# ③ 直接从另一个容器里试探（绕开 app，验证网络和密码）
docker exec node1-web sh -c 'nc -z -w2 node1-db 3306 && echo PORT_OK || echo PORT_FAIL'
docker exec node1-db  mysql -uroot -p"$PASS" -e 'SELECT 1'
```

**判断表**：

| ① 有无重试 | ② db 状态 | ③ 端口 | 结论 |
|-----------|----------|--------|------|
| 有，逐次递增后成功 | starting→healthy | OK | 正常的「等」，什么都不用改 |
| 有，40 次全失败 | healthy | FAIL | 主机名/网络错（不同 network） |
| 有，40 次全失败 | healthy | OK | 认证错：密码、库名、`root@%` 权限 |
| 没有，直接 Traceback | 任意 | 任意 | 代码异常，跟就绪无关 |

这一步的价值在于：**「等」和「连不上」的修法完全不同**——
一个是加超时/加健康检查，一个是查网络/查密码。不区分就动手，会改错地方。

### 修法：两层保险

**第一层：编排层用健康检查**

```yaml
mysql:
  healthcheck:
    test: ["CMD-SHELL", "mysqladmin ping -h 127.0.0.1 -uroot -p$$MYSQL_ROOT_PASSWORD --silent"]
    interval: 15s
    timeout: 5s
    retries: 8
    start_period: 60s      # ★ 启动后 60 秒内的失败不计入 retries

app:
  depends_on:
    mysql: { condition: service_healthy }   # 真的能 ping 通了才启动
```

`start_period` 很关键：没有它，MySQL 还在初始化时健康检查就已经开始计失败次数，
8 次（2 分钟）没等到就被判定 unhealthy，容器会被反复重建。

**第二层：应用自己也要会等**

`app.py` 里的 `wait_for_db()`：

```python
for i in range(max_retry):
    try:
        conn = get_conn(); conn.close(); return True
    except Exception:
        time.sleep(2)
```

为什么编排层已经保证了，应用还要写？因为**生产环境里数据库可能中途重启**，
`depends_on` 只在启动时管一次。应用具备重连能力才是真的健壮。

### 一句话记住

> **`Up` 是「进程活着」，`healthy` 才是「服务可用」。**
> **`depends_on` 只能排「启动顺序」，只有 `condition: service_healthy` 才保证「能用了」。**

### 面试怎么讲

**面试官会问**：Compose 里 `depends_on` 保证依赖先启动，为什么服务还是连不上数据库？

**答法（30 秒，四句）**：
1. `depends_on` 默认是 `service_started`，只等「容器里的进程起来了」；
2. 但 MySQL 镜像要先初始化数据目录，这期间端口不通，`Up` 了没用；
3. 所以要把条件换成 `service_healthy`，配一个 `mysqladmin ping` 的健康检查；
4. 而且健康检查要加 `start_period`，否则初始化阶段就被记成失败、容器被反复重建。

**追问 1：`start_period` 和 `retries` 有什么区别？**
`retries` 是「连续失败几次判为 unhealthy」；`start_period` 是「启动后这段时间内的失败直接不计」。
前者管运行期，后者管启动期。

**追问 2：那应用层还需要重连吗？**
需要。`depends_on` 只管容器启动那一刻，运行中数据库重启它管不了。应用要有重试/重连。

# 第二部分：标识符与类型不匹配

## 3. 健康检查把两个 IP 拼成了一串

### 现象

```
[2026-10-27 14:32:16]   ✘ node1-web(172.20.0.11172.21.0.11) HTTP=000
[2026-10-27 14:32:16]   ✘ node2-web(172.20.0.12172.22.0.11) HTTP=000
[2026-10-27 14:32:19] ✘ 发现 2 项异常，触发告警
```

`HTTP=000` 是 curl 的说法：**请求根本没发出去**（DNS 失败、地址非法、连接被拒都是 000）。

### 原理：Go 模板里 `range` 和 `index` 的区别

出问题的代码：

```bash
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' node1-web
```

`.NetworkSettings.Networks` 是一个 **map**（网络名 → 网络详情）。`range` 的语义是
**遍历所有元素并依次渲染**，中间没有任何分隔符。于是：

```
front 网段  → 172.20.0.11
net-node1  → 172.21.0.11
拼接结果    → 172.20.0.11172.21.0.11     ← 非法地址
```

再加 `| head -1` 也没用——`head -1` 是按**行**取的，而输出的是一整行。

### 定位：一眼看出问题在哪

看括号里的内容：`172.20.0.11172.21.0.11` 有 6 段数字、24 位——**根本不是 IPv4**。
正常应该是 4 段。这种「两串粘一起」的形状，只有一种原因：**模板遍历没做分隔**。

再验证：

```bash
$ docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}} {{end}}' node1-web
172.20.0.11 172.21.0.11        # 加个空格就看出是两个了
$ docker network ls | grep front
NETWORK ID     NAME                DRIVER
xxxx           cluster-p1_front    bridge
```

### 修法：用 `index` 精确取值

```bash
ip=$(docker inspect -f \
  "{{with index .NetworkSettings.Networks \"cluster-p1_front\"}}{{.IPAddress}}{{end}}" \
  "$n")
```

三个要点：

1. **`index` 是「按键取值」**，不是遍历。键就是网络全名
2. **网络全名 = `<compose 项目名>_<网络名>`**。项目名来自 `docker-compose.yml` 的 `name: cluster-p1`，
   所以全名是 `cluster-p1_front`。改项目名，这里要跟着改——所以我把它提成了变量
   `FRONT_NET="${FRONT_NET:-cluster-p1_front}"`
3. **`with` 相当于 if-not-nil**：网络不存在时输出空字符串，而不是报 `<no value>`

再补一个兜底（网络名对不上时，取任意一个 `172.20.x`）：

```bash
ip=$(docker inspect "$n" | python3 -c '
import json,sys
nets=json.load(sys.stdin)[0]["NetworkSettings"]["Networks"]
print(next((v["IPAddress"] for v in nets.values() if v["IPAddress"].startswith("172.20.")), ""))')
```

### 换别的做法会怎样

| 方案 | 评价 |
|---|---|
| 从**宿主机** curl 容器 IP | 测的是「跨网桥可达性」，比较接近真实调用路径，可以保留 |
| 进容器 curl localhost | 只测了容器内 nginx 自己，**测不出网络问题**，不推荐单独用 |
| 通过 LB 测 `/healthz` | 只覆盖「被 LB 选中的那个节点」，另一个节点可能挂了也发现不了 |
| 用 `docker exec node1-web wget -qO- localhost/healthz` | 不依赖 IP，最稳；但需要镜像里有 wget（nginx:alpine 不带） |

**最优组合**：LB 侧测一次（入口可用）+ 每个节点按 IP 各测一次（单点可用），
这正是脚本现在的结构。

### 一句话记住

> **`range` 是拼接，`index` 是取值。一个对象有多个属性时，先问「我要哪一个」。**

### 面试怎么讲

**面试官会问**：你怎么在脚本里拿到某个容器的 IP？有多个网络时要注意什么？

**答法**：不能直接 `{{.IPAddress}}`——接多个网络时它是空的。
要用 `{{with index .NetworkSettings.Networks "网络全名"}}{{.IPAddress}}{{end}}`，
因为 `range` 会把所有网络**当字符串拼起来**（这就是我那次得到 `172.20.0.11172.21.0.11` 的原因）。

**追问：为什么不用 `docker inspect | grep IPAddress`？**
多个网络会出多行，还得猜哪行是哪个网卡；用 `index` 指名网络名，结果是确定的。

**加分点**：能说出「网络全名是 `<项目名>_<网络名>`」——很多人卡在这，明明网络存在却 `index` 不到。

## 4. 接口报 `Object of type Decimal is not JSON serializable`

### 现象

```bash
$ curl -s "http://127.0.0.1/api/orders?user_id=1"
{"node":"node1","error":"Object of type Decimal is not JSON serializable"}
```

而同一个节点的 `/api/stats`（只查 `COUNT(*)`）是正常的。

### 原理：数据库驱动返回的不是 Python 原生类型

`orders.amount` 的类型是 `DECIMAL(10,2)`。PyMySQL 读到它时，**不会给你 float**，
而是返回 `decimal.Decimal` 对象：

```python
>>> cur.execute("SELECT amount FROM orders LIMIT 1")
>>> row = cur.fetchone()
>>> type(row[0])
<class 'decimal.Decimal'>
```

为什么驱动要这么做？因为 **float 是二进制浮点，存不下精确的十进制小数**：

```python
>>> 0.1 + 0.2
0.30000000000000004        # 这就是 float 的精度问题
>>> Decimal('0.1') + Decimal('0.2')
Decimal('0.3')             # 精确
```

金额场景用 float 会导致对账差几分钱，所以驱动把选择权交给你：**要么用 Decimal，要么自己显式转**。

`DATETIME` 同理，返回的是 `datetime.datetime` 对象。

而 `json.dumps` 只认识这几种：`dict / list / str / int / float / bool / None`。
遇到其他类型就抛 `TypeError`——**这不是 bug，是 JSON 规范本身没有 decimal 类型**。

### 定位：为什么只有 `/api/orders` 挂

对比两个接口的返回内容：

| 接口 | 返回字段 | 类型 | 结果 |
|---|---|---|---|
| `/api/stats` | `total_orders`, `max_id` | int | ✅ |
| `/api/health` | 字符串、布尔 | str/bool | ✅ |
| `/api/orders` | `amount`, `created_at` | **Decimal / datetime** | ❌ |

**只有查明细的接口会炸**——这个对比直接指向「某个字段的类型不对」。

### 修法：给 `json.dumps` 一个兜底函数

```python
body = json.dumps(data, ensure_ascii=False, default=str).encode("utf-8")
```

`default=` 的语义是：**遇到序列化不了的对象时，调用这个函数，用它的返回值代替**。
`str(Decimal('9.90'))` → `"9.90"`，`str(datetime(...))` → `"2026-10-19 22:47:21"`。

**为什么不转 float**：`float(Decimal('9.90'))` 得到 `9.9`（丢失末尾 0），
大额数字还会丢精度。转字符串是**无损**的，前端要计算时自己用 decimal 库处理。

### 换别的做法会怎样

| 方案 | 评价 |
|---|---|
| SQL 里 `CAST(amount AS CHAR)` | 可行，但每个查询都要记得写，容易漏 |
| 逐行 `tuple(str(x) ...)` | 可行，但把「展示层格式」混进了数据层 |
| `default=str` | 一行解决，**代价是所有未知类型都会变字符串**（比如 `bytes` 会变成 `"b'...'"`），本项目够用 |

### 一句话记住

> **驱动返回的类型 ≠ Python 原生类型；JSON 也没有 decimal，序列化前必须兜底。**

### 面试怎么讲

**面试官会问**：接口返回订单列表时报序列化错误，你怎么定位？

**答法**：先看报错里的类型名——`Object of type Decimal` 说明驱动把 `DECIMAL` 读成了
`decimal.Decimal`，`datetime` 同理。JSON 规范里只有数字/字符串/布尔/null/数组/对象，
没有「高精度小数」和「时间」，所以必须显式转换。

**关键一句**：**别直接 `float()`**。金额转 float 会丢精度（`89.50` 可能变 `89.49999`），
用 `default=str` 或格式化成两位小数字符串。

**追问：这算不算掩盖问题？**
不掩盖。`default=str` 是「兜底」，正确做法是在返回结构里显式定义字段类型；
兜底的价值是防止以后加了新表、新字段又炸一次。

> 这一类最坑：**不报错，但功能是坏的**。只能靠「结果是否符合预期」发现。

## 5. `/health` 永远失败，`/api/stats` 却正常

### 现象

状态页上「应用健康」永远是红色「请求失败」，但同一页的「订单总数」显示正常。

### 原理：nginx 的 location 匹配规则

nginx 收到 `/health` 后，按这个优先级挑 location：

```
1. location = /health        精确匹配（最高）
2. location ^~ /api/         前缀匹配且不再尝试正则
3. location ~ \.php$         正则匹配（按出现顺序）
4. location /api/            普通前缀匹配（取最长匹配）
5. location /                兜底
```

当时 `node.conf` 里只有：

```nginx
location / { try_files $uri $uri/ /index.html; }     # 兜底
location /api/ { proxy_pass http://app:8080; }        # 只代理 /api/
```

`/health` **不以 `/api/` 开头**，所以匹配到的是 `location /`：

```nginx
try_files $uri $uri/ /index.html;
# /health 这个文件不存在 → 内转到 /index.html
```

结果：**返回 200 + 一整个 HTML 页面**。

前端拿到 HTML 去 `res.json()`，解析失败抛 `SyntaxError`，被 `catch` 抓住，
于是显示「请求失败」——**看起来像后端挂了，其实是路由没配**。

### 定位：一个 200 却「失败」的请求

关键思路：**状态码是 200，说明 nginx 没报错，那问题就在「返回的内容」上**。

```bash
$ curl -s -i http://127.0.0.1/health | head -5
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8      ← 破案了，接口返回了 HTML
```

如果当时先看 `Content-Type`，30 秒就能定位。**这也是我后来在文档里强调
「接口异常先看响应头」的原因**。

### 修法：加一条精确匹配

```nginx
location = /health {
    proxy_pass http://app:8080/health;
}
```

- `= /health` 是**精确匹配**，优先级最高，不会被 `location /` 抢走
- `proxy_pass http://app:8080/health` 带完整路径：请求 `/health` 会被转发到后端的 `/health`

> 注意 `proxy_pass` 的两种写法差别很大：
> `proxy_pass http://app:8080;`（不带路径）会**保留原始 URI**；
> `proxy_pass http://app:8080/health;`（带路径）会**替换成这个路径**。
> 这里两者结果一样，但理解差别能避免另一类坑。

### 一句话记住

> **接口「200 但前端解析失败」，十有八九是返回了 HTML——先看 `Content-Type`。**

### 面试怎么讲

**面试官会问**：前端调用接口报 `Unexpected token '<'`，后端却说日志里 200，谁的问题？

**答法**：`<` 说明拿到的是 HTML，不是 JSON。八成落到 SPA 的 fallback 上去了
（`try_files ... /index.html`）。先 `curl -i` 看 `Content-Type`：
是 `text/html` 就说明路由没匹配到后端，问题在 nginx 的 location。

**关键一句**：**「200」只说明「服务器答应了这个请求」，不说明「返回的是你以为的东西」**。

**追问：为什么 `/api/stats` 正常，`/health` 不正常？**
因为 `location /api/` 是前缀匹配，能覆盖 `/api/xxx`；`/health` 不在这个前缀下，
就落到了 `location /` 的兜底规则。所以要么加 `location = /health`，要么把它挪到 `/api/` 下。

## 6. 页面刷新，节点永远不切换

### 现象

```bash
# curl 循环：完美交替
$ for i in $(seq 1 6); do curl -s http://127.0.0.1/whoami; done
node=node1-web
node=node2-web
node=node1-web
...

# 但浏览器里点「刷新」，永远显示 node2-web
```

### 原理：轮询的计数单位是「请求」，不是「用户」

nginx 的默认 upstream 策略是 **round-robin（加权轮询）**：

> 每来一个请求，就取上游列表里的下一个，**下一个请求取再下一个**。

它不认 Cookie、不认 IP、不认会话——**它只数请求**。

而页面一次「刷新」实际发了 **4 个** HTTP 请求：

| 顺序 | 请求 | 说明 |
|---|---|---|
| 1 | `/whoami` | 显示节点名 |
| 2 | `/health` | 老代码里的一行死代码，重复请求了一次 |
| 3 | `/health` | 正式的健康检查 |
| 4 | `/api/stats` | 订单统计 |

4 是偶数，于是每次刷新的起点都落在**同一个奇偶位**：

```
第 1 次点击:  whoami→A   health→B   health→A   stats→B
第 2 次点击:  whoami→A   health→B   health→A   stats→B    ← 又回到 A
```

所以 `/whoami` 每次都命中同一台，看起来像「轮询失效」。

### 定位：区分「轮询坏了」和「测法不对」

关键对比：**同一个 LB，换一种测法结果就不同**。

- `curl` 循环：每次 1 个请求 → 交替 ✅
- 浏览器刷新：每次 4 个请求 → 不交替 ❌

**如果轮询真的坏了，curl 也不会交替**。所以坏的不是轮询，是「测量方式」。

### 修法：两个层面

**1. 删掉多余请求**（代码问题）

删掉那行死代码后，每次刷新变成 3 个请求（奇数）→ 每次刷新的起点奇偶位翻转 →
`/whoami` 就会交替了。

**2. 验证一律用单请求**（方法问题）

```bash
# 看节点 nginx 打的响应头
for i in $(seq 1 6); do curl -sI http://127.0.0.1/whoami | grep -i x-served-by; done

# 或者看 LB 记录的后端地址
for i in $(seq 1 6); do curl -sI http://127.0.0.1/ | grep -i x-upstream-node; done
```

### 引申：真实站点本来就不「粘」

一个网页几十个请求，RR 会把它们分散到多台机器上——**用户的「这次访问」本来就不是一台机器在服务**。
所以：

- 静态资源无所谓（谁给都一样）
- 有状态的东西（登录态）**必须外置**（Redis 存 session），或者用 `ip_hash` / cookie 粘滞
- `ip_hash` 的代价是**负载不均**（同一出口 NAT 的一批用户会压到一台）

这就是项目二里要引入 Redis 的原因。

### 一句话记住

> **RR 不认识「用户」，只认识「请求」。测轮询必须用单请求。**

### 面试怎么讲

**面试官会问**：负载均衡是轮询，但浏览器里一直访问到同一台后端，是配置错了吗？

**答法**：先验证是不是测法问题。**用一个请求测**（`curl` 循环），
如果单请求严格交替，说明轮询是好的，只是你的页面一次发了很多请求（静态资源、接口并发），
偶数个请求正好绕回同一台。

**关键一句**：**「负载均衡」均衡的是连接/请求，不是会话。要按人会话粘住，得配 `ip_hash` 或 session 共享。**

**追问：那生产上怎么保证用户登录状态？**
不是我这里改 nginx 的事，是应用层做 session 共享（Redis）或 token 无状态。
`ip_hash` 只能缓解，用户换了出口 IP 就漂了，而且某个后端挂了会掉一片会话。

## 7. 延迟告警形同虚设（字段名变了）

### 现象

`health_check.sh` 里明明有这段：

```bash
LAG=$(echo "$SLAVE_OUT" | grep -m1 'Seconds_Behind_Master:' | awk '{print $2}')
if [[ "$LAG" =~ ^[0-9]+$ ]] && [[ "$LAG" -gt "$LAG_THRESHOLD" ]]; then
    ALARMS+=("主从延迟 ${LAG}s")
fi
```

但从上线起**从来没触发过**。看起来是「延迟一直是 0，好事」——
直到手动执行 `SHOW REPLICA STATUS\G` 才发现：

```
                  Source_Host: node1-db
             Seconds_Behind_Source: 0        ← 字段叫 Source，不叫 Master
```

### 原理：MySQL 8.0.23 的术语替换

MySQL 官方在 8.0.22/8.0.23 把复制相关术语从 master/slave 全面改成 source/replica：

| 旧 | 新 |
|---|---|
| `SHOW SLAVE STATUS` | `SHOW REPLICA STATUS` |
| `Seconds_Behind_Master` | `Seconds_Behind_Source` |
| `Master_Host` | `Source_Host` |
| `CHANGE MASTER TO` | `CHANGE REPLICATION SOURCE TO` |

你的镜像是 **8.0.46**，早就是新名字了。

于是 `grep 'Seconds_Behind_Master:'` 取到空字符串：

```bash
LAG=""                                        # 空
[[ "" =~ ^[0-9]+$ ]]  →  false                # 正则不匹配
# → 整个 if 被跳过，永远不会告警
```

**这就是最危险的一类 bug：不报错、不崩溃、只是沉默地失效。**

### 定位：怎么发现「监控其实没在工作」

光看「没告警」是发现不了的——没告警可能是真的好。要靠**故障注入**：

```bash
# 把延迟人为造出来（在主库跑一个长事务，从库就会落后）
# 然后看告警是否触发
```

如果造了延迟还不报警，就说明检查逻辑坏了。**监控系统本身也要被监控**。

### 修法：兼容两种写法

```bash
LAG=$(echo "$SLAVE_OUT" | grep -m1 -E 'Seconds_Behind_(Source|Master):' | awk '{print $2}')
```

`-E` 开扩展正则，`(Source|Master)` 两个名字都认，跨小版本都能跑。

### 更稳的写法（进阶）

`grep + awk` 依赖输出格式，其实很脆。更稳的是让 MySQL 直接给你键值：

```sql
SELECT SERVICE_STATE FROM performance_schema.replication_applier_status;
```

或者用 `SHOW REPLICA STATUS\G` 输出后用 `awk -F': '` 解析成关联数组：

```bash
declare -A ST
while IFS=': ' read -r k v; do [[ -n $k ]] && ST[$k]="$v"; done <<< "$SLAVE_OUT"
LAG="${ST[Seconds_Behind_Source]:-${ST[Seconds_Behind_Master]:-}}"
```

但注意：本项目为了省内存把 `performance_schema` 关了，所以查不了表，只能解析文本。

### 一句话记住

> **升级 MySQL / Nginx / Docker 后，所有「靠 grep 字段名」的监控脚本都要重新核对。**
> **「没告警」不等于「没问题」。**

### 面试怎么讲

**面试官会问**：你的监控怎么保证「真出问题时一定会告警」？

**答法**：监控最危险的状态不是告警太多，是**静默失效**。我踩过这个：
MySQL 8.0.23 把 `Seconds_Behind_Master` 改名为 `Seconds_Behind_Source`，
脚本 grep 旧字段拿不到值，`awk` 得到空串，`if [ "$lag" -gt 10 ]` 直接报错或被跳过，
**永远不告警**，看起来一切正常。

**做法**：① 取不到值时按「异常」处理（fail-fast，而不是 fail-silent）；
② 每条告警规则都要有「反向验证」——故意造一次故障，确认真的会响。

**关键一句**：**没有验证过的告警等于没有告警。**

## 8. 改了代码，容器里没变化

### 现象

改了 `app/app.py`，重启容器、甚至 `docker compose restart`，行为还是旧的。

### 原理：镜像里的文件是「复制进去的快照」

看 `app/Dockerfile`：

```dockerfile
FROM python:3.11-alpine
WORKDIR /app
COPY app.py .            # ★ 把文件复制进镜像层
CMD ["python", "-u", "app.py"]
```

`COPY` 发生在 **build 阶段**，产物是**镜像的一层只读文件系统**。
容器启动时只是在镜像之上加一个可写层，**并不会去读你宿主机上的 `app.py`**。

对比项目一里另外两种挂载方式：

| 内容 | 方式 | 改了宿主机文件会怎样 |
|---|---|---|
| `app/app.py` | `COPY` 进镜像 | **不变**，必须重新 build |
| `nginx/lb.conf` | `volumes: ./nginx/lb.conf:...:ro` | **立即生效**（但 nginx 要 reload 才读新配置） |
| `www/index.html` | `volumes: ./www:...` | **立即生效**（浏览器下次请求就是新文件） |

### 定位：先确认「容器里看到的文件」和宿主机是否一致

```bash
# 对比 md5
$ md5sum app/app.py
$ docker exec node1-app md5sum /app/app.py
```

两个值不一样 → 就是镜像里的旧文件，和宿主机无关。

再看挂载情况：

```bash
$ docker inspect node1-app --format '{{json .Mounts}}'
[]
```

`app` 容器**没有任何挂载**，所以它的代码只能来自镜像——结论明确。

### 修法

```bash
docker compose up -d --build node1-app node2-app
```

- `--build`：**先重新 build 镜像**，再重建容器
- 不加 `--build`：compose 只在「配置变了」时重建容器，**镜像还是旧的**
- `docker compose restart`：连容器都不重建，只是重启进程，**最没用**

### 换别的做法会怎样

| 方案 | 评价 |
|---|---|
| 开发环境把代码 bind mount 进容器 | 改完即生效，适合调试；但会掩盖「镜像里到底有什么」，上线前必须验证纯镜像能跑 |
| `docker cp` 拷进容器 | 临时验证可以，**容器一重建就丢**，绝不能依赖 |
| 每次都 `down && up --build` | 太慢，`up -d --build` 会做「最小变更」 |

### 引申：`sed -i` 改挂载的配置文件，容器里看不到

这个坑有个更隐蔽的变种，本项目改 `lb.conf` 时正面撞上。

`docker-compose.yml` 里是这样挂的：

```yaml
volumes:
  - ./nginx/lb.conf:/etc/nginx/conf.d/default.conf:ro
```

**单文件挂载（不是目录），绑的是「inode」**。而 `sed -i` 的工作方式是：

```
1. 把结果写到临时文件   .sedXXXXXX
2. rename(临时文件, 目标文件)      ← 目标路径指向了一个新 inode
3. 老 inode 被删除
```

宿主机 `ls -l` 看着内容变了、`cat` 出来也变了，但**容器里那个挂载点还钉在旧 inode 上**，
它读到的永远是改之前的内容。`nginx -s reload` 也读不到新配置。

判断方法：

```bash
diff <(cat nginx/lb.conf) <(docker exec lb cat /etc/nginx/conf.d/default.conf)
```

**有差异 = 你改的和它看的不是同一个文件。**

正确改法（保持 inode 不变）：

```bash
sed 's/旧内容/新内容/' nginx/lb.conf > /tmp/new.conf
cat /tmp/new.conf > nginx/lb.conf        # ★ 用 > 覆盖内容，不换文件
```

`>` 是截断原文件后写入，**inode 不变**，挂载立即看到新内容。改完 `nginx -t && nginx -s reload`。

| 改法 | inode | 容器能否看到 |
|---|---|---|
| `sed -i` | **换新** | ❌ 看不到 |
| `perl -pi -e` | 换新 | ❌ |
| `cat /tmp/new > 原文件` | 不变 | ✅ |
| 删除容器重建（`up -d --force-recreate`） | 不管 | ✅ 但会中断服务 |

> 顺带说明：**如果挂的是整个目录**（比如 `./nginx:/etc/nginx/conf.d`），
> 目录挂载绑定的是路径解析，`sed -i` 换 inode 也没问题。**只有单文件挂载才有这个坑。**

### 一句话记住

> **`COPY` 是快照，`bind mount` 是通道。改快照要重建镜像，改通道即时生效。**
> **但单文件挂载的「通道」绑的是 inode —— `sed -i` 会把它换掉，等于悄悄切断了通道。**

### 面试怎么讲

**面试官会问**：改了代码但容器里没生效，你会怎么查？

**答法**：先确认「容器里那份文件」和「宿主机那份文件」是不是同一份。
在容器里 `md5sum` 一下，跟宿主机比：一致的说明是同一份（挂载），不一致说明是镜像里的旧副本（`COPY`）。

**关键一句**：**`COPY` 是在构建那一刻复制进去的，之后宿主机再改也没用，必须 `docker compose up -d --build`。**

**追问：生产上应该用哪种？**
两种都用，但用途不同——**代码/配置**在开发期用 bind mount 便于调试，
**上线**用 `COPY` 打进镜像，保证「镜像即版本」，可回滚、可复用、不依赖宿主机目录。

## 9. 手写镜像域名，反而拉不到

### 现象

```bash
$ docker pull ccr.ccs.tencentyun.com/library/nginx:1.25-alpine
Error response from daemon: manifest for ccr.ccs.tencentyun.com/library/nginx:1.25-alpine not found: manifest unknown
```

但 `docker pull nginx:1.25-alpine` 一次就成功了。

### 原理：mirror 只在「不写 registry」时生效

Docker 拉镜像时先解析镜像名：

```
nginx:1.25-alpine                  → 没有域名 → 认为来自 Docker Hub
                                     → 依次尝试 registry-mirrors 里的每个源
ccr.ccs.tencentyun.com/library/...  → 有域名 → 直接连这个源，mirror 配置完全不参与
```

所以「手写域名」= **放弃了自动换源能力，把自己锁死在单一源上**。

而那个源不一定同步了所有 tag——`manifest unknown` 的准确含义是
**「这个仓库存在，但这个 tag 不存在」**，不是网络问题，也不是认证问题。

### 定位：区分三种「拉不到」

| 报错 | 含义 | 方向 |
|---|---|---|
| `manifest unknown` | 源里没有这个 tag | 换 tag 或换源；先确认名字没写错 |
| `pull access denied` / `unauthorized` | 认证问题 | 私有仓库要 `docker login` |
| `i/o timeout` / `connection reset` | 网络问题 | 换 mirror / 代理 |

### 修法

**镜像名一律写官方原名，不加任何域名前缀**：

```yaml
image: nginx:1.27-alpine
image: mysql:8.0
```

让 Docker 自己去试 mirror 列表。

> 只有**私有仓库**才必须写域名（`registry.cn-hangzhou.aliyuncs.com/ns/img:tag`），
> 因为 mirror 只服务 Docker Hub。

### 一句话记住

> **配了 mirror 就写官方原名。加域名前缀 = 主动放弃加速源。**

### 面试怎么讲

**面试官会问**：配了镜像加速，为什么 `docker pull` 还是超时？

**答法**：`registry-mirrors` **只在「镜像名不带 registry 域名」时才生效**。
写 `nginx:1.25` 会走 mirror；写 `docker.io/nginx:1.25` 或 `xxx.mirror.com/nginx:1.25`
就是「显式指定 registry」，直接连那个地址，mirror 完全不参与。

**排查顺序**：`docker info` 看 mirror 是否生效 → `curl -I <镜像站>/v2/` 看通不通
→ 再试 `docker pull` 官方原名。

**关键一句**：**mirror 是「默认路径的加速」，不是「所有路径的代理」。**

# 第四部分：顺序敏感的操作

## 10. 主从搭完 `Replica_SQL_Running: No`

这是全项目最复杂的一个坑，值得慢慢拆。

### 现象

```
Replica_IO_Running: Yes
Replica_SQL_Running: No
Last_SQL_Error: Coordinator stopped because there were error(s) in the worker(s).
                The most recent failure being: Worker 1 failed executing transaction
                'f6ce116b-cbcb-11f1-9aad-0242ac17000b:7' at source log mysql-bin.000002,
                end_log_pos 2998407.
Auto_Position: 1
```

### 先把这条报错读懂

| 字段 | 含义 |
|---|---|
| `IO_Running: Yes` | 拉取线程正常：网络通、账号对、能读到主库 binlog |
| `SQL_Running: No` | 回放线程停了 → **数据到了但没执行** |
| `Coordinator stopped...` | SQL 线程（协调者）因为 worker 报错而停机 |
| `Worker 1 failed executing transaction 'uuid:7'` | 主库第 7 个事务执行失败 |
| `at source log mysql-bin.000002, end_log_pos 2998407` | 这个事务在主库 binlog 的结束位置 |
| `Auto_Position: 1` | 用 GTID 自动定位（不是文件位点） |

**IO=Yes 这一条排除了网络、账号、权限、端口所有问题**——因为 binlog 已经拉下来了。
问题一定在「怎么执行」上。

### 原理：GTID 复制到底怎么决定「从哪开始」

先看正常流程：

```
主库：每个事务提交时，分配一个全局唯一编号  uuid:序号
      例如 f6ce...:7 = 这台主库的第 7 个事务

从库：维护一个集合 gtid_executed = "我已经执行过哪些事务"
      连上主库时说：我有 1-6，请从 7 开始给我
```

**从库靠 `gtid_executed` 判断自己缺什么。这个集合是它唯一的「进度条」。**

再看搭主从时我们做的事：

```
1. mysqldump 导出主库数据
2. 导入从库            ← 从库有了数据
3. 设置 AUTO_POSITION=1 并启动复制
```

问题出在第 1 步的参数上：

```bash
mysqldump --all-databases --set-gtid-purged=OFF ...
```

**`--set-gtid-purged=OFF` 的含义是：不要在 dump 文件头部写 `GTID_PURGED`。**

正常 dump 头部会有一行：

```sql
SET @@GLOBAL.GTID_PURGED='f6ce116b-...:1-19';
```

这行的作用是告诉从库：**「你刚导入的这批数据，已经包含了主库的 1~19 号事务」**。

关掉它，从库的 `gtid_executed` 就是空的。于是：

```
从库对主库说：我一个事务都没有
主库：那我从第 1 个开始推给你
从库回放第 1 个事务：CREATE DATABASE shop
                     ↑ 但 shop 库刚刚从 dump 里导入过了
报错：Can't create database 'shop'; database exists
→ Worker 停 → Coordinator 停 → SQL_Running = No
```

**这就是「数据已经有了，但进度条是空的」导致的重复执行。**

### 第二个错误：`--all-databases`

这个参数把 `mysql` 系统库也一起导了，包括 `user`、`db`、`tables_priv` 等权限表。
后果：

- 从库的 `root` 密码、账号权限被**主库的快照覆盖**
- 两边的 `server_id`、`uuid` 相关元数据可能混乱
- 严重时从库连 root 都登不上

**正确做法：只导业务库**（`--databases shop`）。

### 定位：为什么能确定是「重复执行」而不是「权限/网络」

三条线索串起来：

1. **IO=Yes** → 网络和账号都没问题
2. **失败的 GTID 是 `:7`**，一个很小的序号 → 说明它**从第 1 个开始重放**，
   而不是"接着之前的位置继续"
3. **dump 头部没有 `GTID_PURGED`**（`grep GTID_PURGED /tmp/dump.sql` 无输出）→
   从库不知道自己已经有数据

如果当时 dump 里有 `GTID_PURGED='...:1-19'`，复制就会从 20 开始，根本不会碰 1~19。

### 修法：清干净重来（不能"就地修"）

为什么不能就地修？因为从库现在是**半吊子状态**：

```
数据：  dump 导入的全量 + 重放到第 7 个事务的一部分
进度：  gtid_executed 里可能记了 1~6
```

**数据和进度已经对不上了**，继续跑只会越来越乱。所以要清空重建：

```bash
# ① 从库：停复制 → 清复制配置 → 删库 → 清空 GTID 记录
STOP REPLICA;
RESET REPLICA ALL;
DROP DATABASE IF EXISTS shop;
RESET MASTER;            # 清空 gtid_executed 和本地 binlog

# ② 主库：只导业务库，保留 GTID_PURGED（默认行为）
mysqldump --single-transaction --quick --routines --triggers --events \
  --databases shop > /tmp/shop.sql

# ③ 确认 dump 头部有那行「通行证」
grep -m1 GTID_PURGED /tmp/shop.sql

# ④ 导入
mysql -uroot < /tmp/shop.sql

# ⑤ 配链路并启动
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='node1-db', SOURCE_PORT=3306,
  SOURCE_USER='repl', SOURCE_PASSWORD='Repl@123456',
  SOURCE_AUTO_POSITION=1;
START REPLICA;
```

### ★ 顺序陷阱：为什么 `DROP` 必须在 `RESET MASTER` 之前

这是本题最精妙的一点：

```
DROP DATABASE 本身也是一个事务 → 会消耗一个 GTID
                                → gtid_executed 变成 {从库uuid:1}
```

而导入 dump 时执行的 `SET GTID_PURGED='主库uuid:1-19'`（8.0 带 `+` 修饰符）
要求：**新的集合必须是现有集合的超集**。

`{从库uuid:1}` 显然不是 `{主库uuid:1-19}` 的子集 → 报错：

```
ERROR 3546 (HY000): @@GLOBAL.GTID_PURGED cannot be changed:
the added gtid set must not overlap with @@GLOBAL.GTID_EXECUTED
```

所以正确顺序是：**先 DROP（产生 GTID），再 RESET（清空所有 GTID）**，这样导入时才是空的。

> 另一种等效写法：DROP 的时候临时关掉 binlog 记录
> `SET sql_log_bin=0; DROP DATABASE shop; SET sql_log_bin=1;`
> 这样不产生 GTID，顺序就无所谓了。

### 为什么不「跳过这个错误」

MySQL 允许跳过：

```sql
SET GLOBAL sql_replica_skip_counter = 1;   -- 传统位点模式
-- 或 GTID 模式：注入一个空事务
```

但**跳过一笔建库/建表事务，等于让从库永久缺失这个对象**。
后面的 `INSERT`、`ALTER` 全都建立在这个对象上，会连锁报错。
**跳过错误是掩盖问题，不是解决问题**——生产上也只在「明确知道这笔操作可以丢」时才用。

### 一句话记住

> **dump 是「数据」，GTID_PURGED 是「进度条」。只给数据不给进度条，从库就会从头重放。**

### 面试怎么讲

> 「第一次搭主从，IO 线程 Yes、SQL 线程 No，报 Worker 在 GTID `:7` 失败。
> 我先看 IO=Yes，排除了网络和账号；再看失败位置是第 7 个事务——一个很小的号，
> 说明它从第 1 个开始重放，不是接着之前的位点。顺着查 dump 头部，
> 发现没有 `GTID_PURGED`，因为脚本里写了 `--set-gtid-purged=OFF`。
> 根因是：全量数据已经导进去了，但从库的 GTID 集合是空的，AUTO_POSITION 认为它什么都没有，
> 于是从头重放，第一个 `CREATE DATABASE` 就撞车。
> 修法是只导业务库、保留 GTID_PURGED，导入前先 DROP 再 RESET MASTER——
> 顺序不能反，因为 DROP 自己会产生一个 GTID。」

## 11. MySQL 报 `Errcode 13`，起不来

### 现象

```bash
$ docker logs node1-db
[ERROR] InnoDB: Operating system error number 13 in a file operation.
[ERROR] Could not create/write to file '/var/log/mysql/error.log' (Errcode: 13)
```

`13` 是 Linux 的 `EACCES`（Permission denied）。

### 原理：容器里的 uid ≠ 宿主机文件的属主

MySQL 官方镜像里，`mysqld` **不是以 root 运行的**，而是降权到 `mysql` 用户：

```bash
$ docker exec node1-db id mysql
uid=999(mysql) gid=999(mysql)
```

而 `docker-compose.yml` 里我们是这么挂的：

```yaml
volumes:
  - ./logs/mysql-node1:/var/log/mysql      # bind mount
```

`bind mount` 的语义是：**把宿主机目录原样映射进去，Docker 不会改它的属主**。

而我们是这么创建目录的：

```bash
mkdir -p logs/{mysql-node1,mysql-node2}
# 属主是 root:root，权限 755
```

所以容器里的 `mysql`（uid 999）想在这个目录里创建 `error.log` → **没有写权限** → 启动失败。

### 为什么 `db-node1` 数据卷没这个问题

数据用的是 **named volume**：

```yaml
volumes:
  - db-node1:/var/lib/mysql     # named volume
```

named volume 第一次创建时，**Docker 会把镜像里该目录的内容和属主一起复制过来**，
所以 `mysql` 用户天然有权限。这就是「数据库用 volume、日志用 bind mount」时要注意的差别。

### 定位：怎么看是权限问题

```bash
# 1) 宿主机看目录属主
$ ls -ld logs/mysql-node1
drwxr-xr-x 2 root root 4096 ...        ← root:root，问题就在这

# 2) 容器里看进程身份
$ docker exec node1-db id mysql
uid=999(mysql) gid=999(mysql)

# 3) 逐层看路径权限（这个命令很多人不知道）
$ namei -l logs/mysql-node1
```

### 修法

```bash
chown -R 999:999 logs/mysql-node1 logs/mysql-node2
```

**必须在 `docker compose up` 之前做**——否则容器一起来就失败，你还得先解决权限再重启。

### 引申：SELinux

如果系统开了 SELinux，光 `chown` 还不够，还要处理安全上下文：

```bash
getenforce                     # Enforcing 就是开着
ls -Z logs/mysql-node1         # 看 context
chcon -Rt svirt_sandbox_file_t logs/mysql-node1
# 或在 compose 里挂载时加 :z
```

**两个坑经常一起出现**：先 `Errcode 13`（权限），改完变 `Errcode 13` 依旧（SELinux）。
排查时 `ausearch -m AVC -ts recent` 能看到被拒绝的记录。

### 一句话记住

> **bind mount 不改属主，named volume 会继承镜像属主。uid 999 是容器化 MySQL 的固定考点。**

### 面试怎么讲

**面试官会问**：MySQL 容器起不来，日志只有 `Errcode 13`，怎么查？

**答法**：`Errcode 13` 是 `EACCES`，权限拒绝。关键是**容器里跑的 uid 和宿主机目录属主不一致**。
MySQL 官方镜像里 `mysql` 用户是 **uid 999**，而 bind mount 过来的宿主机目录属主是 `root`（uid 0），
两个 uid 对不上，容器内进程就没法写。

**修**：`chown -R 999:999 ./logs/mysql-node1`。若开了 SELinux，还要 `chcon -Rt svirt_sandbox_file_t` 或挂载加 `:z`。

**关键一句**：**容器不「继承」宿主机权限，它只按自己的 uid 去访问文件；bind mount 不会帮你改属主。**

**追问：为什么数据卷那个实例没这个问题？**
因为用的是 named volume——首次创建时 Docker 会把镜像里目录的属主（999:999）复制过来。
bind mount 指向的是宿主机既有目录，不复制属主，所以出事的是它。

# 第五部分：环境与「最后一公里」

## 12. `docker compose` 报 `no configuration file provided`

### 现象

```
[root@VM ops]# docker compose ps
no configuration file provided: not found
```

### 原理：compose 只认「当前目录」

`docker compose` 启动时会**在当前目录**找这几个文件（按顺序）：

```
compose.yaml
compose.yml
docker-compose.yaml
docker-compose.yml
```

**它不会向上递归查找父目录**。所以：

```
/opt/ops/                      ← 你站在这，这里没有 compose 文件
├── project1-cluster/
│   └── docker-compose.yml     ← 文件在这
└── project2-lnmp/
    └── docker-compose.yml
```

在 `/opt/ops` 执行必然失败。

### 定位

```bash
pwd                                  # 我在哪
ls docker-compose.yml                # 有没有
find /opt/ops -name "docker-compose.yml"   # 到底在哪
```

一条命令就能确认，**不要凭感觉猜目录**。

### 修法

```bash
cd /opt/ops/project1-cluster && docker compose ps
```

或者不切目录：

```bash
docker compose -f /opt/ops/project1-cluster/docker-compose.yml ps
docker compose --project-directory /opt/ops/project1-cluster ps
```

### 引申：项目名从哪来

compose 会给资源加前缀，避免不同项目冲突：

| 资源 | 命名规则 | 例子 |
|---|---|---|
| 容器 | `container_name` 优先，否则 `<项目>-<服务>-<序号>` | `node1-db` |
| 网络 | `<项目>_<网络名>` | `cluster-p1_front` |
| 卷 | `<项目>_<卷名>`，或用 `name:` 覆盖 | `cluster_p1_db_node1` |

项目名默认取**目录名**，也可以用 `name:` 显式指定。本项目写的是 `name: cluster-p1`。

**这个规则很重要**：第 3 条那个 `cluster-p1_front` 就是从这来的。

### 一句话记住

> **compose 只认当前目录；项目名决定网络/卷的前缀。**

### 面试怎么讲

**面试官会问**：`docker compose up -d` 报 `no configuration file provided`，你怎么看？

**答法**：这条报错只有一个含义——**当前目录找不到 `docker-compose.yml` / `compose.yaml`**。
`docker compose` 不像 `git` 会向上找父目录，它只认当前目录（或 `-f` 指定的路径）。
先 `pwd` 确认自己在哪。

**关键一句**：**先 `pwd`，再动手。** 我在这上面犯过两次同样的错，就是因为没先看位置。

**加分点**：能说清项目名规则——默认取目录名，决定网络全名 `<项目名>_<网络名>` 和卷名。
所以「在哪个目录执行」不只影响能否找到文件，还影响它连的是哪个网络。
放错目录即使文件找到了，起的也是一套新环境（不同的网络前缀、不同的卷）。

## 13. cron 手动能跑，定时不跑

### 现象

```bash
$ bash /opt/ops/project1-cluster/scripts/backup.sh    # 手动执行，成功
$ crontab -l
0 2 * * * /opt/ops/project1-cluster/scripts/backup.sh >> /opt/ops/logs/cron.log 2>&1
# 第二天：备份目录是空的
```

### 原理：cron 的执行环境几乎是「裸的」

cron 启动任务时**不加载你的 `.bashrc` / `.bash_profile`**，用的是极简环境：

```
PATH=/usr/bin:/bin          ← 没有 /usr/local/bin
HOME=/root
SHELL=/bin/sh               ← 不是 bash
```

后果：

| 你手动执行时 | cron 执行时 |
|---|---|
| `docker` 在 `/usr/local/bin`，能找到 | PATH 里没有 → `docker: command not found` |
| 别名、函数都能用 | 全部失效 |
| 当前目录是你的项目目录 | 是 root 的家目录 |

### 三个高频原因（按出现率排）

**① PATH 太短**

```cron
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```
放在 crontab **第一行**。

**② 脚本没执行权限 / CRLF 换行**

Windows 编辑过的脚本带 `\r\n`，shebang 变成 `#!/bin/bash\r`，报：

```
/bin/bash^M: bad interpreter: No such file or directory
```

修法：

```bash
sed -i 's/\r$//' script.sh
chmod +x script.sh
```

**③ 没重定向输出，报错看不见**

```cron
# 错：报错去哪了？可能进了系统邮件，等于黑洞
0 2 * * * /path/backup.sh

# 对：stdout 和 stderr 都进日志
0 2 * * * /path/backup.sh >> /var/log/backup.log 2>&1
```

**补充**：crontab 里的 `%` 是特殊字符（表示换行），命令里要用 `\%` 转义。

### 定位：三步确认

```bash
# 1) cron 服务在跑吗
systemctl status crond

# 2) cron 有没有触发过这条任务
grep backup /var/log/cron

# 3) 脚本自己的日志有没有输出
tail -20 /opt/ops/logs/scripts/backup-cron.log
```

如果 `/var/log/cron` 有触发记录但脚本日志是空的 → 就是 PATH 或权限问题。

### 验证技巧：临时改成每分钟

```bash
crontab -l | sed 's|0 2 |* * |' | crontab -
sleep 70
tail -5 /opt/ops/logs/scripts/backup-cron.log
# 验证完改回去
```

**不要等第二天早上再看**——反馈周期太长，问题会堆积。

### 一句话记住

> **cron 不读你的 profile，PATH 必须自己写；脚本必须自己记日志。**

### 面试怎么讲

**面试官会问**：脚本手动跑没问题，加到 crontab 就不执行，怎么排查？

**答法**：按三个高频原因排，**顺序很重要**（按出现率）：
1. **PATH 不同**——cron 的环境几乎是裸的，`docker`、`python3` 可能找不到。
   解法：脚本头 `export PATH=/usr/local/bin:/usr/bin:/bin`，或用绝对路径。
2. **工作目录不同**——cron 在 `$HOME` 下执行，脚本里的相对路径全炸。
   解法：脚本里 `cd "$(dirname "$0")/.."` 或全用绝对路径。
3. **换行符**——在 Windows 上编辑过，`\r\n` 会让 shebang 变成 `/bin/bash\r`，报「找不到文件」。
   解法：`dos2unix` 或 `sed -i 's/\r$//'`。

**关键一句**：**cron 的问题几乎都不是「没执行」，而是「执行了但失败了，而你没看到输出」。**
所以第一件事是在命令末尾加 `>> /path/cron.log 2>&1`，先让它开口说话。

**加分点**：说清 `2>&1` 为什么两个都要——`>` 只接 stdout，报错走 stderr 会直接丢。
cron 默认把输出发本地邮件，服务器没配邮件就等于黑洞。

## 14. 外网访问不通，但服务器上 curl 正常

### 现象

```bash
# 服务器上
$ curl -I http://127.0.0.1/           → 200 OK
$ curl -I http://172.20.0.10/         → 200 OK

# 你电脑上
$ curl -I http://公网IP/              → 连接超时
```

### 原理：一条请求要穿过三道门

```
你的电脑
   │
   ├─① 云平台安全组（腾讯云控制台，在宿主机「外面」）
   │
   ├─② 宿主机防火墙 firewalld / iptables
   │
   └─③ 应用是否监听在 0.0.0.0（而不是 127.0.0.1）
```

任何一道没开，都会表现为「连接超时」或「拒绝连接」。

**最容易被忘的是第 ① 道**——因为它不在服务器上，`firewall-cmd` 怎么配都看不到它。

### 定位：四层递进测

```bash
# 1) 应用层：本机能不能通
curl -I http://127.0.0.1/

# 2) 监听地址：是不是只听 127.0.0.1
ss -tlnp | grep :80
# 0.0.0.0:80  → 所有网卡都听
# 127.0.0.1:80 → 只有本机，外网必然不通

# 3) 宿主机防火墙
firewall-cmd --list-ports
firewall-cmd --list-all

# 4) 云控制台安全组
# 网页控制台 → 防火墙 / 安全组 → 入站规则
```

### 修法：按定位结果对症下药

**这四条不是「都做一遍」，而是「测到哪层不通就修哪层」**。所以先测，再改，别乱开端口。

| 卡在第几层 | 修什么 | 命令 |
|-----------|--------|------|
| ① 本机 curl 就不通 | 应用/容器的问题，跟防火墙无关 | `docker compose ps`、`docker logs` |
| ② 只听 127.0.0.1 | 改监听地址 | nginx `listen 80;`（不是 `listen 127.0.0.1:80`）<br>或 compose 端口前缀写错成 `127.0.0.1:80:80` |
| ③ firewalld 没放行 | 放行端口 | `firewall-cmd --add-port=80/tcp --permanent && firewall-cmd --reload` |
| ④ 安全组没开 | 控制台加入站规则 | 网页控制台 → 防火墙 → 添加规则（TCP 80，来源 0.0.0.0/0） |

**每一步为什么要这么做**：

- **第 ② 步优先查监听地址**，因为这是「自己犯的错」里最常见的：
  compose 里写成 `"127.0.0.1:80:80"` 是为了「只让本机访问」的写法，
  但很多人是从教程里抄来的，抄完发现外网不通，回头怎么查防火墙都正常。
- **`--permanent` 和 `--reload` 必须成对**：不加 `--permanent` 重启就丢；加了不 `reload` 当前不生效。
  这是 firewalld 独有的坑，`ufw` 和 `iptables` 都没有。
- **安全组是「宿主机外面」的一层**，改完即时生效、不需要重启任何服务，
  但也意味着**你在服务器上永远看不到它的规则**——所以它最容易被忘。

**验证闭环**：改完必须回到你自己的电脑上再 `curl` 一次。
在服务器上 `curl 127.0.0.1` 永远通，用它验证等于没验证。

### 引申：Docker 会绕过 firewalld

这点反直觉但很重要：

- `firewalld` 的规则主要作用在 **INPUT 链**（发给本机的包）
- Docker 发布端口（`-p 80:80`）会在 **nat 表写 DNAT 规则**，把包转发给容器，
  走的是 **FORWARD 链**
- 所以**即使 firewalld 没放行 80，容器端口照样能被访问**

结论：

- 想用 firewalld 限制容器端口 → 常常不生效，得用 `DOCKER-USER` 链
- **云安全组才是最终的那道门**，容器端口暴露出去前先在安全组收口

### 一句话记住

> **云主机是两层防火墙：控制台安全组 + 系统 firewalld，两层都要开。**
> **容器端口不受 firewalld 约束，安全组才是底线。**

### 面试怎么讲

**面试官会问**：服务在服务器上 `curl` 正常，外网访问不了，怎么查？

**答法**：按「由内到外」四层递进，**每一层排除一个可能**：
1. 本机 `curl 127.0.0.1:80` —— 服务本身是否活着
2. `ss -lntp | grep :80` —— 监听的是 `0.0.0.0` 还是 `127.0.0.1`
3. `firewall-cmd --list-ports`（或 `iptables -L -n`）—— 系统防火墙
4. 云控制台安全组入站规则 —— 云厂商那道门

四层都通，问题就在链路中间（运营商、DNS、CDN）。

**关键一句**：**先分清「服务没起」「只听本机」「被防火墙拦」「安全组没开」——这四种现象一样，原因完全不同。**

**加分点（这条很能区分水平）**：Docker 发布端口是靠 iptables 的 `FORWARD` 链 + `DOCKER` 链做 DNAT，
**不经过 `INPUT` 链**，所以 firewalld 放不放行对容器端口往往无效。
这也是「以为关了 80，实际还能访问」的原因。要限制得用 `DOCKER-USER` 链。

## 15. 出故障了，却查不到具体原因

### 现象

主从报错只给了 `Worker 1 failed executing transaction ...`，
但**到底是哪条 SQL 失败、错误码是什么**，看不到。

按常规去查：

```sql
SELECT * FROM performance_schema.replication_applier_status_by_worker;
ERROR 1146 (42S02): Table 'performance_schema.replication_applier_status_by_worker' doesn't exist
```

### 原理：为了省内存，把诊断入口关了

`master.cnf` / `slave.cnf` 里有这么一行：

```ini
performance_schema = OFF
```

`performance_schema` 是 MySQL 的**运行时性能采集库**，默认开启时约占 **100MB 内存**。
2G 的机器跑两个实例，这 200MB 太贵，所以我们关了它。

代价：

| 关闭后失去 | 影响 |
|---|---|
| `replication_applier_status_by_worker` | 看不到是哪个 worker、哪条 SQL 失败、错误码 |
| 各种等待事件、锁等待统计 | 性能分析能力下降 |
| `sys` schema 的视图 | 常用诊断视图不可用 |

**但有两样东西没受影响**：

- `SHOW PROCESSLIST` / `information_schema.processlist`（在 information_schema 里）
- **错误日志** `log_error` 指向的文件

### 定位：从错误日志里挖

配置里写了：

```ini
log_error = /var/log/mysql/error.log
```

而这个目录被挂到了宿主机：

```yaml
volumes:
  - ./logs/mysql-node2:/var/log/mysql
```

所以直接读宿主机文件：

```bash
tail -50 logs/mysql-node2/error.log
grep -iE "error|worker" logs/mysql-node2/error.log | tail -20
```

里面会有完整的一行：

```
[ERROR] [MY-010584] [Replica] Slave SQL for channel '': Worker 1 failed executing
transaction 'f6ce...:7', Error_code: 1007; handler error HA_ERR_FOUND_DUPP_KEY;
Error 'Can't create database shop; database exists' on query...
```

**注意 `docker logs` 为什么看不到**：容器 stdout 只捕获 entrypoint 的输出，
MySQL 自己的日志被 `log_error` 重定向到文件了。**这是两个不同的通道。**

### 修法：在不加内存的前提下留后路

1. **保证 error.log 可读**（已挂到宿主机）——这是最低成本的诊断保障
2. **开慢查询日志**（`slow_query_log=1`, `long_query_time=1`）——性能问题靠它
3. 如果内存允许，可以只开需要的 consumer，而不是整个关掉：

```ini
performance_schema = ON
performance_schema_instrument = 'replication%=ON'   # 只采复制相关
```

4. 长期方案：加内存，或者把 MySQL 拆到独立机器

### 一句话记住

> **省资源的每一个决定，都要问自己「出事时我还查得动吗」。**

### 面试怎么讲

**面试官会问**：你怎么在 2G 内存的机器上跑 MySQL，做了哪些取舍？

**答法**：先给结论——我做了「关诊断、保可读」的取舍，不是无脑调参数。
具体：`performance_schema=OFF` 省了约 200–400MB，`innodb_buffer_pool_size` 压到 128M，
但**错误日志一定挂到宿主机**（`log_error=/var/log/mysql/error.log` + bind mount），
慢查询日志打开。理由是：内存可以省，**出事时能查**不能省。

**关键一句**：**省资源的每一个决定，都要问「出事时我还查得动吗」。**

**追问：为什么 `docker logs` 里没有 MySQL 的报错？**
两个通道。容器 stdout 只捕获 entrypoint 的输出；MySQL 自己把错误写进 `log_error` 指定的文件。
配了文件日志就等于「绕开」了 stdout，所以 `docker logs` 一片空白。
这也是我那次排查卡住的原因——**不是没日志，是我看的地方不对**。

# 第六部分：工具、观测与诊断的脾气

前面 15 个坑都是「环境」或「代码」的问题。这四条不一样——**命令写得语法完全正确，
`bash -n` 也一声不响，但它就是不干活**。因为工具自己有规则，而这些规则不会主动提醒你。

第 16 条是「选项的位置」不讲道理，第 17 条是「工具的版本」不讲道理，
第 18 条最狠——**「观测」本身不讲道理，你量到的可能根本不是你想量的东西**。

第 19 条换了个方向：**工具把话说了一半**。`upstream timed out` 只告诉你「等了太久」，
不告诉你「等在哪一步」——剩下那一半，得靠你自己从 `while xxx` 里读出来。

## 16. `--exclude` 写了等于没写

### 现象

备份脚本每天跑，MySQL 备份成功，代码备份永远失败。终端只有一行：

```
[2026-10-27 16:30:19] [2/4] 备份代码与配置
[2026-10-27 16:30:19]   ✘ 代码备份失败
```

把 tar 的 stderr 放出来之后，它其实一直在喊：

```
tar: The following options were used after any non-optional arguments
     in archive create or update mode.  These options are positional
     and affect only arguments that follow them.  Please, rearrange them properly.
tar: --exclude 'project1-cluster/logs' has no effect
tar: --exclude 'project1-cluster/data' has no effect
tar: --exclude 'project1-cluster/backup' has no effect
tar: Exiting with failure status due to previous errors
```

**`has no effect`** —— 它说的是「我压根没用这几个选项」。

### 原理：`--exclude` 是位置敏感的

GNU tar 的参数分两类：

| 类型 | 例子 | 生效范围 |
|------|------|---------|
| 普通选项 | `-c` `-z` `-f` `-C` | 整个命令 |
| **位置敏感选项** | `--exclude` `--exclude-from` `--files-from` `--no-recursion` | **只对写在它后面的成员名生效** |

原因在语义上就说得通：`--exclude` 的意思是「**接下来**要打包的东西里，符合这个模式的跳过」。
既然是「接下来」，写在成员名后面就无事可做了。

对照原脚本（错误版）：

```bash
tar czf "$CODE_FILE" \
    -C "$(dirname "$PROJECT_DIR")" "$(basename "$PROJECT_DIR")" \   # ← 成员名在这
    --exclude='*/logs/*' --exclude='*/data/*'                        # ← 排除写在它后面，无效
```

`"$(basename "$PROJECT_DIR")"` 就是 `project1-cluster`，它是**非选项参数（成员名）**。
`--exclude` 出现在它之后 → 全部失效 → 整个项目目录（包括 `logs/` 里正被 MySQL 写的 InnoDB 文件）
都被塞进包里 → tar 读到变化的文件 → 报错退出。

⚠️ 有一个容易搞混的点：`-C dir` 里的 `dir` **不是**成员名，它是 `-C` 的实参。
所以下面两种写法都**有效**：

```bash
# ✓ exclude 在成员名 project1-cluster 之前
tar czf out.tar.gz -C /opt/ops --exclude='project1-cluster/logs' project1-cluster

# ✓ 也有效，exclude 可以夹在 -C dir 之后
tar czf out.tar.gz -C /opt/ops --exclude='project1-cluster/logs' --exclude='project1-cluster/data' project1-cluster
```

判别标准只有一条：**`--exclude` 必须出现在所有成员名之前。**

### 定位：退出码 1 和 2 是两回事

这次能一步定死，靠的是两个信号：

```bash
cd /opt/ops
tar cf /dev/null --exclude='project1-cluster/logs' project1-cluster; echo "退出码=$?"
```

| 退出码 | 含义 | 该往哪查 |
|--------|------|---------|
| **1** | 处理过程中有文件变化（`file changed as we read it`） | 有活文件被打包 → 排除规则没覆盖到 |
| **2** | 致命错误（参数非法 / 路径不存在 / 磁盘满） | **先读 tar 的原话**，它通常直接说了原因 |

这次是 **2**，因为「选项位置非法」对 tar 来说是致命错误。如果我一开始就分别对待 1 和 2，
就不会往「通配符跨不跨 `/`」的方向猜。

用 `/dev/null` 当输出还有两个好处：**不占磁盘、不压缩**，2C2G 的小机器上跑起来毫无压力。

### 修法：两个层次

**层次一：把位置调对**（最小改动）

```bash
# 改前
tar czf out -C "$(dirname "$P")" "$(basename "$P")" --exclude='...' 
# 改后：exclude 提前
tar czf out --exclude='...' -C "$(dirname "$P")" "$(basename "$P")"
```

**层次二：换成白名单**（推荐，本项目采用）

黑名单的根本问题是「你永远不知道自己漏了什么」——这台机器上 `logs/` 里挂着 MySQL 的
数据目录，明天可能又挂一个 Redis 的 `dump/`，后天多一个 `tmp/`。
改成只打包该备的东西，新增的目录天然不会进来：

```bash
CODE_ITEMS=""
for i in app www nginx sql scripts docker-compose.yml README.md; do
    [[ -e "${PROJECT_DIR}/${i}" ]] && CODE_ITEMS="${CODE_ITEMS} ${i}"
done
tar czf "$CODE_FILE" -C "$PROJECT_DIR" ${CODE_ITEMS}
```

`[[ -e ]]` 那一句是为了让白名单里的项**可以不存在**——这样以后删掉某个目录脚本也不会报错。

### ★ 复盘：我在这条上连续猜错两次

这个坑最值钱的部分不是结论，是**为什么绕了这么久**。

| 我当时的猜测 | 听起来像回事的理由 | 错在哪 |
|-------------|------------------|--------|
| `*` 不跨 `/`，`*/logs/*` 匹配不到两层路径 | GNU tar 确实默认 `--no-wildcards-match-slash` | **根本没验证**。这个知识点是真的，但和本次故障无关 |
| 磁盘满了 | 1MB 的 mysqldump 成功、几百 MB 的 tar 失败，很像磁盘满 | 也是脑补。`df -h` 一次就能否掉 |

两次都错的**共同原因只有一个**：

```bash
... 2>>"$LOG"      # tar 的报错被重定向进日志文件，终端只剩「失败」两个字
```

**我把故障信息关掉了，然后在没有信息的情况下做推理。**

所以「看不到错误信息」应该被当成**第一故障**来修，而不是当成「反正日志里有」。
正确的顺序永远是：

```
① 让工具把话说完整（去掉 2>>log，或改成 2>&1 捕获后同时打印）
② 读它说了什么
③ 再决定往哪查
```

跳过 ① 直接 ③，就是靠经验赌博。赌对了显得很神，赌错了浪费三轮。

### 一句话记住

> **`--exclude` 必须写在成员名之前，否则它一声不响地什么都不做。**
> **更要紧的是：先让工具说话，再动脑子。**

### 面试怎么讲

**面试官会问**：脚本里某个参数写了但没效果，你会怎么查？

**答法**：先别猜，**先把 stderr 放出来**。我踩过一个典型的：
`tar czf out -C dir member --exclude=xxx`，`--exclude` 写在成员名后面，
tar 的规则是「位置敏感选项只对后面的成员名生效」，所以它直接报 `has no effect` 并退出。
语法检查（`bash -n`）完全发现不了，因为语法没错，是**语义位置**错。

**关键一句**：**参数写了不生效，九成是位置或作用域的问题；而你要做的第一件事，是让程序把它的抱怨说完。**

**追问：怎么避免再犯？**
① 关键命令不要 `2>>log` 就完事，要 `2>&1` 捕获后同时打到终端和日志；
② 用退出码区分故障类型（tar 的 1 和 2 含义不同）；
③ 能写白名单就不写黑名单。

## 17. 仓库里的脚本，拿到服务器上跑不起来

### 现象

在服务器上照着文档敲：

```bash
[root@VM-0-14-opencloudos ops]# bash scripts/failover_drill.sh node1-web 20
bash: scripts/failover_drill.sh: No such file or directory
```

注意这句话的措辞：**是「文件不存在」，不是「目录不存在」**。
这两种报错的差别看起来只是差了两个字，实际指向完全不同的原因——而这个差别正是坑的核心。

### 原理：两层原因叠在一起

**第一层：相对路径依赖「当前目录」，而根目录下正好有个同名目录。**

仓库结构是这样的：

```
/opt/ops/                    ← 你现在站在这里
├── scripts/
│   └── mirror_probe.sh      ← 根目录真有一个 scripts/，里面没有演练脚本
└── project1-cluster/
    └── scripts/
        └── failover_drill.sh   ← 你要的文件在这儿
```

所以：

| 你站的位置 | `scripts/` 是否存在 | bash 的报错 | 为什么 |
|---|---|---|---|
| `/opt/ops` | **存在**（含 mirror_probe.sh） | `No such file or directory` | 目录找到了，文件没找到 |
| `/opt/ops/project1-cluster` | 不存在 | `No such file or directory` | 目录本身就没找到 |

**两种情况报的是同一句话。** 这就是它误导人的地方——你没法从报错文案里判断到底是「站错目录」还是「文件真的没部署」。

如果根目录没有那个 `scripts/`，你会看到 `No such file or directory` 之外还会感觉奇怪：「目录都没有，为什么不说 no such directory？」——因为 **bash 在打开文件时只报目标路径打不开**，它不会告诉你中间哪一层断了。

**第二层：即使路径对了，脚本本身在新机器上也可能跑不出结果。**

这个脚本原来靠 curl 的 `%{header_json}` 提取响应头：

```bash
node=$(curl -s -o /dev/null -w '%{header_json}' http://127.0.0.1/whoami \
       | grep -o '"x-served-by":\["[^"]*"' | sed 's/.*:"//')
```

`-w '%{header_json}'` 是 **curl 7.83（2022-04）才加的变量**。而 OpenCloudOS / CentOS 自带的是：

| 系统 | 自带 curl |
|---|---|
| OpenCloudOS 9 / RHEL 9 | 7.76 |
| OpenCloudOS 8 / RHEL 8 | 7.61 |
| Ubuntu 22.04 | 7.81 |

**全都低于 7.83。** 低了会怎样？不会报错，`%{header_json}` 被当成一个未知变量，**输出空字符串**。于是：

```
演练前：? ? ? ? ? ? ? ? ? ? ? ? ? ? ? ? ? ? ? ?
```

满屏问号，但退出码 0、没有任何错误提示。脚本「跑完了」，只是什么都没测出来。

### 定位：两步就够

**第 ① 步：确认文件到底在哪**

```bash
cd /opt/ops
find . -name failover_drill.sh          # 精确找人
ls -l scripts/                          # 看看根目录那个 scripts/ 里有什么
```

如果 `find` 有输出、`ls scripts/` 里没有它，就是**站错目录**，不用再查了。

如果 `find` 一点输出都没有，那才是**文件没部署上去**——你服务器上的是旧版本包。

**第 ② 步：确认 curl 版本**

```bash
curl --version | head -1
```

低于 `7.83.0` 就意味着 `%{header_json}` 不能用。**判断依据是版本号，不是「有没有报错」**——这正是第二层坑最难发现的原因：它根本不报错。

### 修法：让脚本自己解决「站在哪」和「能不能跑」

改了三处，每一处对应一个具体的失败模式：

**① 自定位：脚本自己 `cd` 到项目目录**

```bash
cd "$(dirname "$(readlink -f "$0")")/.." || { echo "✘ 无法定位项目目录"; exit 1; }
```

`$0` 是脚本被调用时的路径，`readlink -f` 把它解析成绝对路径（能穿透软链接），
`dirname ... /..` 得到**脚本所在目录的上级**，也就是 `project1-cluster/`。

**为什么要这么做**：脚本里所有命令（`docker`、`curl`）都假设当前目录是项目目录。与其要求使用者「先 cd 对地方」，不如让脚本自己保证——**这是防御性编程的基本姿势：能自己确定的事，不要交给调用者**。

注意它只解决了「站错目录」，**没解决「调用路径写错」**。`bash scripts/xxx.sh` 这个路径本身还是相对的，脚本根本还没开始执行，bash 就已经打不开文件了——**自定位救不了这一层，只能靠你把路径写对**。

**② 便携取头：用 `-D` 落盘再解析，不依赖 curl 版本**

```bash
probe() {
    local code node
    code=$(curl -s -m 3 -D "$HDR" -o /dev/null -w '%{http_code}' "$URL" 2>/dev/null)
    [[ -z "$code" ]] && code=000
    node=$(tr -d '\r' < "$HDR" 2>/dev/null \
           | awk -F': *' 'tolower($1)=="x-served-by"{print $2; exit}')
    printf '%s %s' "$code" "${node:-?}"
}
```

三个细节都有原因：

- `-D "$HDR"`：把响应头写进临时文件。`-D` 从 curl 7.0 就有，**任何系统都能用**。
- `tr -d '\r'`：删掉 CRLF 里的 `\r`。HTTP 头用 CRLF 换行，不删的话节点名末尾会带一个不可见字符，` == "node1-web"` 这种比较永远为假。
- `awk -F': *'` + `tolower($1)`：HTTP 头**字段名大小写不敏感**，nginx 发的是 `X-Served-By`，curl 的 `header_json` 会转小写，自己解析就必须显式统一。
- `${node:-?}`：取不到就显示 `?`，**让「没测到」显式可见**，而不是留一片空白让人以为正常。

**③ 前置检查 + 退出兜底**

```bash
# 三个条件不满足，演练结果没有意义
docker inspect -f '{{.State.Running}}' lb | grep -q true    || err "lb 没跑"
docker inspect -f '{{.State.Running}}' "$TARGET" | grep -q true || err "目标容器没跑"
[[ "$FIRST_NODE" == "?" ]] && err "拿不到 X-Served-By 响应头"
```

```bash
trap cleanup EXIT INT TERM       # 被 Ctrl-C 也要把停掉的节点拉回来
```

**为什么必须加 `trap`**：这个脚本会 `docker stop node1-web`。如果演练跑到一半你按了 Ctrl-C，
或者中间某条命令失败退出，**node1 就停在那儿了**——集群只剩一个节点扛着，而你可能完全不知道。
演练脚本最危险的时刻不是「测出问题」，是「测到一半自己挂了」。

### 换别的做法会怎样

| 方案 | 结果 |
|---|---|
| 每次手动 `cd` 到项目目录再跑 | 能用，但换个脚本就忘一次；根本原因（脚本依赖 cwd）没解决 |
| 在根目录 `scripts/` 里放个软链接指过去 | 能跑通，但多一处需要维护的间接层，换机器就断 |
| 用 `curl -I` 只看头不看状态码 | 头能拿到，但**丢掉 HTTP 状态码**，502 和 200 分不出来——演练就失去意义 |
| 用 `-w '%{header_json}'` 但要求升级 curl | 为了一个字段升级系统 curl，可能连带影响其他依赖 libcurl 的程序，不划算 |
| 用 `docker logs lb` 解析 upstream 日志 | 依赖 nginx 日志格式，配置一改就失效，且有时序偏差 |

### 一句话记住

> **`No such file` 要分两层看：是文件没找到，还是目录没找到？先 `find` 再下结论。**
> **「没报错」不等于「跑对了」——`curl` 版本不够时，那个变量会静默变成空字符串。**

### 面试怎么讲

**面试官会问**：你写的脚本拿到别人的机器上跑不起来，怎么排查？

**答法**：我会先分两类——**还没开始执行就失败的**，和**执行了但结果不对的**。

第一类是路径和权限：`No such file or directory` 这句话有歧义，它可能是文件不存在，
也可能是中间某一层目录不存在，bash 不会告诉你是哪一层。所以我第一步永远是 `find . -name xxx`
确认文件真实位置，而不是猜。

第二类更隐蔽。我踩过一个：脚本用 `curl -w '%{header_json}'` 提取响应头，
这个变量要 curl 7.83+。CentOS/OpenCloudOS 自带 7.61~7.76，**它不报错，直接把那个字段输出成空字符串**，
脚本照常跑完、退出码 0，只是所有结果都是空的。

**关键一句**：**跨机器的脚本，凡是依赖「某个工具的某个版本特性」，都要有降级路径或者显式的版本检查。静默降级比报错危险得多。**

**追问：那你怎么防？**
① 用最古老也最稳的方式（`-D` 落盘再 `awk` 解析），不赌版本；
② 关键取值加「空值即失败」判断，`${node:-?}` 让没取到的情况显式暴露；
③ 会改系统状态的脚本必须加 `trap`，被中断时把状态恢复回去。

## 18. 演练 20 次挂了 9 次，其实一次都没挂

### 现象

停掉 node1-web，跑 20 次请求，结果长这样：

```
200:? 000:? 200:? 000:? 200:? 000:? 200:? 000:? 200:? 200:? 000:? 200:? ...
✘ 结果：9/20 次请求失败
```

**交替出现的 `000`**，看起来像「LB 一半请求打到死节点上直接失败」，很自然的结论是：

> 被动健康检查没生效，nginx 没有把 node1 摘掉。

**这个结论是错的。** 后来的实验结果：

```
第1次 code=200 耗时=0.000818s
第2次 code=200 耗时=3.005635s   ← 撞上死节点，卡满 3 秒，但仍然是 200
第3次 code=200 耗时=0.000653s
第4次 code=200 耗时=3.005429s   ← 第二次慢，之后就再也不慢了
第5次 code=200 耗时=0.000653s
第6次 code=200 耗时=0.000616s
```

**六次全是 200，一次都没失败。** 摘除不仅生效了，而且很干净：第 2、4 次各慢 3 秒，
**从第 5 次起永久恢复到 0.6 毫秒**。那 9 个 `000` 从头到尾都是**测量方式造出来的假象**。

### 原理：三个机制串在一起，环环相扣

**第一环：容器被 stop 之后，那个 IP 不是「拒绝连接」，而是「吞掉连接」。**

直觉上以为，服务挂了就会回 RST（connection refused），nginx 立刻知道。实际不是：

| 场景 | 网络层发生什么 | 连接结果 | 快慢 |
|------|--------------|---------|------|
| 进程还在，端口没监听 | 内核回 **RST** | `ECONNREFUSED` | **1 毫秒** |
| 容器被 stop，veth 被删 | 网桥上查不到这个 IP，**SYN 包被静默丢弃** | 没有回应，一直等 | **慢** |

`docker stop` 是把容器连同它的 veth 网卡一起销毁。网桥上 172.20.0.11 这个地址消失了，
发往它的 SYN 包既没人接收、也没人拒绝——**它就凭空消失了**。

内核 TCP 的做法是：**重传 SYN，继续等**。等到 nginx 的 `proxy_connect_timeout` 到点，
nginx 才自己放弃，返回 `upstream timed out (110: Connection timed out)`。

所以那个 3 秒**不是「发现失败」花的时间，是「傻等到超时」花的时间**。
这就是为什么耗时精确到 3.005 秒——不是 3.0 附近的随机值，而是**掐着超时线**。

**第二环：客户端超时和服务端超时撞在一起，谁先到谁说话。**

`lb.conf` 里 `proxy_connect_timeout 3s`，旧演练脚本里 `curl -m 3`。两个都是 3 秒，于是：

```
0s ──── curl 发出请求 ──── nginx 转发给 node1 ──── SYN 石沉大海
                                      │
3s ──── curl 到点，主动断开 ──────────┤ nginx 也到点，正准备重试 node2
                                      │
        ↑ 但 nginx 发现客户端没了，记一条 499，放弃这次请求
```

**客户端比服务端早醒了那么一点点，就足以让整次重试作废。** 访问日志里留下了铁证：

```
[27/Oct/2026:13:12:30 +0000] "GET /whoami HTTP/1.1" 499 0 "-" "curl/7.61.1"
[27/Oct/2026:13:12:33 +0000] "GET /whoami HTTP/1.1" 499 0 "-" "curl/7.61.1"
[27/Oct/2026:13:12:37 +0000] "GET /whoami HTTP/1.1" 499 0 "-" "curl/7.61.1"
```

`499` 是 nginx 自定义的状态码，**意思只有一个：客户端在 nginx 给出响应之前就关闭了连接**。
它不是后端返回的错误码，是「nginx 在抱怨你不等它」。

**第三环：被 499 掐掉的请求，不算「上游失败」，所以摘除永远不触发。**

这是最关键的一环。nginx 的 `max_fails` 统计的是**上游明确失败**（连接超时、连接被拒、5xx）。
客户端先断的情况下，整个请求被标记为 `NGX_HTTP_CLIENT_CLOSED_REQUEST`，
**这一次尝试不计入 `peer->fails`**。

于是形成自持续的循环：

```
撞死节点 → 卡 3 秒 → curl 先放弃（499）→ 不计失败 → fails 停在 0
   ↑                                                      │
   └────────── 轮询下一轮又轮到它 ←─────────────────────┘
```

`max_fails=2` 需要**两次完整的失败**才摘除。而每次到 3 秒就被客户端掐断，
**永远凑不满 2 次**，node1 就永远留在轮询里。日志里那 9 个 499 分散在 28 秒内，
一直没有停止，就是它始终没被摘掉的证据——如果第 2 次就摘掉了，后面应该是清一色的 200。

反过来，`-m 8` 给了 nginx 足够时间把事情做完：

```
#2 → node2 卡 3s → nginx 重试 node1 → 200（这次计入 fails=1）
#4 → node2 卡 3s → nginx 重试 node1 → 200（计入 fails=2 → 摘除，fail_timeout=10s）
#5 起 → 只走 node1 → 0.0006s
```

**第 2、4 次慢，正好是「轮询隔一次才轮到死节点」的必然结果**——这也是为什么它必须是偶数位。

### 定位：三步分清「谁放弃了」

**第 ① 步：把客户端超时放大到远超服务端的值**

```bash
docker stop node2-web && sleep 2
for i in $(seq 1 6); do
  curl -s -o /dev/null -m 8 -w "第${i}次 code=%{http_code} 耗时=%{time_total}s\n" http://127.0.0.1/whoami
done
docker start node2-web
```

**`-m 8` 不是为了「等更久」，是为了「让 nginx 把话说完」。**
如果它能在 3 秒内解决，8 秒不会多花一毫秒；如果它需要 3.1 秒，3 秒的窗口就会把真相切掉。

**第 ② 步：看 nginx 记了多少 499**

```bash
docker exec lb tail -60 /var/log/nginx/lb_access.log
```

- 大量 **`499`** → 客户端先断，你测的是自己
- **`502` / `504`** → nginx 侧真失败，继续查 upstream
- 清一色 **`200`** → LB 正常，问题在别处

**第 ③ 步：找 `upstream timed out`**

```bash
tail -30 logs/nginx-lb/lb_error.log | grep -i upstream
```

> **⚠️ 这一步有个陷阱：`docker logs lb` 会是空的。**
>
> compose 里写了 `./logs/nginx-lb:/var/log/nginx`，这个 bind mount **把整个日志目录盖住了**。
> 官方 nginx 镜像本来把 `access.log → /dev/stdout`、`error.log → /dev/stderr` 做成软链，
> 但目录一被挂载，那两个软链就不存在了，所有日志都写到宿主机磁盘。
>
> 所以「`docker logs lb` 什么都没有」**不等于「nginx 没报错」**。这个坑和 #15 是同一类：
> 你在错误的地方找证据，然后得出「没有证据」的结论。

### 修法：把切换窗口从 6 秒压到 2 秒

**核心是一个公式**（这是整件事的钥匙）：

```
摘除需要多久 = max_fails × proxy_connect_timeout
```

原因：每次撞死节点都要**傻等满 connect timeout**，而 `max_fails=2` 要求失败两次。

改之前：`2 × 3s = 6 秒`（实测就是第 2、4 次各 3 秒）
改之后：`2 × 1s = 2 秒`

```nginx
upstream web_cluster {
    server node1-web:80 max_fails=2 fail_timeout=10s;
    server node2-web:80 max_fails=2 fail_timeout=10s;
    keepalive 32;
}

location / {
    proxy_connect_timeout 1s;      # ★ 3s → 1s
    proxy_next_upstream error timeout http_500 http_502 http_503 http_504;
    proxy_next_upstream_tries 2;
}
```

**为什么 1 秒是安全的**：lb 和 node-web 在同一台宿主机、同一个 bridge 网络里，
RTT 是**微秒级**。1 秒已经是「宽松到夸张」的上限。真正需要担心 1 秒不够的场景是跨机房、跨公网。

**为什么不能干脆设 100ms**：同一台机器上跑 7 个容器，2G 内存，
`docker stop` 期间宿主机可能短暂卡顿。1 秒留了三个数量级的余量，100ms 只剩一个数量级。

**为什么 `max_fails` 保持 2 而不改成 1**：

| 配置 | 切换窗口 | 误摘风险 |
|------|---------|---------|
| `max_fails=1` | 1 秒 | 一次抖动就摘掉健康节点，10 秒内只剩一半容量 |
| `max_fails=2` | 2 秒 | 要连续两次都失败，**抖动很难连续两次** |

对 2 节点的集群，`max_fails=1` 的风险不值得省那 1 秒。

**验证方法**：改完 `docker exec lb nginx -s reload`，重跑演练，应该看到：

```
200:node1-web(1ms) 200:node2-web(1002ms) 200:node1-web(1ms) 200:node2-web(1005ms) 200:node1-web(1ms) ...
                                                                          ↑ 之后全是 1ms
统计：20 次 / 失败 0 / 超 1s 2 / 最慢 1005ms
```

**只有 2 次慢请求，之后全恢复。** 用户感受到的是「有两次请求慢了一秒」，不是「网站挂了」。

### 事后验证：日志把整件事写成了流水账

改完回头看 `logs/nginx-lb/lb_error.log`，三个阶段全被记下来了。**这份日志值得逐行读**，因为它是「机制真的按原理运转」的第一手证据，不是推测。

#### ① `temporarily disabled` = 摘除成功的直接证据

```
2026/10/27 13:25:21 [error] 22#22: *3609 upstream timed out (110: Operation timed out)
                           while connecting to upstream, upstream: "http://172.20.0.12:80"
2026/10/27 13:25:24 [warn]  22#22: *3612 upstream server temporarily disabled
                           while connecting to upstream
2026/10/27 13:25:24 [error] 22#22: *3612 upstream timed out (110: Operation timed out)
                           while connecting to upstream
```

`temporarily disabled` 这句话在 nginx 源码里**只有一个触发点**：本次失败之后 `peer->fails >= max_fails`。
它一出现，就等于 nginx 亲口告诉你「这个节点我已经摘掉了」。**不需要再猜，不需要再看别的证据。**

注意日志时间戳是**请求结束的时刻**，不是开始。还原时间线：

| 时刻 | 事件 | 累计 fails |
|------|------|-----------|
| 13:25:18 | 第 1 次轮询落到 node2，SYN 石沉大海 | 0 |
| 13:25:21 | 等满 3s 放弃 → 打第 1 条 `error` | **1** |
| 13:25:21 | `proxy_next_upstream` 立刻重试 node1 → 200（用户没感知） | 1 |
| 13:25:21 | 下一轮轮询又落到 node2，再发一次 | 1 |
| 13:25:24 | 又等满 3s → 打第 2 条 `error`，同时 fails=2 达标 → 打 `warn` | **2 → 摘除** |
| 13:25:24 起 | 后续请求只走 node1 | — |

所以 `21 → 24` 差 3 秒，**不是「摘除用了 3 秒」，而是「第二次等待又花了一个 connect timeout」**。
整个窗口从 `13:25:18` 算到 `13:25:24`，正好 `2 × 3s = 6 秒`——和公式严丝合缝。

**一个细节能验证这个还原**：第 1 条只有 `error` 没有 `warn`，第 2 条是 `warn` 和 `error` 同时出现，且 `warn` 在前。
因为 nginx 是「先判断 fails 是否到上限 → 打 warn → 再打本次请求的 error」。**日志顺序本身就是执行顺序。**

#### ② 10/27 和 10/29 两组日志，正好构成一次 A/B 对比

同一个动作（停节点），改配置前后各跑一次：

| 日期 | 两次超时的间隔 | 说明 |
|------|--------------|------|
| 10/27 13:25:21 → 13:25:24 | **3 秒** | `proxy_connect_timeout 3s` |
| 10/29 10:08:20 → 10:08:21 | **1 秒** | `proxy_connect_timeout 1s` |

```
2026/10/29 10:08:20 [error] 46#46: *4532 upstream timed out (110) while connecting to upstream
2026/10/29 10:08:21 [warn]  46#46: *4535 upstream server temporarily disabled while connecting to upstream
2026/10/29 10:08:21 [error] 46#46: *4535 upstream timed out (110) while connecting to upstream
```

`21 → 24` 和 `20 → 21`，**日志自己把「改名前后」的差别量化出来了**。
总降级窗口从 `2 × 3 = 6 秒` 缩到 `2 × 1 = 2 秒`，用户从「卡六秒」变成「卡两秒」。

（顺带：`*4532` 和 `*4535` 之间跳号，说明中间还有别的请求进来了，这很正常——轮询是全局共享的，不只服务你一个 curl。）

#### ③ `fail_timeout=10s` 的节律：每 12 秒重演一次

还有一组日志来自 **10/21，是真实用户**（`client: 112.2.91.171`、`host: 111.231.169.180`），不是演练：

```
2026/10/21 08:43:46 [warn] upstream server temporarily disabled while reading response header
2026/10/21 08:43:58 [warn] upstream server temporarily disabled while reading response header
2026/10/21 09:11:22 [warn] upstream server temporarily disabled while reading response header
2026/10/21 09:11:34 [warn] upstream server temporarily disabled while reading response header
```

**间隔精确是 12 秒**：10 秒 `fail_timeout` 到期把它放回轮询 → 下一次请求又撞上 → 再超时 → 再摘除。

这条节律的含义比它看起来重要：

> **`temporarily disabled` 是「暂时」，不是「永久」。10 秒后 nginx 会无条件把它放回去试一次。**
> 只要后端没恢复，这个循环就会一直转。

于是日志形态本身就成了判据：

| 日志形态 | 含义 |
|---------|------|
| 只有一条 `disabled`，之后没了 | 瞬时抖动，已经自愈 |
| 同一个 upstream 每隔 ~12 秒一条 `disabled` | **故障持续存在**，后端一直没起来 |
| `disabled` 密集到几乎每条都是 | 集群实际上只剩一个节点在扛，容量已经腰斩 |

**这比看监控更有用**：不需要任何额外工具，只看这条 warn 的密度，就能判断「故障是过去时还是进行时」。

### 换别的做法会怎样

| 方案 | 切换速度 | 代价 |
|------|---------|------|
| 调小 `proxy_connect_timeout` | 1~2 秒 | **零成本**，本项目采用 |
| `max_fails=1` | 1 秒 | 抖动容易误摘，2 节点集群扛不住 |
| 上主动健康检查（`health_check` 指令） | 毫秒级 | **nginx 开源版不支持，要商业版 Nginx Plus** |
| 换 HAProxy + `option httpchk` | 毫秒级 | 要换组件，简历上多一个技术栈但架构复杂度上升 |
| Keepalived 做 VIP | 秒级 | 解决的是「LB 单点」，**不解决「后端节点故障」**，两件事不能互相替代 |
| 靠 `fail_timeout` 调小 | 摘除更快恢复，但**不加快首次发现** | 治不了根本——发现慢是因为 connect timeout |

**关键区别：`proxy_connect_timeout` 决定「发现有多快」，`fail_timeout` 决定「摘掉后多久放回来」。**
这两个经常被混为一谈，实际管的是完全不同的事。

### 一句话记住

> **客户端超时必须大于服务端超时，否则你测到的是「自己放弃了」，不是「服务坏了」。**
> **容器被 stop 后 IP 会静默丢包，不是拒绝连接——所以故障发现只能靠超时，快慢全看 `proxy_connect_timeout`。**

### 面试怎么讲

**面试官会问**：nginx 做负载均衡，后端挂了一个节点，多久能切走？怎么验证？

**答法**：切开三个问题——**发现**、**重试**、**摘除**。

发现靠 `proxy_connect_timeout`。这里有个反直觉的点：**容器死掉之后 IP 是静默丢包，不是回 RST**，
所以 nginx 不能靠「连接被拒」秒级发现，只能傻等到超时。我实测下来每次都精确卡在 3.005 秒——
这个数字本身就说明它是在等超时，不是在等 RST。

重试靠 `proxy_next_upstream`。这一条保证**切换期间客户端仍然拿到 200**，只是慢，不是错。

摘除靠 `max_fails`。摘除时间 = `max_fails × proxy_connect_timeout`，我把它从 2×3s=6 秒压到 2×1s=2 秒。

**验证的时候踩过一个坑值得说**：我一开始用 `curl -m 3` 去测，结果 20 次里 9 次返回 000，
看起来像摘除失效。查访问日志发现有大量 `499`——**499 是客户端先断开**，不是后端错误。
更关键的是，被客户端掐断的请求**不计入 `max_fails`**，所以失败次数永远凑不满 2 次，
节点永远不被摘除，形成自持续的假故障。把 `-m` 放大到 8 秒，立刻变成 6 次全 200，
只有第 2、4 次各慢 3 秒——这才是真实行为。

**关键一句**：**监控和演练的「观测窗口」必须比「被观测的机制」更宽，否则你测的永远是自己的超时。**

**追问：那 499 到底算谁的错？**
不算错，它是一个信号：**客户端等不及了**。生产上 499 大量出现，通常意味着后端慢到用户主动取消，
是「体验已经受损」的早期指标。监控 499 比例比监控 5xx 更能反映真实的用户感受。

## 19. 同样是「upstream 超时」，connecting 和 reading 是两种病

### 现象

同一份 `lb_error.log` 里，两类日志长得几乎一样，只有一处措辞不同：

```
# A 类 —— 演练时有意停节点造成的
[error] upstream timed out (110: Operation timed out) while connecting to upstream,
        request: "GET /whoami HTTP/1.1", upstream: "http://172.20.0.12:80/whoami"

# B 类 —— 10/21 真实用户访问时留下的
[warn]  upstream server temporarily disabled while reading response header from upstream,
        request: "GET /api/stats HTTP/1.1", upstream: "http://172.20.0.12:80/api/stats"
```

两行都是「上游超时 + 摘除这个节点」，很容易当成同一个问题。**但它们指向完全不同的故障，修法也完全不同。**

如果不加区分，后果是这样：B 类故障（后端活着但慢）被误判成 A 类（节点挂了），
于是你去调 `proxy_connect_timeout`、去查网络、去重启容器——**这些动作一个都不会有用**，
因为连接一直是通的。

### 原理：一次代理转发有四个阶段，各有各的超时

nginx 转发一个请求到上游，不是「发出去等结果」这么简单，中间有四个可以卡住的点：

| 阶段 | 在干什么 | 对应指令 | 超时说明什么 |
|------|---------|---------|------------|
| **connecting** | TCP 三次握手 | `proxy_connect_timeout` | 这个 IP 上**没人接 SYN** |
| **sending request** | 把请求头/体写过去 | `proxy_send_timeout` | 对端**不读**数据（接收窗口满、进程卡死） |
| **reading response header** | 等响应的第一行 | `proxy_read_timeout` | 连接通了、请求发了，但**后端不说话** |
| reading response body | 读响应体（流式时） | `proxy_read_timeout` | 说到一半停住了 |

日志里的措辞就是阶段名，`while connecting` 和 `while reading response header` 精确对应前两个和后一个。

**为什么这两件事的根因天差地别**：

```
B 类（reading 超时）：TCP 握手成功 → 说明端口在监听、进程活着、网络通
                      ↓
                    请求送达了，但后端 10 秒内产不出响应
                      ↓
                    所以问题在「应用内部」：慢 SQL、死锁、连接池耗尽、外调接口卡住

A 类（connecting 超时）：SYN 发出去没回应
                      ↓
                    有两种可能，日志本身分不出来（见下面的定位表）
```

**一分钟对照实验：`stop` 和 `pause` 是天然的两个对照组**

想亲眼看到两种超时的差别，不需要改代码，两个命令就够：

```bash
# A 组：stop —— 容器连同 veth 一起消失 → 应该看到 while connecting
docker stop node2-web && sleep 1
curl -s -o /dev/null -m 5 -w "A组 code=%{http_code} 耗时=%{time_total}s\n" http://127.0.0.1/whoami
tail -2 logs/nginx-lb/lb_error.log

# B 组：pause —— 容器还在，只是进程被冻住 → 应该看到 while reading
docker start node2-web && sleep 3
docker pause node2-web
curl -s -o /dev/null -m 15 -w "B组 code=%{http_code} 耗时=%{time_total}s\n" http://127.0.0.1/whoami
tail -2 logs/nginx-lb/lb_error.log

docker unpause node2-web
```

**为什么 `pause` 会走到 reading 阶段**：`docker pause` 用的是 cgroup freezer，冻结的是**进程**，
不是网络栈。内核仍然会替那个 socket 完成三次握手（SYN 由内核回，不需要应用参与），
所以 TCP 连得上；但应用被冻住，永远不调 `read()`、也永远不会 `write()` 响应。

于是 nginx 的连接建立成功、请求发出去，然后**卡在等第一行响应**上，直到 `proxy_read_timeout` 到点。
一模一样的一次「超时」，走的是完全不同的阶段——**这就是为什么不能只看结论「超时了」。**

### 定位：一张表分清「人不在」和「人不说话」

| 日志阶段 | 上游 HTTP 状态 | 实际发生什么 | 下一步查什么 |
|---------|--------------|------------|------------|
| `connecting` 超时 | 无（没连上） | 容器没了 / 端口没监听 / 中间有防火墙 DROP | `docker ps`、`ss -lntp`、`iptables -L` |
| `connecting` → **`Connection refused`** | 无 | 进程在、端口没监听 | 应用启动日志 |
| `reading` 超时 | 无 | **进程活着但卡住** | 应用日志、`slow_query_log`、`docker stats` 看 CPU |
| `reading` → 立刻 `502` | 502 | 后端主动断开（崩了） | `docker logs <容器>` 最后 30 行 |
| `sending` 超时 | 无 | 后端不读请求体 | 少见，通常是超大 POST + 后端不消费 |

**最快的分辨办法是看「上游状态码有没有值」**：

- `upstream_status` 为空 → 根本没拿到响应，问题在连接层或后端完全没回
- `upstream_status` 是 `502/504` → 后端有反应，但结果不对

所以日志格式里必须带 `$upstream_addr $upstream_status $upstream_response_time $request_time`。
**默认的 `main` 格式不带这四个变量，等于把定位信息扔掉了**——这和 #16 把 tar 的 stderr
重定向进日志是同一类错误：出了事才发现该看的东西没记。

### 修法：两种病，两套药

**A 类（connecting 超时）——本项目演练遇到的：**

根因是「容器被 stop 后 IP 静默丢包」，修法就是 #18 那套：
调小 `proxy_connect_timeout` + `max_fails` 摘除。**在连接层解决。**

**B 类（reading 超时）——10/21 真实用户遇到的：**

连接层一切正常，**调 `proxy_connect_timeout` 毫无意义**。要做的是往上游走一层：

```bash
# ① 先确认 web 容器是否活着且端口通
docker exec lb sh -c 'nc -z -w2 172.20.0.12 80 && echo "端口通"'

# ② 从 lb 内部直接打后端，绕过轮询看真实耗时
docker exec lb sh -c 'curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://172.20.0.12/api/stats'

# ③ 再往下一层：web 到 app 的转发
docker exec node2-web sh -c 'curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" http://node2-app:8080/stats'

# ④ app 到 db
docker exec node2-app sh -c 'time mysqladmin -h node2-db -uroot -p*** ping'
```

**逐层测量，哪一层耗时突增，问题就在哪一层。** 这叫二分法——一次砍掉一半可能性，
而不是凭直觉猜「大概是数据库慢」。

**那 `proxy_read_timeout` 该不该调大？**

| 做法 | 效果 | 判断 |
|------|------|------|
| 调大 `proxy_read_timeout`（比如 10s → 60s） | 用户等更久，**慢请求变成更慢的请求** | ❌ 掩盖问题 |
| 保持 10s，让请求快速失败 + 重试下一个节点 | 用户可接受，同时**暴露真实问题** | ✅ 本项目做法 |
| 查到慢 SQL 并加索引 | 根因解决 | ✅ 最终答案 |

`proxy_read_timeout` 是**止损线**，不是性能参数。它的作用是「别让用户无限等」，
而不是「让慢请求有机会成功」。**把它调大等于把故障藏起来。**

### 换别的做法会怎样

| 方案 | 能发现 A 类 | 能发现 B 类 | 代价 |
|------|-----------|-----------|------|
| 只调 `proxy_connect_timeout` | ✅ | ❌ | 零成本，但对应用层慢毫无帮助 |
| 只调 `proxy_read_timeout` | ❌ | ⚠️ 只是延后失败 | 用户等更久，问题更难查 |
| 两条都调 + 分阶段日志 | ✅ | ✅ | 需要改日志格式，成本极低 |
| 上 APM（SkyWalking / Pinpoint） | ✅ | ✅ | 要额外部署组件，2G 机器扛不住 |
| 主动健康检查（Nginx Plus） | ✅ | ⚠️ 只能探「活着」不能探「慢」 | 商业版收费 |

**注意最后一行**：主动健康检查探的是 `/health` 返回 200，**探不出「某个接口慢」**。
`/health` 快而 `/api/stats` 慢的情况，主动检查会认为节点健康，照样把流量打过去。

### 一句话记住

> **`while connecting` 是「找不到人」，`while reading` 是「找到人了，他不说话」。**
> **前者改超时，后者查代码。**

### 面试怎么讲

**面试官会问**：nginx 报 `upstream timed out`，你怎么排查？

**答法**：**先看超时发生在哪个阶段，这一步就能砍掉一半可能性。**

`while connecting` 超时，说明 SYN 没回应。这里有个反直觉的点：**容器被 stop 之后 IP 是静默丢包，
不是回 RST**，所以它跟「端口没监听」表现完全不同——后者毫秒级报 `Connection refused`，
前者要傻等到 connect timeout。如果日志里连 `Connection refused` 都没有，基本可以确定是网络层丢包。

`while reading response header` 超时，说明 TCP 通了、请求发出去了，但后端产不出响应。
**这时候查超时配置是最没用的做法**——连接全程都是通的，`proxy_connect_timeout` 根本没参与。
要往上一层查应用：慢 SQL、连接池耗尽、死锁、外调接口卡住。

我在项目里两种都遇到过：演练停容器是 `connecting`，改动前后日志间隔从 3 秒降到 1 秒；
线上真实用户那次是 `reading`，请求的是 `/api/stats`，最后查到是应用侧慢。

**关键一句**：**`upstream timed out` 只说明「等了太久」，不说明「等谁」。日志里的 `while xxx` 才告诉你等在哪一步。**

**追问：为什么 `proxy_read_timeout` 不该调大？**
因为它是止损线不是性能参数。调大只让用户从「等 10 秒失败」变成「等 60 秒失败」，
既没提高成功率，又让故障更难被发现。正确做法是保持它，让问题快速暴露，然后去查应用层。

# 第七部分：监控告警链路的两个暗坑

这一部分是给 Zabbix 加的。它的坑和前面七个部分性质不同：
**前面都是「东西坏了」，这里是「东西没坏，但它在骗你」。**

## 20. 告警配置全对，钉钉一声不响

### 现象

监控搭到最后一步——把告警推到手机。配完之后，界面上看不出任何问题：

- 触发器正常：`Monitoring → Problems` 里能看到 `主从延迟过高`
- Action 是启用的：`actions` 表 `status=0`
- Operation 存在：`operations` 表有两条，分别是问题通知和恢复通知
- 消息内容配好了：`opmessage` 表有 subject
- 收件人挂着：`opmessage_grp` / `opmessage_usr` 都有记录
- 媒介启用了：`media_type` 里 `DingTalk` 是 Enabled
- 用户身上也挂了：`media` 表有 `DingTalk`

**每一项单独看都对。但手机一条消息都没有，`Action log` 一片空白。**

而且这不是「发失败」，是**什么都没发生**。数据库里能看到的对比是：

```
events 表（触发器事件）：
  19:08:10  value=1   主从延迟过高   ← PROBLEM，事件产生了
  19:10:02  value=0   主从延迟过高   ← 恢复，事件也产生了

alerts 表（通知记录）：
  2 | 17:20:02 | status=2 | No media defined for user   ← 最后一次
  （之后什么都没有）
```

**有事件、没有通知记录。** 这个组合是最难查的一种，因为大部分排查思路都是从「发送失败」出发的，
而这里根本没有「发送」这个动作。

### 原理：告警投递要过五道闸门，任何一道算出空集就整条作废

Zabbix 不是「事件产生就发消息」，中间要算一次**收件人集合**：

```
① 触发器求值           →  产生 event（value=1 / 0）
② 找匹配的 action      →  eventsource + conditions + status 三项都满足
③ 计算收件人集合       →  从这里开始是重点
④ 集合非空             →  写 alerts（status=3）→ alerter 发送 → 更新 status
⑤ 集合为空             →  ★ 什么都不写，只在 debug 日志留一行
```

第 ③ 步展开是这样：

```
operation 里配置的 user group  →  展开成组内所有 user
            ＋
operation 里直接配置的 user
            ↓
        对每个 user 逐一过滤：
            ├─ 用户本身可用吗
            ├─ 这个 user 有 media 吗
            ├─ 那条 media 是启用状态吗（media.active = 0）
            ├─ media.mediatypeid 和 opmessage.mediatypeid 对得上吗
            ├─ media.severity 覆盖当前事件的级别吗   ← ★ 本次根因
            └─ media.period 包含当前时间吗
            ↓
        全部通过的才进入收件人集合
```

**第 ⑤ 步是整件事的关键：它不写数据库、不报错、界面上没有任何痕迹。**

Zabbix 的设计逻辑是「没有收件人 = 这条告警不需要发」，属于正常业务分支，不是错误。
所以它不会给你留任何可查的东西——`alerts` 表里连一行 `status=2` 都没有。

这和「发送失败」是完全不同的两种状态，必须分清：

| alerts 表 | 含义 | 该查什么 |
|---|---|---|
| 有记录，`status=1` | 发出去了 | 钉钉侧（发错群 / 限流 / 被拦） |
| 有记录，`status=2` | 尝试发送，失败 | `error` 列会写原因，查媒介 / 网络 / 凭据 |
| **没有记录** | **算出了空收件人，根本没尝试** | **action / operation / 收件人关联 / media** |

### 根因：severity 是位掩码，`7` 不含 `Average`

最后一行数据查出来是这样：

```
mediaid | userid | mediatypeid |  sendto  | active | severity |     period
--------+--------+-------------+----------+--------+----------+-----------------
      1 |      1 |          72 | dingtalk |      0 |        7 | 1-7,00:00-24:00
```

前面七列全对：类型对了、启用了、时间段对了。**只有 `severity = 7`。**

`media.severity` 不是「最低级别」，是**位掩码**——每个级别占一个二进制位：

| 级别 | 中文 | 位值 | `7` 里有吗 |
|---|---|---|---|
| 0 | Not classified | 1 | ✅ 有（1） |
| 1 | Information | 2 | ✅ 有（2） |
| 2 | Warning | 4 | ✅ 有（4） |
| 3 | **Average** | **8** | ❌ **没有** |
| 4 | High | 16 | ❌ 没有 |
| 5 | Disaster | 32 | ❌ 没有 |

`7 = 1 + 2 + 4`，只勾了最低三档。

而我们造的 `主从延迟过高` 触发器，级别是 **Average**。它的位值是 `8`，`7 & 8 = 0`，
于是在「media.severity 覆盖当前事件级别吗」这一步被过滤掉，收件人集合变成空集，告警静默消失。

**这个错误的杀伤力在于方向是反的**：

> `severity = 7` 的监控，**只通知 Warning 及以下，Average / High / Disaster 全部静默**。

也就是说，**问题越严重，越收不到告警**。而界面上看起来，你明明勾了 Warning 那一格。

### 定位：五层逐级查表，每层用一条 SQL 否掉一个假设

这次的排查过程比结论更有价值。**配置层的每一项我都查过、都对**，
所以只能一层一层往下走，每层用一个数据点排除一种可能：

| 层 | 查什么 | 命令 | 本次结果 |
|---|---|---|---|
| 1 | 通知记录 | `select * from alerts order by alertid desc` | 停在 17:20，之后无记录 |
| 2 | 事件记录 | `select * from events order by eventid desc` | 19:08 / 19:10 都有 → 触发器正常 |
| 3 | operation + 消息 | `select * from operations` / `opmessage` | 11/12 都对，`mediatypeid=72` |
| 4 | 收件人关联 | `select * from opmessage_grp` / `opmessage_usr` | 有 11/12 的记录 |
| 5 | 媒介 + 用户 media | `select * from media_type` / `media` | **media.severity = 7** |

第 1 层是最重要的判断点：**`alerts` 表有没有记录，直接把问题劈成两半**。

```bash
# 一键查完五层（容器名按实际改）
docker exec zbx-postgres psql -U zabbix -d zabbix -c 'select alertid,to_timestamp(clock) as t,status,left(error,40) from alerts order by alertid desc limit 5'
docker exec zbx-postgres psql -U zabbix -d zabbix -c 'select eventid,to_timestamp(clock) as t,value,name from events order by eventid desc limit 8'
docker exec zbx-postgres psql -U zabbix -d zabbix -c 'select operationid,actionid,operationtype,recovery from operations order by operationid'
docker exec zbx-postgres psql -U zabbix -d zabbix -c 'select operationid,default_msg,mediatypeid,subject from opmessage order by operationid'
docker exec zbx-postgres psql -U zabbix -d zabbix -c 'select mediaid,userid,mediatypeid,sendto,active,severity,period from media'
```

**为什么一定要查表而不是看界面**：Zabbix 的前端在保存时会做一层 JS 校验，
它和数据库里的真实状态**可以不一致**。本次就遇到一个典型例子，见下面的「三个假线索」。

### 修法

把 `media.severity` 改成 `63`（= 1+2+4+8+16+32，全选）：

**界面做法**：`Users → Users` → `Admin` → `Media` 标签 → 点那条 `dingtalk` →
`Use if severity` 里**六个级别全部逐个勾选**（注意 `Not classified` 也要勾）→ 弹窗 Update → 页面底部 Update。

**SQL 快速验证**（改完要等 server 重载配置，默认 60 秒）：

```bash
docker exec zbx-postgres psql -U zabbix -d zabbix -c 'update media set severity=63 where mediaid=1'
```

改完推一个超标值触发告警验证：

```bash
printf '%s %s %s\n' "$(hostname)" shop.repl.lag 999 \
  | docker run --rm -i --network host --entrypoint zabbix_sender \
      zabbix/zabbix-server-pgsql:alpine-7.0-latest \
      -z 127.0.0.1 -p 10051 -i -

# 10 秒后查通知记录
docker exec zbx-postgres psql -U zabbix -d zabbix \
  -c 'select alertid,to_timestamp(clock) as t,status,left(error,30) from alerts order by alertid desc limit 3'
```

`status=1` 就是真发出去了，同时手机会响。

### 三个假线索（这次排查绕路的主要原因）

这一节比修法更值得记。**排查过程中有三个「看起来很有价值、实际是假的」的信息**，
每一个都足以把方向带偏：

| 假线索 | 看起来说明什么 | 实际是什么 |
|---|---|---|
| 前端红字 `At least one user or user group must be selected` | operation 没配收件人，保存被拦住了 | **Zabbix 7.0 前端校验缺陷**，数据库里收件人完整存在，红字不影响后端 |
| `Test` 按钮点通了 | 整个通知链路都正常 | **Test 只测 media type 本身**，绕过用户配置、绕过 severity、绕过 action 匹配 |
| 手动 `SHOW REPLICA STATUS` 显示两个 `Yes` | 采集脚本应该也能取到 | 脚本多加的 `-N -B` 把输出格式换掉了（见第 21 坑） |

三个线索共同的特征是：**它们都在验证一个「相邻但不相同」的东西**。

- 前端红字验证的是「浏览器端的表单状态」，不是「数据库里的配置」
- Test 按钮验证的是「这个媒介能不能发出去」，不是「这条告警会不会发这条媒介」
- 手动 SQL 验证的是「MySQL 里的复制状态」，不是「脚本解析出来的复制状态」

**排查时最该警惕的，就是用一个相邻层的证据去证明当前层没问题。**

### 换别的做法会怎样

| 方案 | 能提前发现吗 | 代价 |
|---|---|---|
| 配完后只在界面上逐项核对 | ❌ | 本次失败的方式，界面上全绿 |
| 配完后看 `Action log` 有没有记录 | ⚠️ 只能发现「发送失败」，发现不了「没发送」 | 低 |
| **配完后查 `alerts` 表，确认有 `status=1` 的记录** | ✅ | 一条 SQL |
| 配完后造一个假故障，看手机响不响 | ✅ | 最直接，但需要能造出跨级别的故障 |
| 加 `nodata()` 监控告警链路自身 | ✅ 能发现「整条链路停摆」 | 中，本身也依赖链路 |

**推荐组合**：造一次假故障（覆盖最高级别）+ 查 `alerts` 表确认 `status=1`。
前者验证「能不能到」，后者验证「Zabbix 认为到了」。

### 一句话记住

> **「没收到告警」分三种：发失败了、产出了空收件人、压根没产生事件。**
> **查 `alerts` 表有没有记录，一次就能分辨。**

以及这一条的姊妹句：

> **界面上看着勾了，不等于数据里勾上了。告警级别是位掩码，少勾一格等于关掉一整档。**

### 面试怎么讲

**面试官会问**：Zabbix 告警配好了，但收不到通知，你怎么排查？

**答法**：**先分清三种「没收到」，靠一张表就能劈开。**

第一种，`alerts` 表有记录且 `status=2`，说明 Zabbix 尝试发了但失败，`error` 列会直接写原因，
比如「No media defined」「连接超时」。这层最好查。

第二种，`alerts` 表**没有记录**，但 `events` 表有事件——这是最隐蔽的。
说明 Zabbix 算出的收件人集合是空的，直接静默丢弃了，**它认为这条告警不需要发**。
这时候要往上查四样东西：action 匹配、operation 配置、收件人关联表、以及每个用户的 media 是否满足条件。
media 的过滤条件有六个：启用状态、媒介类型匹配、**severity 位掩码**、时间段、用户可用性。

第三种，`events` 表都没有事件——那问题在触发器，跟通知无关。

我在项目里踩的是第二种，根因很反直觉：`media.severity` 是**位掩码**不是「最低级别」，
我配成了 `7`（= 1+2+4，只覆盖 Warning 及以下），而触发器是 Average（位值 8），
`7 & 8 = 0`，于是这个 media 被过滤掉，收件人为空，整条告警消失。
**讽刺的是，这个配置的效果是「越严重的问题越收不到」，而界面上看起来一切正常。**

**关键一句**：**Zabbix 里「没有告警记录」和「发送失败」是两件完全不同的事，
前者的意思是「它算完觉得没人该收」，连错误日志都不会给你留。**

**追问：为什么不用 `Test` 按钮验证？**
因为 `Test` 只测试 media type 本身——它拿你手填的 URL 直接发一次 HTTP 请求，
完全绕过用户配置、绕过 severity、绕过 action 匹配。
**Test 通过只能证明「这个通道能发出去」，证明不了「这条告警会走这个通道」。**
我在项目里就是被这个按钮骗了一段时间。

## 21. 同一句 SQL，多两个参数就废了

### 现象

监控采集脚本 `host_checks.sh` 跑出来是这样：

```bash
[root@VM-0-14-opencloudos monitoring]# bash scripts/host_checks.sh --dry-run
hostname=VM-0-14-opencloudos
shop.repl.lag     = -1
shop.repl.running = 0
```

`running = 0` 表示主从复制断了，`lag = -1` 表示取不到延迟。看起来是**主从真的挂了**。

但手动执行同一条 SQL，结果是好的：

```bash
[root@VM-0-14-opencloudos monitoring]# docker exec -e MYSQL_PWD='Root@123456' node2-db mysql -uroot -e 'SHOW REPLICA STATUS\G' 2>&1 | head -30
*************************** 1. row ***************************
Replica_IO_State: Waiting for source to send event
Source_Host: node1-db
Replica_IO_Running: Yes      ← 好的
Replica_SQL_Running: Yes     ← 好的
```

**同一个容器、同一个库、同一句 SQL，一条正常一条报错。** 并且脚本那条不报错，只是安静地返回了空。

### 原理：`-B` 会把 `\G` 的垂直输出覆盖掉

两条命令唯一的差别是脚本里多了 `-N -B`：

```bash
# 手动执行的（正常）
mysql -uroot -e 'SHOW REPLICA STATUS\G'

# 脚本里的（取不到）
mysql -uroot -N -B -e 'SHOW REPLICA STATUS\G'
```

- `\G` 是**客户端**的指令，意思是「把结果集按竖排显示，每行 `字段名: 值`」
- `-B`（batch）是**另一个客户端选项**，意思是「用 tab 分隔、一条记录一行，不要任何装饰」

**两者冲突时，`-B` 赢。** 于是脚本拿到的不是：

```
Replica_IO_Running: Yes
Replica_SQL_Running: Yes
```

而是一整行几十个 tab 分隔的裸值：

```
Waiting for source to send event	node1-db	repl	3306	10	mysql-bin.000003	2718	...
```

后面的解析是这么写的：

```bash
IO=$(echo "$STATUS" | sed -nE 's/^ *(Replica|Slave)_IO_Running: *//p' | head -1)
```

它要匹配 `Replica_IO_Running:` 这个**字面量**，而 batch 输出里根本没有这个字符串。
于是 `IO`、`SQL` 都是空，`RUNNING` 保持默认值 `0`，`LAG` 保持默认值 `-1`。

**最要命的是退出码是 0。** 命令执行成功、没有任何报错，只是安静地返回了「取不到」。
这就是为什么它骗了人——**一个不报错的错误，比报错难查十倍**（见心法 3）。

### 定位：单变量对照

这类问题不需要猜，只需要**把两条命令逐字比较**：

```bash
docker exec ... node2-db mysql -uroot        -e 'SHOW REPLICA STATUS\G' | head -5
docker exec ... node2-db mysql -uroot -N -B  -e 'SHOW REPLICA STATUS\G' | head -5
```

第一条输出竖排、带字段名；第二条输出一行裸值。看一眼就明白了。

顺带一个佐证：脚本里另一条查复制通道的命令，输出是这样的：

```bash
docker exec ... node2-db mysql -uroot -N -B -e "SELECT CHANNEL_NAME, SERVICE_STATE FROM performance_schema.replication_connection_status"
# 输出：ON
```

一个 tab 加一个 `ON`。这正是 `-N`（去列名）+ `-B`（tab 分隔）的效果：**第一列是空字符串，
所以你只看到一个 tab 后面跟着 `ON`**。这条输出本身就是「`-N -B` 正在生效」的证据。

### 修法

删掉 `-N -B`，让 `\G` 恢复作用：

```bash
sed -i "s/-uroot -N -B -e 'SHOW REPLICA STATUS/-uroot -e 'SHOW REPLICA STATUS/" scripts/host_checks.sh
```

改完 `--dry-run` 立刻正常：

```bash
hostname=VM-0-14-opencloudos
shop.repl.lag     = 0
shop.repl.running = 1
shop.backup.age   = 245442
```

> 顺带说一个反面对照：项目里的 `health_check.sh` 从头到尾都是对的，
> 因为它写的是 `mysql -uroot -e "SHOW REPLICA STATUS\G"`，**没有 `-N -B`**。
> `host_checks.sh` 是从它抄的，抄的时候「顺手规范化一下」加了两个参数，就坏在这里。
> **同一台机器、同一个库、同一句 SQL，只因为多了两个参数，一个正常一个失灵。**

### 姊妹案例：`zabbix_sender` 的 `-k` 只能出现一次

同一类错误的另一个实例，同一天撞上。

```bash
# 我以为可以这样（多组 key/value）
zabbix_sender -z 127.0.0.1 -s host \
  -k shop.repl.lag     -o 0 \
  -k shop.repl.running -o 1 \
  -k shop.backup.age   -o 12345
```

报错：

```
zabbix_sender [1]: option "-k" or "--key" specified multiple times
zabbix_sender [1]: option "-o" or "--value" specified multiple times
```

`zabbix_sender` 有两种工作模式：**命令行单条**（`-k/-o`，只能一组）和
**批量文件**（`-i`，每行 `主机名 key 值`，可以任意多行）。两者二选一，不能混用。

正确写法是走 stdin：

```bash
printf '%s %s %s\n' \
  "$(hostname)" shop.repl.lag     0 \
  "$(hostname)" shop.repl.running 1 \
  "$(hostname)" shop.backup.age   12345 \
| docker run --rm -i --network host --entrypoint zabbix_sender \
    zabbix/zabbix-server-pgsql:alpine-7.0-latest \
    -z 127.0.0.1 -p 10051 -i -
```

**两个案例的共同点**：都是我按「想当然的参数语义」写代码，而没有先查它到底怎么设计。

但它们的表现恰好相反，值得作为一对记住：

| | `-N -B` 覆盖 `\G` | `-k` 重复 |
|---|---|---|
| 表现 | **静默返回错误数据** | **当场报错** |
| 排查耗时 | 两小时 | 两分钟 |
| 危险程度 | 高（数据看起来是「真的」） | 低（明确告诉你哪里错） |

**所以：报错明确的 bug 是好 bug，不报错的 bug 才是真麻烦。**

### 一句话记住

> **命令不报错、结果却是空的 —— 先怀疑自己传的参数改了输出格式，别急着怀疑数据源。**

### 面试怎么讲

**面试官会问**：脚本取到的监控数据和手动执行的结果不一致，你怎么查？

**答法**：**先做单变量对照**——把脚本里的命令和手动命令逐字比对，一次只改一个参数。

我这个案例里，两边的差别只有 `-N -B` 两个选项。`\G` 要求竖排显示（`字段名: 值`），
而 `-B` 批量模式要求用 tab 分隔、去掉一切装饰。两者冲突时 `-B` 生效，
所以脚本拿到的是一整行裸值，后面用 `sed` 匹配 `Replica_IO_Running:` 一个字都匹配不上，
解析结果全空，脚本按默认值记成了「复制断了」。

**这个 bug 最值钱的地方在于它不报错。** 命令退出码是 0，没有任何异常输出，
只是安静地返回了错误的数据。如果不是拿手动结果去对照，它会一直显示「主从挂了」，
而且看起来特别可信——因为「采集失败」和「真的挂了」在数据上长得一模一样。

**关键一句**：**监控数据要能区分「采集失败」和「真的异常」，否则它会用假数据骗你做决策。**

**追问：那你怎么设计才不会有这个问题？**
两个做法：一，取不到值时不要给 `0`，给一个明确的哨兵值（比如 `-1`），并在触发器里单独处理；
二，配一条 `nodata()` 触发器，专门监控「采集本身有没有停」。
这也是我在 `host_checks.sh` 里用 `push` 架构而不是让 agent 读文件的原因——
**文件方案在 cron 挂掉时会一直返回上一次的旧值，监控显示一切正常，而实际上早就没人采集了。**

# 第八部分：nginx 配置的上下文陷阱

## 22. nginx 配置全对，容器起不来

### 现象

项目二 LNMP 第一次 `docker compose up -d`，三个服务只有两个起来：

```bash
$ docker compose ps
lnmp-mysql   Up (healthy)
lnmp-php     Up
# nginx 不见了
```

加 `-a` 才看到它，状态是 **`Created`**：

```
lnmp-nginx   nginx:1.27-alpine   ...   Created
```

`Created` 的含义很特殊，值得单独记住：

| 状态 | 含义 | `docker logs` |
|---|---|---|
| **`Created`** | 容器对象建好了，但**进程一次都没执行过** | **空的** |
| `Exited (1)` | 进程跑过、然后退出 | 有日志 |
| `Restarting` | 反复崩溃重启 | 有日志 |

这时候 `docker logs lnmp-nginx` 是空的。**「没有日志」不等于「日志被清了」，而是「进程根本没启动过」**——这两件事的排查方向完全不同。

### 第一轮误判：以为是 8080 端口冲突

这个误判很自然，理由有两条：

1. **三个服务里只有 nginx 映射了宿主机端口**（`8080:80`），php 和 mysql 只有 `expose`
2. 8080 之前正被另一个项目的容器占着

于是按端口冲突的思路走了一遍：

```bash
ss -tlnp | grep ':8080'
# >>> 8080 空闲
```

**端口是空的。假设被一条命令否掉了。**

接着重新 `up -d`，这次启动成功了，但 19 秒后：

```
lnmp-nginx   Exited (1)   19 seconds ago
```

**从 `Created` 变成 `Exited (1)`，说明进程真的跑起来了，然后死于自身原因。** 这时候 `docker logs` 终于有内容了。

### 根因：`log_format` 被写进了 `server {}`

```nginx
server {
    listen 80;
    ...
    log_format main_ext '$remote_addr - [$time_local] "$request" ...';  # ← 非法
    access_log /var/log/nginx/lnmp_access.log main_ext;
}
```

日志：

```
nginx: [emerg] "log_format" directive is not allowed here
       in /etc/nginx/conf.d/default.conf:12
```

`log_format` 是**只能出现在 `http` 上下文**的指令。写进 `server {}` 不是「不生效」，而是**直接拒绝启动**。

### 原理：conf.d 里的文件，天然就在 http 上下文里

这是整件事最反直觉的地方——**修法是把这段配置挪到文件最上面，内容一个字不用改。**

```
nginx.conf
└── http {
      ├── log_format main '...';        ← 镜像预定义的，所以 server 里能直接用 main
      │
      └── include conf.d/*.conf;        ← 你的文件在这里被展开
            │
            ├── ★ 文件顶层  ────────────  等价于写在 http{} 内 → log_format 合法
            │
            └── server { ... }  ────────  上下文降级为 server → log_format 非法
          }
```

**`conf.d/*.conf` 是被 `http {}` include 进去的**，所以「文件顶层」等于「http 上下文」。
一个指令能不能用，看的不是它在哪个文件里，而是**它最终落在哪一层花括号内**。

### 定位：`nginx -t` 一步到位

```bash
docker compose run --rm nginx nginx -t
```

输出会直接给文件名 + 行号 + 指令名：

```
nginx: [emerg] "log_format" directive is not allowed here in /etc/nginx/conf.d/default.conf:12
nginx: configuration file /etc/nginx/nginx.conf test failed
```

**这是本坑唯一需要记住的命令。** nginx 的语法检查做得非常好——它不但告诉你哪个指令错了，还告诉你第几行。比翻容器日志、`up` 了再等它退出，快十倍。

养成习惯：**改完任何 nginx 配置，先 `nginx -t`，再 reload/up。**

### 修法

把 `log_format` 从 `server {}` 里挪到文件顶部：

```nginx
# 文件顶层 = http 上下文
log_format main_ext '$remote_addr - [$time_local] "$request" '
                    '$status rt=$request_time urt=$upstream_response_time '
                    'body=$body_bytes_sent';

server {
    listen 80;
    ...
    access_log /var/log/nginx/lnmp_access.log main_ext;
    error_log  /var/log/nginx/lnmp_error.log warn;
    ...
}
```

顺手还要删掉一行：原配置里先写了 `access_log ... main;`，后面又写 `access_log ... main_ext;`。
**同一个文件用两种格式各写一遍，日志会重复且格式混乱。**

### 一句话记住

> **nginx 的指令有「允许出现的上下文」，写错位置不是「不生效」，是「拒绝启动」。**
> **所以 nginx 起不来的第一反应永远是 `nginx -t`，不是翻日志。**

### 面试怎么讲

**面试官会问**：nginx 容器起不来，你怎么查？

**答法**：**先分清 `Created` 和 `Exited`。**

`Created` 说明容器对象建好了但进程从未执行，`docker logs` 是空的——这时候查日志是白查，要去看 `up` 时的报错（端口分配、挂载、网络）。`Exited (1)` 说明进程跑过又退出，日志里一定有原因。

我遇到的这次先卡在 `Created`，第一反应是端口冲突，因为三个服务里只有 nginx 映射了宿主机端口。`ss -tlnp` 一查，8080 是空的，假设当场被否掉。重新启动后变成 `Exited (1)`，日志里写着 `"log_format" directive is not allowed here`。

**根因很反直觉**：`log_format` 只能写在 `http` 上下文，我把它写进了 `server {}`。
而 `conf.d/*.conf` 本来就是被 `http {}` include 的，**所以修法是把这段配置挪到文件最顶层，内容一个字都不用改**。

**关键一句**：**一个指令能不能用，不看它在哪个文件里，看它最终落在哪一层花括号内。**

**追问：那你怎么快速定位这类问题？**
`nginx -t`。它不光做语法检查，还做上下文检查，会直接给出文件名、行号、指令名。
这条命令三秒出结果，比 `up` 起来等它崩溃快得多。我现在改任何 nginx 配置都先跑它。

# 第九部分：测量方法的陷阱

## 23. 加了索引反而「没效果」

### 现象

项目二对 4 条慢查询做了索引优化，`bench.sh` 跑出来的对比是这样：

| 查询 | 优化前 | 优化后 | 看起来的结论 |
|---|---|---|---|
| Q1 用户订单分页 | 164 ms | 69 ms | 提升 2.4 倍，一般 |
| Q2 分组统计 | 183 ms | 90 ms | 提升 2 倍，一般 |
| Q3 范围 + 排序 | 161 ms | 145 ms | 几乎没变 |
| Q4 JOIN | 66 ms | **67 ms** | **完全没效果，甚至更慢** |

按这组数字，结论应该是：「索引只对少数查询有用，JOIN 优化失败」。

**但这组数字全是错的。**

### 关键线索：四个互不相关的查询，耗时收敛到同一个值

把表格重新排一下，只留优化后的数字：

```
Q1  69 ms
Q2  90 ms
Q3 145 ms
Q4  67 ms
```

注意到没有——**Q1 是「索引定位读 20 行」，Q4 是「JOIN 两张表」，两者的实际工作量差了几个数量级，
但测出来一个 69ms、一个 67ms，几乎一样。**

这就是异常信号。**当多个复杂度差异极大的查询耗时高度一致时，说明你测的不是查询，是别的东西。**

### 真相：测到的是 `docker exec` 的进程启动开销

`bench.sh` 原本这样计时：

```bash
S=$(date +%s%3N)
docker exec -e MYSQL_PWD=... lnmp-mysql mysql -uroot -N -B -e "$SQL"
E=$(date +%s%3N)
```

每一次测量要启动：`docker exec` → `runc` 进命名空间 → 启动 `mysql` 客户端 →
建连 + 认证 → 发 SQL → 取结果 → 退出。**2 核机器上这一套 30-70ms。**

打开 MySQL 自己的计时一看就露馅了：

```sql
EXPLAIN ANALYZE SELECT ...;
-- actual time=0.123..0.138
```

| 查询 | `docker exec` 墙钟 | 服务端 `actual time` | 差距 |
|---|---|---|---|
| Q1 优化后 | 69 ms | **0.11 ms** | 69 ms |
| Q4 优化前 | 66 ms | **0.677 ms** | 65 ms |
| Q4 优化后 | 67 ms | **0.138 ms** | 67 ms |

**Q4 的「67ms」里，真实的查询只占 0.138ms，剩下的 67ms 全是在启动进程。**

换句话说：**那条 JOIN 查询从头到尾都不是慢查询，它根本无从优化，也无须优化。**

### 后果：结论完全反了

| 表面数据 | 会得出的错误结论 | 服务端的真相 |
|---|---|---|
| Q1：164 → 69（2.4 倍） | 索引效果一般 | **133 → 0.11，约 1200 倍** |
| Q4：66 → 67（无变化） | 索引对 JOIN 无效 | **本来就 0.68ms，不需要优化** |

如果按表面数据写复盘，会得到一段完全错误的经验总结：
「复合索引对分页查询提升有限，对 JOIN 查询无效」——
**而事实恰恰相反，分页查询是 1200 倍的提升。**

**这就是最危险的地方：错误的测量不会报错，它会给你一份看起来很正常、逻辑也自洽的错误报告。**

### 定位：一句话判据

> **多个工作量差异极大的查询，耗时却收敛到同一个数值 —— 瓶颈在测量工具，不在被测对象。**

有了这个判据，连 `EXPLAIN` 都不用看就知道有问题。
再进一步：随便挑一条最简单的查询（比如 `SELECT 1`）测一下，
如果它也要 60ms，那就实锤了——**`SELECT 1` 不存在慢的可能**。

```bash
# 实锤实验：一条不可能慢的 SQL
time docker exec -e MYSQL_PWD='xxx' lnmp-mysql mysql -uroot -N -B -e "select 1"
# 输出接近 60-70ms → 这 60ms 就是固定开销
```

### 修法：以服务端计时为准

```sql
-- ① 最优：EXPLAIN ANALYZE（8.0.18+），服务端计时，还能看每个节点的耗时
EXPLAIN ANALYZE SELECT ...;
-- 最外层节点 actual time=开始..结束，第二个数是总耗时

-- ② 次优：performance_schema 直接读
SELECT TIMER_WAIT/1e9 AS ms FROM performance_schema.events_statements_history
ORDER BY TIMER_START DESC LIMIT 1;

-- ③ 可用：一次连接里跑 N 次，把固定开销摊薄
```

**`docker exec` + `date` 只适合粗筛**（判断是 10ms 还是 10s 级别），
**不适合精确对比，更不适合写进结论。**

### 换别的做法会怎样

| 方案 | 能否发现真实差异 | 代价 |
|---|---|---|
| `docker exec` + `date` | ❌ 0.1ms 级差异完全被淹没 | 零 |
| **`EXPLAIN ANALYZE` 的 `actual time`** | ✅ | 零，一条 SQL |
| `performance_schema` | ✅ 还能看历史 | 要开 `events_statements_history` |
| 在容器内直接跑 `mysql` | ⚠️ 省掉 `docker exec`，但仍有客户端启动开销 | 要 `docker exec -it` 进容器 |
| 压测工具（sysbench / mysqlslap） | ✅ 适合看 QPS | 配置成本高 |

### 一句话记住

> **多个无关查询耗时高度一致，说明你测的是工具，不是查询。**
> **先跑一条 `SELECT 1` 看看它的「耗时」——那就是你的开销底线。**

以及这个坑真正教会的事：

> **测量工具本身会成为被测系统的瓶颈，而它不会报错。**
> **所有「优化前后对比」的第一步，都是先证明你的尺子准。**

### 面试怎么讲

**面试官会问**：你说优化了慢查询，提升了多少？怎么测的？

**答法**：**先说测量方法，再说数字。**

「我最初用 `docker exec` 包一层 `date` 前后相减，测出来 4 条查询里 2 条有提升、
1 条几乎没变、1 条完全没变——JOIN 那条两轮都是 66 毫秒。

我没直接下结论，因为有个地方不对劲：**Q1 是索引定位读 20 行，Q4 是两张表 JOIN，
工作量差几个数量级，但测出来一个是 69ms、一个是 67ms，几乎一样。**
多个无关查询耗时收敛到同一个值，说明瓶颈在测量工具。

换成 `EXPLAIN ANALYZE` 看服务端耗时，Q4 实际只用了 **0.138 毫秒**——
那 67 毫秒全是 `docker exec` 启动进程的开销。而 Q1 从 133 毫秒降到 0.11 毫秒，
**不是 2.4 倍，是 1200 倍**。

**如果我拿最初的数字去写复盘，会得出「索引对 JOIN 无效」的错误结论，
而真实情况是那条查询本来就快，根本不需要优化。**」

**追问：那你怎么判断一次优化到底成没成功？**
先建立可信的度量：跑一条 `SELECT 1`，它的「耗时」就是固定开销底线。
低于这个量级的差异都不可信。然后再看服务端计时和 `EXPLAIN` 的 `type` / `Extra` 变化——
**指标变化比毫秒数更稳定**，`ALL` 变 `ref`、`Using filesort` 消失，这些是不会骗人的。

**关键一句**：**优化前后对比的第一步，是先证明尺子准。**

## 24. 恢复演练「0 秒成功」

### 现象

第一次跑备份恢复演练，脚本这样收场：

```
[22:06:02] 开始恢复...
ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: YES)
[22:06:02] 恢复完成，耗时 0s
[22:06:02] shop.orders 行数对比： 生产=300000  恢复后=
[22:06:02] [FAILED] 行数不一致或无法读取，备份可能有问题 ✘
```

三条证据摆在一起，第一反应是「备份文件坏了」。

### 关键线索：0 秒

8.3 MB 的全库备份，里面是 30 万行 orders。这个量级只做磁盘顺序写也要几秒。
**耗时 0 秒只有一种解释：管道里的数据根本没被消费**，`mysql` 客户端在建立连接
那一步就被踢回来了，后面的 SQL 一行都没执行。

而报错本身已经把方向说清楚了：`using password: YES` —— 密码发出去了，服务器不认。
如果真是备份文件损坏，报的会是 `ERROR 1064 (42000): You have an error in your SQL syntax`
之类。**连接层的错和 SQL 层的错，是两个完全不同的方向，不要混着查。**

### 真相：`mysqladmin ping` 分不清「活着」和「能用」

脚本判断临时库是否就绪，用的是：

```bash
if docker exec ... mysqladmin ping -uroot --silent; then
```

`mysqladmin ping` 的语义是 **「服务器有没有响应」**，不是 **「我能不能登录」**。
MySQL 官方文档写得很直接：

> The return status from mysqladmin is 0 if the server is running, 1 if it is not.
> This is 0 even in case of an error such as `Access denied`, because this means
> that the server is running but refused the connection.

**认证失败也返回 0。**

而 `mysql:8.0` 官方镜像启动不是「进程起来就能用」。entrypoint 的流程是：
先起一个带 `--skip-networking` 的**临时实例**执行初始化（建系统库、设 root 密码），
做完再关掉、重启正式实例。于是存在这样一个窗口：

| 阶段 | socket | root 密码 | `ping` | 带密码连 |
|---|---|---|---|---|
| 初始化中的临时实例 | 在听 | **还没设** | **0（成功）** | `Access denied` |
| 初始化完成的正式实例 | 在听 | 已生效 | 0 | 成功 |

脚本在「服务器有响应但密码还没生效」的那段窗口里就开导了。

修法一行：

```bash
mysql -uroot -e 'SELECT 1'     # 带密码真能跑一条 SQL，才算就绪
```

改完，就绪等待从 **0 秒** 变成 **16 秒**——**这 16 秒就是被 `ping` 漏掉的初始化时间**。
就绪时间突然变长不是变慢了，是之前测得太早。

### 次生陷阱：`TABLE_ROWS` 全是 0

旧脚本恢复完还打印了张表：

```
TABLE_SCHEMA   TABLE_NAME    TABLE_ROWS
shop           order_items   0
shop           orders        0
shop           users         0
```

紧接着下一行却是 `生产=300000  恢复后=300000`。**两行数字互相打脸。**

`information_schema.TABLES.TABLE_ROWS` 对 InnoDB 是**采样估算值**（默认抽样若干索引页），
不是 `COUNT(*)`。刚导入完统计信息还没重算，它就报 0。

**要精确数字一律 `COUNT(*)`；`TABLE_ROWS` 只能用来「大概看哪张表大」，
拿它做备份校验等于用一把没有刻度的尺子量长度。**

### 顺带修掉的两处

**（1）备份文件名日期重复**

`full_20261102_20261102_220546.sql.gz`——`DATE` 本身已经是 `%Y%m%d_%H%M%S`，
又拼了一个 `DAY`，日期出现两遍。改回 `full_${DATE}.sql.gz`。

**（2）临时库密码现在从生产容器读**

全量备份包含 `mysql` 系统库，恢复时会把 `mysql.user` 表一起还原，
`root@localhost` 的认证串被改写成生产库密码。如果临时库另用一个密码，
**恢复完就连不上了**——校验阶段读到空行数，看上去又像「备份坏了」。

所以临时库的 `MYSQL_ROOT_PASSWORD` 直接取生产值：

```bash
PROD_PASS=$(docker exec lnmp-mysql printenv MYSQL_ROOT_PASSWORD)
```

**恢复演练把系统库也恢复回来，这件事本身就意味着「演练环境」会被备份内容改写。**

### 一句话记住

> **`mysqladmin ping` 只证明服务器还活着，不证明你能进去。**
> **就绪判断要验到「能执行一条 SQL」，不是「端口能连」。**

### 面试怎么讲

**面试官会问**：你怎么确认备份是有效的？

**答法**：**先说演练方式，再说第一次是怎么失败的。**

「我写了恢复演练脚本：起一个临时 MySQL 容器，把最新全量备份灌进去，
然后对比生产库的行数。第一次跑就失败了，报 `Access denied`，而且**耗时 0 秒**。

0 秒是最关键的信号——8 MB 的库不可能 0 秒恢复完，0 秒说明数据根本没被消费。
如果是备份文件损坏，报的会是 SQL 语法错；报认证错，说明问题在连接阶段。

根因是我用 `mysqladmin ping` 判断容器就绪。这个命令**在认证失败时同样返回 0**，
因为它只问服务器有没有响应。而 mysql 官方镜像启动时会先起一个带 `--skip-networking`
的临时实例做初始化，那会儿 socket 已经在听、root 还没设密码——ping 通过，
但带密码连接被拒。**我等于在 MySQL 还没准备好的时候就开始导入了。**

改成 `mysql -uroot -e 'SELECT 1'` 之后，就绪等待从 0 秒变成 16 秒，
数据行数 300000 完全一致。

顺带还排掉一个干扰项：脚本打印的 `TABLE_ROWS` 三张表全是 0，看着像数据是空的，
其实那是 InnoDB 的估算值，刚导入完统计信息没更新。真实行数要用 `COUNT(*)`。」

**关键一句**：**「服务活着」和「服务可用」是两件事——健康检查必须验到业务层，
端口通、进程在、ping 有响应，这三样都不能证明服务真的能干活。**

## 25. 日志上限配了，磁盘还是在涨

### 现象

`daemon.json` 里早就写了：

```json
"log-driver": "json-file",
"log-opts": { "max-size": "20m", "max-file": "3" }
```

按道理每个容器最多占 60MB。但 `logs/nginx/lnmp_access.log` 几个小时就涨到 337KB，
而且**从来没有回落过**。项目二的日志目录是 `./logs/nginx` 和 `./logs/mysql`，
两个 bind mount。

### 关键线索：`docker inspect` 说配置是对的

```bash
docker inspect --format '{{.HostConfig.LogConfig}}' lnmp-nginx
# {"Type":"json-file","Config":{"max-file":"3","max-size":"10m"}}
```

配置完全正确，但文件在涨。**配置对 ≠ 管到了**——这两件事在这里根本不指向同一个对象。

### 真相一：日志有两个出口，Docker 只管前门

| 出口 | 位置 | 谁在写 | 谁负责轮转 |
|---|---|---|---|
| A. 容器 stdout/stderr | `/var/lib/docker/containers/<id>/<id>-json.log` | 进程 fd 1/2 | Docker 的 `max-size` |
| B. 应用写的文件 | `./logs/nginx/`、`./logs/mysql/` | 应用自己 `open()` | **没人** |

`max-size` 只作用于**容器标准输出的那一份拷贝**。而 nginx 的 `access_log /var/log/nginx/lnmp_access.log`
是 nginx 自己 open 的文件——虽然在容器内，但它落在 bind mount 上，**对 Docker 来说只是一堆宿主机普通文件**，
体积多大、要不要轮转，Docker 既不知道也不关心。

所以真正的形态是：**A 出口被管得死死的，B 出口完全敞开。**
配 `max-size` 就像给前门上了锁，然后把后门敞着。

修法是给 B 出口配 logrotate。**Docker 不负责的事，要用宿主机的工具补上。**

### 真相二：轮转方式必须匹配应用，不能照抄

B 出口配 logrotate 后，还有个更细的坑：**nginx 和 mysql 的轮转方式必须不同**。

| 应用 | 方式 | 原因 |
|---|---|---|
| nginx | `create` + `postrotate` 发 USR1 | 支持「重新打开日志文件」，连接不断 |
| mysql | `copytruncate` | **没有**重开日志的信号 |

如果 mysqld 也照抄 nginx 的 rename + create：logrotate 把 `slow.log` 改名成 `slow.log.1`、
新建一个空 `slow.log`，但 mysqld 手里握的还是**旧 inode**，继续往那个已改名的 `.1` 里写。

结果：`slow.log` 永远 0 字节，日志全堆在 `.1` —— **看着轮转成功，实际一个字节都没省。**

### 真相三：看到 `.1` 出现，不等于轮转成功

这是本坑最阴的一层。执行完 `logrotate -f`：

```text
lnmp_access.log      0 字节
lnmp_access.log.1    337087 字节
```

看起来完美。但如果 USR1 没送到，nginx 会继续写 `.1`，`.log` 永远 0——
**日志全丢了，而目录结构看起来完全正常。**

唯一的判定方法是**轮转后再发一次请求，看新建的文件长不长**：

```bash
curl -s -o /dev/null http://127.0.0.1:8080/
sleep 1
ls -l logs/nginx/lnmp_access.log*
tail -1 logs/nginx/lnmp_access.log
```

实测：

```text
lnmp_access.log      92 字节      ← ★ 新文件有新内容，USR1 生效
lnmp_access.log.1    337087 字节  ← 停止增长
```

那 92 字节正是轮转之后那次请求的记录。**这一条才是成功的证据，前面的文件名只是必要条件。**

### 修法汇总

1. **两层都配**：compose 里用 YAML 锚点给四个服务统一 `10m×3`（跟着代码走），
   `daemon.json` 留 `20m×3` 兜底（管手动 `docker run` 的临时容器）
2. **重建容器才生效**：日志配置在容器创建时写进 `HostConfig`，`restart` 没用，必须 recreate
3. **B 出口配 logrotate**：nginx 用 USR1 重开，mysql 用 `copytruncate`
4. **验证要验行为**：灌 40MiB 看总量是否卡在 `3 × max-size`；轮转后再发一次请求看新文件是否增长

### 一句话记住

> **`max-size` 管的是「容器说了什么」，不是「应用写了什么」。**
> **日志分散在两个出口时，只配一个出口等于没配。**

### 面试怎么讲

**面试官会问**：日志把磁盘写满了，怎么处理？

**答法**：**先分清两个出口，因为处理方式完全不同。**

「容器的 stdout/stderr 落在 `/var/lib/docker/containers/<id>/<id>-json.log`，这块归 Docker 的
`max-size` 管。但应用自己写进挂载目录的文件——nginx 的 `access.log`、mysql 的 `slow.log`——
Docker 完全不管，它只当那是宿主机上的普通文件。**只配 `max-size` 等于只锁了前门。**

我在 compose 里用 YAML 锚点给四个服务统一了 `10m×3`，让配置跟着代码走；
`daemon.json` 留 `20m×3` 做兜底，管住以后手动 `docker run` 的临时容器。
挂载目录那部分用 logrotate 按天 + 20M 轮转，留 7 份。

**这里有个不能照抄的地方**：nginx 能收 USR1 重新打开日志文件，所以用 rename + create；
mysqld 没有这个信号，只能 `copytruncate`——先复制再截断。如果给 mysql 也配成 rename + create，
它会一直写那个已被改名的旧文件，**新的 `slow.log` 永远是 0 字节，看着轮转成功但一个字节都没省。**

验证也分两层：`docker inspect` 看配置对不对，起临时容器灌 40MiB 看总量是不是卡在 30M 附近。
nginx 那边不能只看 `.1` 出现，必须再发一次请求，看**新建的 `.log` 有没有新内容**——
如果 USR1 没送到，日志会全丢在 `.1` 里，而目录结构看起来完全正常。」

**关键一句**：**「配置生效」和「问题解决」之间隔着一次行为验证；
只看配置文件，你永远不知道信号有没有送到。**

# 第十部分：把 25 个坑压缩成 5 条心法

## 心法 1：先分层，再动手

排查任何问题，按这个顺序走，**不要跳层**：

```
① 容器/进程活着吗        docker compose ps -a / systemctl status
② 端口在听吗、地址对吗    ss -tlnp
③ 网络通吗               curl / nc / docker network inspect
④ 应用日志说什么          docker logs / error.log
⑤ 数据层                 连得上吗、状态对吗
⑥ 系统资源               CPU / 内存 / 磁盘 / fd
```

跳层的代价：在第 ③ 层折腾半小时，最后发现是第 ① 层容器根本没起来。

## 心法 2：先确认「信息在哪」，再开始查

不同组件的日志出口不一样：

| 组件 | 日志在哪 |
|---|---|
| 容器主进程 stdout | `docker logs` |
| MySQL（配了 log_error） | **文件**，`docker logs` 看不到 |
| nginx（配了 error_log） | 文件，`docker logs` 只有启动期的 emerg |
| cron | `/var/log/cron` + 脚本自己重定向的文件 |
| 内核 | `dmesg` |

**「查不到日志」本身就是一条线索**——说明日志被重定向了，或者采集组件被关了。

## 心法 3：「没报错」≠「没问题」

本项目里最危险的两个 bug 都属于这类：

- `Seconds_Behind_Master` 字段改名 → **延迟检查静默失效**
- `/health` 返回 HTML 但状态码 200 → **前端解析失败，看起来像后端挂了**

共同点：**没有异常日志，功能却是坏的**。

对策：
- 关键检查要**做故障注入**验证（停掉服务，看告警响不响）
- 验证要看**内容**而不只看状态码（`curl -i`、`Content-Type`）
- 监控脚本要有**自检**（比如「延迟取到空值」本身就该告警）

## 心法 4：顺序敏感的操作，先想「谁有副作用」

| 操作 | 副作用 |
|---|---|
| `DROP DATABASE` | 产生一个 GTID |
| `docker compose up` | 创建容器、注册 DNS（有先后） |
| `nginx -s reload` | 不断连接，但**改监听端口必须 restart** |
| `RESET MASTER` | 清空 binlog 和 gtid_executed（不可逆） |
| `docker compose down -v` | **删数据卷** |

**凡是不可逆的，先备份；凡是有副作用的，先想清楚顺序。**

## 心法 5：改完必须重跑，别信「应该好了」

`health_check.sh` 的 IP bug 藏了一整天。那天的「告警成功」其实是**一半正确**：
容器异常的告警发出去了，节点 HTTP 检查却是坏的，只是没人注意。

每次修完，至少验证三件事：

```bash
1. 原来失败的那个现象，现在成功了吗    ← 正向验证
2. 原来正常的功能，还没坏吗            ← 回归验证
3. 异常场景下，还能正确报错吗          ← 反向验证
```

# 第十一部分：怎么把这份文档变成你的

## 三遍法

**第一遍：只读「现象 + 原理」**
遮住修法，问自己：*如果是我，会往哪查？* 想不出来再看。

**第二遍：挑 3 条讲成故事**
按「我以为是 X → 看到 Y 线索 → 想明白是 Z → 所以这么修」的结构口述。
讲不顺 = 没真懂。

**第三遍：回服务器复现**
最容易复现的六条：

| 坑 | 怎么复现 | 花多久 |
|---|---|---|
| **#17 脚本跑不起来** | 在 `/opt/ops` 敲 `bash scripts/failover_drill.sh` → 看是「文件」找不到还是「目录」找不到；再 `curl --version` 看是否 < 7.83 | **5 秒** |
| **#16 `--exclude` 无效** | `cd /opt/ops && tar cf /dev/null -C /opt/ops project1-cluster --exclude='project1-cluster/logs'; echo $?` → 立刻看到 `has no effect` + 退出码 2 | **10 秒** |
| **#18 假失败** | 停一个节点后跑 `curl -m 3` 和 `curl -m 8` 各一次，对比状态码；再 `docker exec lb tail -20 /var/log/nginx/lb_access.log` 找 499 | **20 秒** |
| **#19 两种超时分不清** | `docker stop` 看日志是 `while connecting`；`docker pause` 看日志是 `while reading`——同一个「超时」，两个阶段 | 1 分钟 |
| #5 `/health` 返回 HTML | 临时把 `location = /health` 注释掉，reload，`curl -i` 看头 | 2 分钟 |
| #6 轮询奇偶 | 在页面控制台连续 `fetch('/whoami')` 4 次看结果 | 2 分钟 |
| #13 cron PATH | 建个测试任务 `* * * * * docker ps`，不写 PATH，看日志 | 5 分钟 |
| **#24 `ping` 谎报存活** | `docker exec -e MYSQL_PWD=错的密码 lnmp-mysql mysqladmin ping -uroot --silent; echo $?` → **照样输出 0** | **5 秒** |

**#17 排最前，因为它 5 秒就能撞一次，而且每一次换机器都会重演。**
**#16 紧随其后，10 秒能复现，却是本仓库里我猜错次数最多的一个。**
**#18 只花 20 秒，但它是这 19 条里唯一一条「你量到的数据在骗你」**——
前面 17 条都是「东西坏了」，只有它是「东西没坏，是尺子坏了」。
**#19 是唯一一条「越努力越错」的**——方向判错以后，你调的每一个参数都在加深误解。

复现成本低、认知成本高——这种坑最值得亲手撞一次。

**动过手的那一条，面试时你能说出细节；只看过的那一条，一追问就露馅。**

## 复盘模板（每次新故障都填）

```
【现象】  一句话，带上关键报错原文
【影响】  哪些功能不可用，持续多久
【定位】  我看了什么 → 排除了什么 → 锁定什么
【根因】  机制层面的解释（不是"配置错了"这种废话）
【修复】  改了什么，为什么这么改
【验证】  正向 / 回归 / 反向 三个结果
【预防】  怎么让同类问题下次能被更早发现
```

最后一项「预防」是分水岭——**大多数人只做到「修复」，能做到「预防」的才是运维思维**。

## 面试时的黄金结构

不要说「我遇到过 XX 问题，改了个配置就好了」。要说：

> 「现象是 XXX。我一开始以为是 A，但看到 B 线索就排除了——
> 因为如果是 A 的话，C 也应该异常。继续查发现根因是 D（这里讲机制）。
> 修法是 E，之所以不选 F 是因为 G。修完我做了三件事验证：
> 正向、回归，还有故意造一次故障看告警会不会响。」

**这段话里有：现象、假设、排除、机制、取舍、验证。** 六样齐全，就是 L3。
