## D2 · 起项目一集群（1 小时）

### 步骤 2-1：进目录 + 准备日志目录权限

```bash
cd /opt/ops/project1-cluster

# ★ 必须做：mysqld 以 uid 999 运行，挂载出来的日志目录属主不对会直接起不来
mkdir -p logs/{mysql-node1,mysql-node2,nginx-lb,nginx-node1,nginx-node2}

ls -ld logs/mysql-node1
```

**预期**：`drwxr-xr-x. 2 999 999 ...`
对不上（显示 root）→ chown 没执行成功，确认你在正确的目录下。

### 步骤 2-2：拉镜像（先单独拉，能看清卡在哪）


> ★ **镜像名一律写官方原名，不要加任何域名前缀**。
> 加了前缀就等于绕过了已配好的 `registry-mirrors`，把自己锁死在单个源上 ——
> 那正是我之前拉不到镜像的真正原因（详见 `03-Docker镜像与加速源.md`）。
> 拉不动先按该文档排查，不要改镜像名。

### 步骤 2-7：卡住了怎么办

| 症状 | 排查命令 | 处理 |
|---|---|---|
| 容器一直 `(health: starting)` | `docker logs node1-db --tail 30` | 多半是初始化中，再等等；超 3 分钟就查日志 |
| `node1-db` 反复 Restarting | `docker logs node1-db --tail 50` | 见下方三条 |
| 报 `Errcode: 13` | — | 日志目录属主 → 回到步骤 2-1 做 chown |
| 报 `unknown variable` | — | my.cnf 参数问题 → `mysql/master.cnf` 里注释掉报错的参数 |
| 报 `Address already in use` | `ss -tlnp \| grep :80` | 端口占用 → kill 掉占用进程 |
| 报 `Pool overlaps` | — | 见下方"网段冲突" |
| `curl` 返回 502 | `docker logs lb --tail 20` | 后端没起来，按上面逐项查 |

**网段冲突**（腾讯云内网用了 172.16/12 时会撞车）：
```bash
# 报错信息：Pool overlaps with other one on this address space
# 改掉四个网段，比如改成 10.20/10.21/10.22/10.23
sed -i 's/172\.20\.0/10.20.0/g; s/172\.21\.0/10.21.0/g; s/172\.22\.0/10.22.0/g; s/172\.23\.0/10.23.0/g' docker-compose.yml
# 注意 nginx/lb.conf 里的 allow 172.20.0.0/24 也要跟着改
sed -i 's|allow 172.20.0.0/24|allow 10.20.0.0/24|' nginx/lb.conf
docker compose down && docker compose up -d
```


### 步骤 4-5：★ 验证 cron 真的会触发（新手 90% 栽在这里）

```bash
# 临时改成每分钟，验证完再改回去
crontab -l | sed 's|\*/5|\*|' | crontab -
sleep 70
tail -3 /opt/ops/logs/scripts/health-cron.log

# ★ 验证完记得改回 5 分钟
crontab -l | sed 's|^\* \* \* \* \*|*/5 * * * *|' | crontab -
crontab -l | grep health
```

**cron 不执行的三大原因**（背下来，面试常问）：
1. **环境变量**：cron 的 PATH 极短 —— 所以 crontab 第一行必须写 `PATH=...`
2. **CRLF 换行**：Windows 编辑过的脚本在 Linux 上直接报 `bad interpreter: /bin/bash^M`
3. **没有执行权限**：`chmod +x`
4. 还有一个：**脚本用了相对路径**，cron 的工作目录是用户的 home，不是脚本所在目录

```bash
# 看 cron 到底执行了没
journalctl -u crond --since "10 min ago" | tail -20
# 或
grep CROND /var/log/cron | tail -10
```

### 步骤 4-6：★ 做一次备份恢复演练

> **备份没验证过恢复，等于没备份。** 这一步不做，前面全白干。
>
> ⚠️ 注意：dump 是 `--all-databases`，里面带 `CREATE DATABASE shop; USE shop;`，
> **直接往生产库导入会覆盖真实数据**。所以必须用**临时容器**隔离。
> （在临时容器里 `--force` 是安全的——那里本来就是空的。）

```bash
# ① 先看内存够不够（2G 机器必须看，Restore 容器约需 300~400MB）
free -h

# ② 先清掉可能残留的同名容器（★ 不删会踩「密码不对」的坑，见下方说明）
docker rm -fv restore-test 2>/dev/null

# ③ 起临时容器：★ 限内存 + 压小 buffer pool，避免把宿主机拖垮
#    密码用纯字母数字：带 @ # 等字符在命令行/URL 里容易被二次解析
docker run -d --name restore-test \
  --memory=400m \
  -e MYSQL_ROOT_PASSWORD=Restore123 \
  mysql:8.0 --innodb-buffer-pool-size=64M

# ④ 轮询等就绪（初始化要 40~60 秒，固定 sleep 不可靠）
#    ★ 用 SELECT 1 探测，不要用 mysqladmin ping——
#      ping 只问「进程在不在」，密码错了它照样回 "mysqld is alive"，会误判就绪
for i in $(seq 1 60); do
  docker exec restore-test mysql -uroot -pRestore123 -e "SELECT 1" >/dev/null 2>&1 \
    && { echo "就绪，用时 $((i*2))s"; break; }
  sleep 2
done

# ⑤ 导入（--force 跳过 dump 里的重复建库报错）
zcat "$(ls -t /opt/ops/backup/mysql/mysql_*.sql.gz | head -1)" \
  | docker exec -i restore-test mysql -uroot -pRestore123 --force

# ⑥ 关键验证：表数量 + 数据量，要和主库对得上
docker exec -e MYSQL_PWD=Restore123 restore-test mysql -uroot -e "
  SELECT COUNT(*) AS tables_count FROM information_schema.tables WHERE table_schema='shop';
  SELECT COUNT(*) AS orders_count FROM shop.orders;"
```

> **为什么必须先删同名容器**：镜像里的 `MYSQL_ROOT_PASSWORD` **只在数据目录首次初始化时生效**。
> 如果同名容器已经存在（或复用了旧数据目录），你再传这个环境变量会被**静默忽略**，
> 容器里还是老密码。表现就是 `ERROR 1045 (28000): Access denied for user 'root'@'localhost'`。
> 这不是权限问题，也不是网络问题——**是密码根本不是你以为的那个**。

**把上面的数字和主库对比**，对得上才叫恢复成功：

```bash
docker exec -e MYSQL_PWD='Root@123456' node1-db mysql -uroot -e "
  SELECT COUNT(*) AS tables_main FROM information_schema.tables WHERE table_schema='shop';
  SELECT COUNT(*) AS orders_main FROM shop.orders;"
```

```bash
# ⑦ 收工，删掉临时容器（一定要删，400MB 内存别白占）
#    -v 连匿名卷一起删，否则下次重建可能又复用到旧数据目录（→ 1045）
docker rm -fv restore-test
```

**预期**：两边的 `tables` 和 `orders` 数量一致。不一致说明备份本身有问题，
或者备份时间点和现在隔着数据（比如你刚下了新订单）。

## D5 · 故障演练与复盘（一整天，这是简历的核心产出）

> **这一天是整套方案里最值钱的一天。**
> 故障不会自己送上门，你得亲手造出来，再亲手查出来。

### 步骤 5-1：LB 摘除演练

**先进项目目录**（本手册从 D2 起的所有命令都以 `/opt/ops/project1-cluster` 为当前目录）：

```bash
cd /opt/ops/project1-cluster
ls -l scripts/failover_drill.sh          # 先确认文件在
bash scripts/failover_drill.sh node1-web 20
```

> **只写 `bash scripts/failover_drill.sh` 会报 `No such file or directory`**，
> 因为仓库根目录 `/opt/ops` 下**也有一个 `scripts/`**（里面只有 `mirror_probe.sh`），
> 所以你不会看到「目录不存在」，而是「文件不存在」——更容易误判。
> 脚本已改成自定位（内部 `cd` 到自己的上级目录），但**调用路径必须写对**。

**预期**：停掉 node1 后，20 次请求全部返回 200，且都打到 node2；恢复后两个节点重新交替。

脚本会先做三项前置检查（lb 在跑 / 目标容器在跑 / 响应头可读），任一项不过就中止——**避免演练跑完才发现结果是假的**。

#### 5-1a：先看清楚「切换要几秒」

跑完看这一行统计：

```
统计：20 次 / 失败 0 / 超 1s 2 / 最慢 1005ms / 全程 6s
    最后一次慢请求在第 4 次 —— 说明摘除在第 4 次请求后完成
```

**理想结果是「失败 0、超 1s 2」**，也就是只有 2 次请求变慢，没有任何请求失败。
这 2 次慢是必然的：轮询隔一次才轮到死节点，而摘除需要连撞 2 次。

如果 `失败` 不是 0，**先别改 nginx**，先看失败耗时：

| 失败耗时 | 谁放弃了 | 怎么办 |
|---------|---------|-------|
| ≈`DRILL_TIMEOUT`×1000 ms | curl 自己超时 | 调大脚本超时，你测的是自己 |
| ≈1000 ms | nginx 在等 `proxy_connect_timeout` | 属正常，只是慢 |
| < 50 ms | 后端立刻拒绝（502） | 查 upstream / 容器端口 |

> 这一条是真实踩过的坑：**`curl -m 3` 和 `proxy_connect_timeout 3s` 撞在一起时，
> 20 次里会有 9 次「失败」，但 LB 其实一次都没出错**——客户端先断开、nginx 记 499、
> 被掐断的请求还不计入 `max_fails`，于是节点永远摘不掉，形成假故障循环。
> 完整推导见 `docs/08-踩坑与修复记录.md` 第 18 坑。

#### 5-1b：确认摘除窗口的公式

```
摘除需要多久 = max_fails × proxy_connect_timeout
```

本项目配置（`nginx/lb.conf`）：

```nginx
server node1-web:80 max_fails=2 fail_timeout=10s;
proxy_connect_timeout 1s;
```

→ 窗口 = `2 × 1s = 2 秒`。改完 reload 再跑一次，确认最慢值从 3005ms 降到 ~1005ms：

```bash
docker exec lb nginx -t && docker exec lb nginx -s reload
bash scripts/failover_drill.sh node1-web 20
```

> **为什么容器死掉后不是「秒级发现」**：`docker stop` 会把容器在网桥上的 IP 一起撤掉，
> 发过去的 SYN 既不回 RST 也不回 ICMP，**直接消失**。nginx 没法靠「连接被拒」立即感知，
> 只能傻等到 `proxy_connect_timeout`。所以这个超时值直接决定故障切换有多快。
