状态：🟡 5/6 达标（仅 `PermitRootLogin` 待收紧）

#### 为什么 `kbdinteractiveauthentication` 这条不能漏

只关 `PasswordAuthentication` **不等于**禁用密码登录。SSH 还有第二条能输密码的路径——
PAM 的键盘交互认证。攻击者用这条命令就能绕过去：

```bash
ssh -o PreferredAuthentications=keyboard-interactive root@IP
```

**两条都设 `no`，密码路径才算真的堵死。** 很多加固教程只写第一条，
于是机器看起来「已禁用密码登录」，实际上密码还能用。

#### 待办：`PermitRootLogin yes` → `prohibit-password`

当前值 `yes` 允许 root 以任何方式登录。因为 `passwordauthentication no` 是全局生效的，
**眼下 root 其实不能用密码登录**，所以这不是一个正在被利用的漏洞，而是**纵深防御少了一层**：

> 只要哪天有人为了临时排障把 `PasswordAuthentication` 改回 `yes`，
> root 就会立刻变成可爆破对象 —— 而 root 是最值得爆破的账号。

收紧后不影响现有用法（仍然可以用密钥直接登 root），只是把「root + 密码」这条路径焊死。

```bash
# ① 先确认最终生效的是哪个文件（sshd_config.d/ 里的优先级更高）
grep -rn 'PermitRootLogin' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/ 2>/dev/null

# ② 备份
cp -a /etc/ssh/sshd_config /etc/ssh/sshd_config.bak.$(date +%F)

# ③ 改（若 ① 显示 drop-in 文件里也有，改那个）
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config

# ④ 校验语法，必须无输出
sshd -t

# ⑤ reload（不断开现有连接）
systemctl reload sshd

# ⑥ 复验
sshd -T | grep -i permitrootlogin
```

> ⚠️ **改 SSH 配置前先确认云控制台的 VNC 登录可用**。这是唯一能在配错后救回你的通道。
> 改完**不要关掉当前会话**，另开一个窗口测试密钥登录成功后再关。
> 顺序错了会把自己锁在门外，而这个项目里的数据都在那台机器上。

### B2-2. 故障切换要几秒（★ 简历上「高可用」的真实数字）

```bash
cd /opt/ops/project1-cluster
docker stop node2-web && sleep 2
for i in $(seq 1 6); do
  curl -s -o /dev/null -m 8 -w "第${i}次 code=%{http_code} 耗时=%{time_total}s\n" http://127.0.0.1/whoami
done
docker start node2-web
```

> `-m 8` 不是「等更久」，是**让 nginx 把重试做完**。客户端超时必须大于
> `proxy_connect_timeout`，否则测到的是自己放弃（详见踩坑 #18）。

**预期**：全部 `200`，前 2 次各约 1 秒（`proxy_connect_timeout`），之后恢复到毫秒级。

**实测记录（2026-10-27，优化前 `proxy_connect_timeout 3s`）**：
```
第1次 code=200 耗时=0.000818s
第2次 code=200 耗时=3.005635s   ← 撞上死节点，卡满 connect timeout
第3次 code=200 耗时=0.000653s
第4次 code=200 耗时=3.005429s   ← 第二次撞击，max_fails=2 达成 → 摘除
第5次 code=200 耗时=0.000653s   ← 从此只走存活节点
第6次 code=200 耗时=0.000616s
```

**结论**：切换全程 `2 × 3s = 6 秒`，期间**零错误**（全部 200），只是 2 次请求慢 3 秒。
公式：`切换窗口 = max_fails × proxy_connect_timeout`。

**优化后（`proxy_connect_timeout 1s`）预期**：窗口降到 2 秒，最慢值从 3005ms → ~1005ms。

#### 注 ①：场景 1 的原手册做法在本机不成立

手册写的是「先 `python3 -m http.server 80` 抢占，再重启 lb」，但**本机 80 端口已经被
lb 容器占着**，假服务根本起不来。正确顺序要反过来：

```bash
cd /opt/ops/project1-cluster
docker compose stop lb                                    # 先释放 80
python3 -m http.server 80 >/tmp/fake80.log 2>&1 & echo $! > /tmp/fake80.pid
docker compose up -d lb                                   # 再启动，触发冲突
```

**预期报错**：`Bind for 0.0.0.0:80 failed: port is already allocated`

**关键观察点**：容器会停在 `Created` 状态，而 **`docker logs lb` 是空的**。
这不是「没有日志」，而是**进程从未启动过**——Docker 在创建网络命名空间阶段就失败了。
区分「没有日志」和「没启动过」，是容器排障的基本功。

```bash
# 排查三步
ss -tlnp | grep ':80'                                      # 谁占的
ps -fp $(ss -tlnp | grep ':80' | grep -oP 'pid=\K[0-9]+' | head -1)
docker ps --format '{{.Names}}\t{{.Ports}}' | grep ':80'   # 排除 docker-proxy

# 修复
kill $(cat /tmp/fake80.pid) && docker compose up -d lb
```

> 端口占用分两种来源：**宿主机普通进程**（`kill`）和**另一个容器经 docker-proxy 转发**
> （`docker rm -f`）。多花 5 秒确认一次，能避免杀错人。

#### 注 ②：场景 3 必须用 loop device，不能写满根分区

2C2G / 40G 的机器写满 `/` 会导致 MySQL 崩溃、日志写不进去、SSH 可能卡死，恢复代价大。
用独立小分区演示，**排查手法一个都不少，风险为零**：

```bash
dd if=/dev/zero of=/opt/ops/tmpdisk.img bs=1M count=100
mkfs.ext4 /opt/ops/tmpdisk.img
mkdir -p /mnt/drill && mount -o loop /opt/ops/tmpdisk.img /mnt/drill
dd if=/dev/zero of=/mnt/drill/fill bs=1M count=200 2>&1 | tail -2   # 必然 No space left
df -h /mnt/drill        # 分区满了
df -i /mnt/drill        # ★ inode 满了是另一种情况：df -h 有空间但就是写不进
du -sh /mnt/drill/* | sort -rh | head
lsof +L1                # ★ 文件已删除但进程仍持有句柄 —— 最隐蔽的磁盘泄漏

rm /mnt/drill/fill && umount /mnt/drill
```

`df -i` 和 `lsof +L1` 这两条是磁盘排查里最容易漏的：
前者解释「明明有空间却写不进去」，后者解释「删了文件空间却没释放」。
**排查能力的重点是「怎么定位」，不是「把机器弄坏」。**

### C3. ★ 慢 SQL 优化前后对比（这是简历上那条的核心证据）

```bash
bash scripts/bench.sh before          # 优化前跑一次，记下耗时
# 施加索引（见 sql/optimize.sql）
bash scripts/bench.sh after           # 优化后再跑一次
```

**实测记录（2026-11-02，orders 30 万行 / buffer_pool 256M）**

下表耗时均为 **`EXPLAIN ANALYZE` 的服务端 `actual time`**，不是 `docker exec` 墙钟时间：

| 查询 | 优化前 | 优化后 | 提升 | 备注 |
|---|---|---|---|---|
| Q1 用户订单分页 | 133 ms | **0.11 ms** | **约 1200 倍** | 全表扫 30 万行 → 索引定位读 20 行 |
| Q2 分组统计 | 145 ms | 65.8 ms | 2.2 倍 | 覆盖索引免回表，但要扫 6 万行，收益有天花板 |
| Q3 范围 + 排序 | 125 ms | 101 ms | 仅 1.24 倍 | **排序仍走 filesort**，索引解决不了 |
| Q4 JOIN | 0.677 ms | 0.138 ms | 无意义 | **本来就快，不需要优化** |

`EXPLAIN` 关键变化：

| 查询 | type | key | Extra |
|---|---|---|---|
| Q1 前 → 后 | `ALL` → `ref` | 无 → `idx_orders_user_status_created` | `Using filesort` → `Using index condition` |
| Q2 前 → 后 | `ALL` → `ref` | 无 → `idx_orders_status_user_amount` | `Using temporary; Using filesort` → **`Using index`** |
| Q3 前 → 后 | `ALL` → `range` | 无 → `idx_orders_city_created` | `Using filesort` → **仍有 `Using filesort`** |
| Q4 后 | `ref` / `ref` | `idx_users_city` + `idx_orders_status_user_amount` | `o` 表 **`Using index`**，rows=11 |

**这一项最有价值的不是「快了多少」，而是三个「没有变快」的结论**：

1. **Q2 只有 2.2 倍**：索引减少的是回表和无效行扫描，**减少不了必须扫的行数**。聚合类查询命中比例高时，索引的天花板很明显，真正的解法是预聚合
2. **Q3 只有 1.24 倍**：范围条件之后的列在 B+ 树里无序，`ORDER BY amount` 必须 filesort。**这条查询索引解决不了**，得改语义或加缓存
3. **Q4 本来就不慢**：服务端 0.677 ms，驱动表仅 5005 行 + `LIMIT 20` 提前终止。**判断出「不需要优化」也是能力**

> ⚠️ **初版 bench.sh 的计时方式是错的**：用 `docker exec` 外面包 `date` 相减，
> 把进程启动开销（30-70 ms）算进了查询耗时。结果 Q4 两轮都显示 66-67 ms，
> 得出「加索引无效」的错误结论——实际服务端只用 0.68 ms。
> 详见 `project2-lnmp/docs/SQL优化记录.md` 的「测量方法的坑」。
> **多个无关查询耗时高度一致，就是瓶颈在测量工具的信号。**

### C4. 备份 + 恢复演练

```bash
bash scripts/mysql_backup.sh      # 全库 + 分库，gzip，保留 7 天
bash scripts/restore_test.sh      # 起临时容器灌进去，校验一致
```

**实测记录（2026-11-02 22:11）**

| 项 | 数值 |
|---|---|
| 备份文件 | `full_20261102_220546.sql.gz`，**8.3 MB**（全库含 30 万行 orders） |
| 临时容器 | `mysql:8.0`，`--memory 512m`，`--innodb-buffer-pool-size=64M` |
| 初始化等待 | **16 秒** |
| 恢复耗时 | **17 秒** |
| 校验结果 | `shop.orders` 生产 **300000** / 恢复后 **300000**，一致 ✔ |

**第一次跑是失败的**，而且失败得很典型：

```
[22:06:02] 开始恢复...
ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: YES)
[22:06:02] 恢复完成，耗时 0s
[22:06:02] shop.orders 行数对比： 生产=300000  恢复后=
```

两个数字直接定性：

1. **耗时 0s** —— 8.3 MB 的库不可能 0 秒恢复完。0 秒不是「快」，是**一条都没导进去**
2. **`using password: YES`** —— 密码发出去了但被拒，说明问题在连接阶段，跟备份内容无关

根因：脚本用 `mysqladmin ping` 判断临时库是否就绪，而 **`mysqladmin ping` 在认证失败时同样返回 0**（它只问服务器有没有响应，不问你能不能登录）。于是脚本在 MySQL 初始化还没结束、root 密码尚未生效时就开导，第一条语句被踢回来。

改成「带密码能真正执行一条 SQL」才算就绪：

```bash
mysql -uroot -e 'SELECT 1'    # 替代 mysqladmin ping -uroot --silent
```

就绪等待从 0 秒变成 16 秒——**这 16 秒就是被 `ping` 漏掉的那段初始化时间**。

> ⚠️ 顺带排掉一个容易误判的干扰项：旧脚本打印的 `TABLE_ROWS` 三张表全是 **0**，
> 看起来像「数据是空的」。实际 `information_schema.TABLES.TABLE_ROWS` 对 InnoDB
> 只是**采样估算值**，刚导入完统计信息还没更新就报 0。判读必须用 `COUNT(*)`。
> 完整复盘见 `docs/08` 第 24 坑。

### C5. ★ Redis 缓存 + 压测（简历上「QPS 提升」那条的证据）

**缓存生效的直接证据**（连发三次，第一次回源、之后命中）：

```bash
for i in 1 2 3; do curl -s http://127.0.0.1:8080/ | grep -oE 'HIT 命中缓存|MISS 回源|BYPASS 强制回源'; done
```

**压测对比**：

```bash
docker run --rm --network host httpd:2.4-alpine ab -n 500 -c 20 "http://127.0.0.1:8080/?nocache=1"
curl -s http://127.0.0.1:8080/ > /dev/null
docker run --rm --network host httpd:2.4-alpine ab -n 500 -c 20 "http://127.0.0.1:8080/"
```

| 组 | QPS | 单请求延迟(mean) | 服务端耗时 | 取数耗时 |
|---|---|---|---|---|
| A 强制回源 | 12.62 / 12.63 | 1585 / 1583 ms | 79.2 / 79.1 ms | 58 ms |
| B 走缓存 | **819.74 / 793.93** | 24.4 / 25.2 ms | 1.22 / 1.26 ms | **0.45 / 0.07 ms** |

- **QPS 提升约 63 倍**，两组各跑两次，数字可复现
- `Failed requests` 的 486 / 151 **全部是 `Length`**（响应长度因 session ID、实时耗时而不同），
  `Connect` / `Receive` / `Exceptions` 均为 0，且无 `Non-2xx responses` —— **没有真实的 4xx/5xx**

**瓶颈分析**：A 组慢在 58ms 的重复聚合计算（`1000 ÷ 79 ≈ 12.6` 可反推验证）；
B 组瓶颈转移到 PHP-FPM 的 `pm.max_children=8` 与 2 核 CPU，
QPS 不会随缓存线性增长。

### D2. 服务器重启后能自愈

**前置改动（2026-11-03）**：重启验证前先补掉了两个真实缺陷——

```yaml
# docker-compose.yml（四服务统一）
restart: unless-stopped
mem_limit: 768m   # mysql；nginx 128m / php 384m / redis 96m
```

改动前的状态：nginx/php/mysql 三个服务 `restart=no`、`mem_limit=0`——
**服务器重启后网站直接躺平**，且任何一个内存失控都可能把整机拖进 swap
（重启前 swap 已被吃掉 256M，就是证据）。

**内存预算的算法**：按「配置允许的理论峰值」算，不按当前 RSS——

| 服务 | 依据 | 上限 |
|---|---|---|
| mysql | `innodb_buffer_pool` 256M + `log_buffer` 16M + 基础 ~200M + 连接 | 768m |
| php | `pm.max_children=8` × ~30M + master 20M | 384m |
| nginx | worker + buffer | 128m |
| redis | `maxmemory 64m` + 开销 | 96m（原有） |
| **合计** | | **1376M** |

1376M + 系统常驻 295M（dockerd 76 + YDService 69 + firewalld 25 + containerd 22
+ barad 16 + 内核）= **1671M / 1975M，余量 15%**。
系统常驻里的 `YDService`/`barad_agent` 是腾讯云组件，删不掉，必须算进预算。

**实测记录（2026-11-03）**

```bash
reboot
# 重连后（未执行任何 docker 命令）：
docker ps --format 'table {{.Names}}\t{{.Status}}'
curl -s -o /dev/null -w 'HTTP %{http_code}\n' http://127.0.0.1:8080/
docker exec -e MYSQL_PWD=... lnmp-mysql mysql -uroot -N -B -e \
  "SELECT COUNT(*) FROM shop.orders;"
docker stats --no-stream --format 'table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}'
```

| 验证项 | 结果 |
|---|---|
| 容器自动拉起 | **4 个全部 `Up 18 minutes`**，未手动干预 |
| 服务可用 | HTTP **200** |
| 数据完好 | `shop.orders` = **300000** |
| 内存上限生效 | `docker stats` 的 LIMIT 列：`128MiB / 384MiB / 768MiB / 96MiB`（不再是统一的 1.929GiB） |
| Swap | 重启前已用 256M → 重启后 **0** |

**两个值得记的验证细节**：

1. **`live-restore: true` 会让 `systemctl restart docker` 验不了 restart 策略**——
   该选项让 daemon 停止时容器继续运行，容器根本不停，策略没机会触发。
   看到容器还在就以为验证通过，是这一步最常见的假阳性。**必须 reboot。**
2. **`docker stats` 的 LIMIT 列就是 cgroup 里的实际限制值**，它变成 128MiB/384MiB/768MiB
   的那一刻，等于 `inspect` 验证过了——配置写入和运行时生效是同一个证据。

**遗留**：用临时容器灌爆内存验证 OOM Kill（`--memory=64m` + 往 tmpfs 写 200M，
预期退出码 137）没跑，cgroup 限制已由 LIMIT 列证实，这项属于锦上添花。

状态：✅ 已通过

### E6. ★ 采集断流能被发现（push 架构的命门）

```bash
# 停掉 cron 里的采集任务，观察 2 小时后是否出现「采集断流」告警
crontab -l | grep -v host_checks.sh | crontab -
```

cron 一挂，这个值会永远停在最后一次的正常值上，前三条**全部判定正常**——
**监控自己瞎了，界面上却显示一切健康**。只有 `nodata()` 是在问「还活着吗」。

  `lag=0 / running=1 / backup_age=3xxx`，全是旧值。这个「安静的假象」正是本条验收存在的理由
