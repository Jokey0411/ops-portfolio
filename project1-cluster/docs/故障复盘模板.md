## 填写示例（节选，供参考语气）

### 根因分析示例

```
直接原因：node2-db 的数据目录 /var/lib/mysql 属主被误改为 root:root，
         mysqld 进程（运行用户 mysql）无法写入，启动失败并反复重启。

根本原因（5 Why）：
  Why1 为什么 mysqld 起不来？  → 数据目录没有写权限
  Why2 为什么属主变成 root？   → 有人用 root 用户在容器内执行了 tar 解包覆盖了目录
  Why3 为什么会用 root 执行？  → 运维操作没有固定执行账号的规范
  Why4 为什么没有规范？        → 初期只有我一个人维护，没有沉淀 SOP
  Why5 为什么没被提前发现？    → 健康检查只探了 HTTP，没有探数据库进程状态

结论：不是 MySQL 的问题，是**操作规范缺失**的问题。
```

### 改进措施示例

```
1. 【预防】所有容器内操作统一用服务运行用户，禁止 root 直改数据目录；
2. 【发现】健康检查脚本增加 MySQL 进程与主从状态检查（已完成，5 分钟轮询）；
3. 【流程】写《数据库变更 SOP》，任何涉及数据目录的操作需二次确认；
4. 【兜底】每周做一次备份恢复演练，确保最坏情况下能拉起。
```

## 面试怎么讲（30 秒版本）

> "印象最深的是一次主从复制断裂。凌晨健康检查告警说从库 SQL 线程停了，
> 我登上去看 `SHOW REPLICA STATUS`，错误码 1062，主键冲突。
> 追下来是有人用 root 账号在从库插了一条测试数据——`read_only` 对 root 是无效的，
> 这是 MySQL 权限模型的已知弱点。
> 我选了补数据而不是跳过事务，因为跳过会永久丢数据。
> 事后我把从库改成 `super_read_only`，应用账号去掉 SUPER 权限，
> 并且把主从双 Yes + 延迟检测写进了 5 分钟轮询的健康检查脚本。
> 这个事情之后半年没再出现过同类问题。"

**这段讲完，面试官基本不会再追问细节了**——因为它同时体现了：会看日志、懂 MySQL 权限模型、有数据一致性意识、有闭环改进的思维。
