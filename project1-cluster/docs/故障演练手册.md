# 故障演练手册：6 个可复现故障

> 简历写的是「排查解决权限异常、端口占用等故障，通过系统日志定位，解决并输出复盘文档」。
> 故障不会自己送上门——**你得亲手造出来，再亲手查出来**。
>
> 每个场景分四步：**制造 → 现象 → 排查 → 解决**。
> 排查的时候把每条命令的输出都截图保存，那是复盘文档的素材。

---

## 场景 1：端口占用（简历原文提到）

### 制造
```bash
# 在宿主机上抢先占用 80 端口
python3 -m http.server 80 &
# 或者
dnf install -y nc && nc -l 80 &

# 然后重启 LB 容器
docker compose restart lb
```

### 现象
```
Error response from daemon: driver failed programming external connectivity
on endpoint lb: Bind for 0.0.0.0:80 failed: port is already allocated
```
或者 `docker logs lb` 里出现：
```
nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
```

### 排查（按这个顺序，就是你的方法论）
```bash
# 1. 谁占了端口（-t tcp -l listen -n 数字显示 -p 进程）
ss -tlnp | grep ':80'
lsof -i:80
netstat -tlnp | grep ':80'      # 老工具，也要会

# 2. 看是什么进程
ps -fp $(ss -tlnp | grep ':80' | grep -oP 'pid=\K[0-9]+' | head -1)

# 3. 如果进程不存在但端口还占着 → TIME_WAIT / 僵尸 socket
ss -tan state time-wait | wc -l

# 4. Docker 层面的端口占用（容器已经退出但端口没释放）
docker ps -a | grep -i 80
```

### 解决
```bash
kill -9 <PID>
# 容器层面的话
docker rm -f <残留容器>
docker compose up -d lb
```

### 复盘要点（写进文档的话术）
> 定位思路是「从现象反推端口归属」：先看 `ss -tlnp` 确认端口被哪个 PID 持有，
> 再 `ps -fp` 确认进程来源，最后判断是杀进程还是改端口。
> 根因是重启容器前没有确认宿主机端口占用情况。
> **改进措施**：把端口占用检查写进部署前置检查脚本，部署前先跑一遍。

## 场景 2：权限异常（简历原文提到）—— 两种，都要会

### 2A. 数据目录属主错误导致 MySQL 启动失败

#### 制造
```bash
docker exec node1-db sh -c 'chown -R root:root /var/lib/mysql'
docker restart node1-db
```

#### 现象
```
$ docker logs node1-db
mysqld: Can't create/write to file '/var/lib/mysql/...' (Errcode: 13 - Permission denied)
[ERROR] [MY-010119] Aborting
```

#### 排查
```bash
docker logs node1-db --tail 50
docker exec node1-db sh -c 'ls -ld /var/lib/mysql && id mysql'
# ★ 逐层检查路径权限（这个命令很多运维不知道，用了很显专业）
docker exec node1-db sh -c 'namei -l /var/lib/mysql/ibdata1'
```

#### 解决
```bash
docker exec node1-db sh -c 'chown -R mysql:mysql /var/lib/mysql && chmod 750 /var/lib/mysql'
docker restart node1-db
```

### 2B. SELinux 导致宿主机目录挂载后容器内无权限（★ 高分场景）

#### 制造
```bash
# 确认 SELinux 状态
getenforce
# 如果是 Disabled，先开启（OpenCloudOS 可能默认关闭，需要改 /etc/selinux/config 并重启）
# 开启后，bind mount 的宿主机目录容器内访问会被拒绝
```

#### 现象
Nginx 返回 403，日志里是：
```
open() "/usr/share/nginx/html/index.html" failed (13: Permission denied)
```
但 `ls -l` 看起来权限明明是对的（644 + 可读）。**这是 SELinux 的典型迷惑点**。

#### 排查
```bash
getenforce                          # Enforcing 就是它
# ★ 关键命令：查 AVC 拒绝记录
ausearch -m AVC -ts recent | head -20
# 或者
journalctl -t setroubleshoot --since "10 min ago"
# 临时验证：关掉 SELinux 试试，能访问就坐实是它
setenforce 0
curl -I http://127.0.0.1/
```

#### 解决（三个层次，面试能讲出层次感）
```bash
# 1) 临时：setenforce 0（生产禁止，只能用于确认问题）

# 2) 正确做法：给目录打容器可访问的标签
chcon -Rt svirt_sandbox_file_t /opt/ops/project1-cluster/www

# 3) 最标准的做法：docker 挂载时加 :z / :Z 标志（改 compose 文件）
#    - /opt/ops/.../www:/usr/share/nginx/html:ro,z
#    z = 多容器共享标签   Z = 独占私有标签
#    这就是 docker volume 挂载里那个神秘的 :z 参数的真实用途
```

### 复盘要点
> 权限问题不能只看 `ls -l`。Linux 的权限是三层的：
> **传统 DAC 权限（rwx）→ ACL → SELinux MAC**。
> 前两层都对却仍然 Permission denied，就要查 AVC 日志。
> 我用 `ausearch -m AVC` 定位到是 SELinux 标签不匹配，
> 最终通过挂载参数 `:z` 解决，而不是直接关 SELinux —— 关掉是掩盖问题，不是解决问题。

## 场景 3：磁盘占满导致 MySQL 崩溃

### 制造
```bash
# 造一个 5G 的大文件把根分区塞满（先看 df 剩多少）
df -h /
fallocate -l 5G /tmp/bigfile    # 若不支持则用：
# dd if=/dev/zero of=/tmp/bigfile bs=1M count=5000 status=progress
```

### 现象
MySQL 容器自动退出，`docker logs node1-db` 显示：
```
[ERROR] [MY-000035] Disk is full writing './mysql-bin.000003' (Errcode: 28 - No space left on device)
```
网站开始报 502。

### 排查
```bash
df -h                                  # 确认满了
df -i                                  # ★ 也可能是 inode 耗尽（很多小文件时）
# 找出大目录
du -sh /* 2>/dev/null | sort -rh | head -10
du -sh /var/lib/docker/* 2>/dev/null | sort -rh | head
# ★★ 经典陷阱：文件已删除但空间没释放（进程还持有 fd）
lsof | grep deleted | head -20
# 上面的输出里，被 MySQL/Nginx 打开着的已删除日志文件就是元凶
# 另外 Docker 自身的空间：
docker system df
docker system df -v | head -30
```

### 解决
```bash
# 有大文件：直接删
rm -f /tmp/bigfile

# 是 deleted 文件占着：重启持有它的进程，或 truncate
: > /proc/<PID>/fd/<FD号>     # 在线清空不重启服务，生产救命技巧

# Docker 垃圾清理
docker system prune -a --volumes    # ⚠ 注意：会把未使用的 volume 也删了

# 日志轮转（MySQL/Nginx 日志）
docker exec node1-db sh -c 'ls -lh /var/log/mysql/'
```

### 复盘要点
> 根因是备份脚本和 binlog 都在往根分区写，且没有容量监控。
> 改进：① 备份目录挂到独立目录并加 85% 告警（已写进 backup.sh）；
> ② binlog 设置 `binlog_expire_logs_seconds=604800` 自动过期；
> ③ 日志加 logrotate。

## 场景 4：MySQL 参数写错导致容器反复重启

### 制造
```bash
# 在 master.cnf 里加一行不存在的参数（MySQL 8.4 已移除的参数最容易踩）
echo "innodb_log_file_size = 64M" >> mysql/master.cnf   # 8.0.30+ 已弃用
# 或者故意写错：
echo "thread_concurrency = 8" >> mysql/master.cnf       # MySQL 5.7 后已移除
docker compose up -d node1-db
```

### 现象
```
$ docker compose ps
node1-db   mysql:8.0   "docker-entrypoint.s…"   Restarting
```
容器一直 Restarting，起不来。

### 排查
```bash
docker logs node1-db --tail 30
# 典型输出：
# [ERROR] [MY-000067] unknown variable 'thread_concurrency=8'
docker inspect node1-db --format '{{.State.ExitCode}}'

# ★ 容器起不来时怎么进去看（救命技巧）
docker run --rm -v cluster_p1_db_node1:/data -it alpine sh
# 或者把配置临时改回来：
docker compose down node1-db && vi mysql/master.cnf && docker compose up -d node1-db
```

### 解决
注释掉错误参数，重启。

### 复盘要点
> MySQL 8.0 到 8.4 之间废弃了一批参数名（`innodb_log_file_size`、`thread_concurrency`、
> `slave_parallel_workers` → `replica_parallel_workers`）。
> 教训：**改配置前先在测试环境验证，改完用 `mysqld --verbose --help --defaults-file=xxx` 做语法校验**。
> 我的做法是把配置文件纳入版本管理，每次改动都先在测试容器验证再上生产。

## 场景 5：主从复制断裂（★ 最常见的生产故障）

### 制造
```bash
# 在从库手动写入（read_only 对 root 无效，这正是生产事故来源）
docker exec -e MYSQL_PWD=Root@123456 node2-db mysql -uroot -e \
  "INSERT INTO shop.orders (id,user_id,product,amount,status) VALUES (1000,88,'ghost',1.00,'paid');"

# 再在主库写入同一主键
docker exec -e MYSQL_PWD=Root@123456 node1-db mysql -uroot -e \
  "INSERT INTO shop.orders (id,user_id,product,amount,status) VALUES (1000,77,'real',2.00,'paid');"
```

### 现象
从库 SQL 线程停止：
```
Replica_SQL_Running: No
Last_SQL_Error: Could not execute Write_rows event on table shop.orders;
                Duplicate entry '1000' for key 'orders.PRIMARY'
```

### 排查
```bash
docker exec -e MYSQL_PWD=Root@123456 node2-db mysql -uroot -e "SHOW REPLICA STATUS\G" \
  | grep -E 'Replica_IO_Running|Replica_SQL_Running|Last_SQL_Error|Last_SQL_Errno|Retrieved_Gtid|Executed_Gtid'

# 1062 = 重复键   1032 = 找不到行（从库少数据）
# 看具体冲突的 GTID，定位是哪条事务
```

### 解决（两条路，都要会）
```bash
# 方案 A（数据一致优先）：删掉从库那条幽灵数据，让复制追上
docker exec -e MYSQL_PWD=Root@123456 node2-db mysql -uroot -e "DELETE FROM shop.orders WHERE id=1000;"
docker exec -e MYSQL_PWD=Root@123456 node2-db mysql -uroot -e "START REPLICA;"

# 方案 B（跳过事务，GTID 模式下的标准做法：注入空事务）
# 1) 拿到 Executed_Gtid_Set 和出错事务的 GTID
# 2) 执行：
STOP REPLICA;
SET @@SESSION.GTID_NEXT='<出错的GTID>';
BEGIN; COMMIT;                    # 空事务占位
SET @@SESSION.GTID_NEXT=AUTOMATIC;
START REPLICA;
```

### 复盘要点
> 根因是有人在从库执行了写操作。`read_only=ON` 挡不住 root/SUPER 权限账号，
> 这是 MySQL 权限模型的已知弱点。
> 改进：① 从库开启 `super_read_only=ON`；② 应用账号不给 SUPER；
> ③ 把 `SHOW REPLICA STATUS` 的双 Yes + 延迟纳入健康检查脚本（已实现，5 分钟一次）。
> 修复时我优先选了「补数据」而不是「跳过事务」，因为跳过会永久丢失这条数据。

## 场景 6：连接数打满 too many connections

### 制造
```bash
# 开 60 个长连接（max_connections=60）
for i in $(seq 1 60); do
  docker exec -d -e MYSQL_PWD=Root@123456 node1-db mysql -uroot -e "SELECT SLEEP(300);"
done
```

### 现象
应用接口报 500，`docker logs node1-app` 里：
```
pymysql.err.OperationalError: (1040, 'Too many connections')
```

### 排查
```bash
docker exec -e MYSQL_PWD=Root@123456 node1-db mysql -uroot -e \
  "SHOW STATUS LIKE 'Threads_connected'; SHOW VARIABLES LIKE 'max_connections';"

# ★ 管理员预留连接：root 也连不上时用
docker exec -e MYSQL_PWD=Root@123456 node1-db mysql -uroot -e \
  "SELECT id,user,host,db,command,time,state,LEFT(info,80) FROM information_schema.processlist ORDER BY time DESC LIMIT 20;"

# 找出 sleep 最久的连接
docker exec -e MYSQL_PWD=Root@123456 node1-db mysql -uroot -N -e \
  "SELECT CONCAT('KILL ',id,';') FROM information_schema.processlist WHERE command='Sleep' AND time>60;"
```

### 解决
```bash
# 批量 kill 掉 sleep 连接
docker exec -e MYSQL_PWD=Root@123456 node1-db mysql -uroot -N -e \
  "SELECT CONCAT('KILL ',id,';') FROM information_schema.processlist WHERE command='Sleep' AND time>60;" \
  | docker exec -i -e MYSQL_PWD=Root@123456 node1-db mysql -uroot

# 根治：应用侧要设连接超时/连接池
# MySQL 8.0 有管理员预留连接的机制：
#   admin_address / admin_port，或用 --max_connections 之外的方式
```

### 复盘要点
> 根因是应用没有设置连接超时，慢查询期间连接堆积，最终打满 `max_connections`。
> 我从三个层面处理：① 紧急 kill 长期 Sleep 连接恢复服务；
> ② 应用侧加连接池和 `wait_timeout`；
> ③ 监控加 `Threads_connected` 阈值告警，在打满之前预警而不是事后救火。
