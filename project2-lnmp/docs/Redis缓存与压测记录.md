# Redis 缓存接入与压测记录

> 本文记录项目二从「每次都查 MySQL」到「命中缓存直接返回」的完整过程，
> 包含压测方法与原始数据、瓶颈分析、以及一个把 98 个成功请求误判成失败的坑。

---

## 一、为什么加 Redis

首页原来每次请求都要执行 3 条聚合查询：

```sql
SELECT COUNT(*) FROM orders;       -- 30 万行
SELECT COUNT(*) FROM order_items;  -- 15 万行
SELECT COUNT(*) FROM users;        -- 5005 行
```

实测这段回源逻辑耗时 **58 ms**。

关键判断：`COUNT(*)` 在 InnoDB 里没有「总行数」缓存，**必须扫一遍索引**。
行数越多越慢，而这个数字对业务来说变化很慢（下单才 +1），
**每一次请求重新算一遍是纯浪费**。

这类「结果变化慢、单次计算贵、读多写少」的聚合，是缓存最典型的适用场景。

> 反过来说，如果换成「查询某用户最近 20 条订单」这种个性化、变化快的数据，
> 缓存的收益就会小很多，还要处理一致性——**不是所有查询都值得缓存**。

## 二、缓存设计（Cache-Aside）

```
请求 → 查 Redis ──命中──→ 直接返回
         │
       未命中
         ↓
      查 MySQL → 写回 Redis(TTL 60s) → 返回
```

代码位置：`www/index.php`，四个要点：

| 设计 | 取值 | 原因 |
|---|---|---|
| 缓存 key | `lnmp:stats:v1` | 带版本号，改结构时换 v2 即可，不用手动清 |
| TTL | 60 秒 | 决定**最多容忍多久的脏数据**，不设就永远脏下去 |
| 序列化 | `json_encode` | 存字符串，人能直接 `redis-cli get` 看，排障方便 |
| 降级 | 连不上就把 `$redis` 置 null | **缓存是性能组件，不能变成可用性单点** |

降级那段代码长这样，是整个设计里最重要的 6 行：

```php
try {
    $redis = new Redis();
    if (!$redis->connect($rdHost, $rdPort, 0.5)) {
        throw new RuntimeException('connect timeout');
    }
} catch (Throwable $e) {
    $redis = null;          // ← 置空，后面所有 if ($redis) 自动跳过
    $rdErr = $e->getMessage();
}
```

`0.5` 秒连接超时也是刻意的：Redis 卡住时不能让整个页面跟着卡死。

## 三、压测方法

### 为什么用 ab 而不是 curl 循环

`curl` 是串行的，测出来的是「一次往返的延迟」；`ab` 能压出**吞吐量**（QPS），
这才是能写进简历的量。

```bash
docker run --rm --network host httpd:2.4-alpine \
  ab -n 500 -c 20 "http://127.0.0.1:8080/?nocache=1"
```

### ab 报告里两个 "Time per request" 有什么区别

这是最容易看错的地方：

```
Time per request:       1582.986 [ms] (mean)
Time per request:       79.149 [ms] (mean, across all concurrent requests)
```

| 指标 | 含义 | 什么时候看 |
|---|---|---|
| `(mean)` | **单个用户**感受到的耗时，含排队时间 | 看用户体验 |
| `(mean, across all concurrent requests)` | 总耗时 ÷ 总请求数 | 看**服务端真实处理能力** |

两者相差的倍数约等于并发数（1583 ÷ 79 ≈ 20），
差值就是「排队等待」的部分。

**判断优化效果要看第二个**，因为排队是并发的副产物，不是优化的对象。

## 四、结果

环境：2 核 2G 轻量服务器，MySQL 8.0.46（buffer pool 256M），Redis 7-alpine（maxmemory 64mb）

| 组 | 条件 | QPS | 单请求延迟(mean) | 服务端耗时 | 取数耗时 |
|---|---|---|---|---|---|
| A | `?nocache=1` 强制回源 | **12.62 / 12.63** | 1585 / 1583 ms | 79.2 / 79.1 ms | 58 ms |
| B | 走缓存 | **819.74 / 793.93** | 24.4 / 25.2 ms | 1.22 / 1.26 ms | **0.45 / 0.07 ms** |

**QPS 提升约 63 倍**（794 ÷ 12.6），服务端耗时降低约 **63 倍**。

两组各跑了两次，数字几乎一致（12.62 vs 12.63、819.74 vs 793.93）——
**两次独立测量能复现，才说明这个数字可信**。

缓存命中链路的直接证据：

```
MISS 回源      ← 第一次，回填缓存
HIT 命中缓存    ← 第二次
HIT 命中缓存    ← 第三次
```

## 五、瓶颈分析（这段比数字值钱）

**A 组慢，不是因为 MySQL 差，是因为每次都在做重复计算。**

12.6 QPS 这个数字可以反推验证：

```
1000 ms ÷ 79 ms ≈ 12.6   ← 和服务端耗时完全吻合
```

说明 A 组的瓶颈就是那 58ms 的回源，没有别的隐藏开销。

**B 组快，但不可能无限快。**

QPS 提到 794 之后，瓶颈已经从 MySQL 转移到下面几处：

| 新瓶颈 | 表现 |
|---|---|
| PHP-FPM worker 数（`pm.max_children=8`） | 20 并发时有 12 个请求排队，表现为 `mean` 延迟远大于 `across all` |
| CPU（2 核，ab 自己占一个） | 压测工具本身成为限制 |
| nginx / 网络 | 单机回环，影响小 |

**所以正确的结论不是「加了缓存就快 63 倍」，而是**：

> 缓存把重复的聚合计算消掉了，瓶颈从数据库转移到应用层；
> 并发继续提高时，需要调 `pm.max_children` 或加 PHP 副本，
> 而 QPS 不再随缓存而线性增长。

这句话能挡住「那再加并发是不是还能更高」的追问。

## 六、踩坑：98 个「失败」其实全成功

第一次压测的输出：

```
Failed requests:        486
```

看着像一半请求挂了。实际细分是：

```
Failed requests:        98
   (Connect: 0, Receive: 0, Length: 98, Exceptions: 0)
```

`Length: 98` 的意思是**响应体长度不一致**，不是 HTTP 错误。

原因很直接——页面内容每次都在变：

```
会话 ID：a1b2c3d4        ← 每个请求不同
本会话访问次数：3         ← 递增
取数耗时：58.09 ms       ← 每次不同
```

ab 发现长度对不上，就记一笔 failed。

**判断真实错误要看三处**：

| 位置 | 含义 |
|---|---|
| `Connect` / `Receive` / `Exceptions` | 非 0 才是真失败（连接、收包、异常） |
| `Non-2xx responses` 这一行 | 出现即说明有 4xx/5xx；**没出现就说明全是 200** |
| `Complete requests` | 是否等于 `-n` 的值 |

> 这个坑和项目一 `docs/08` 第 23 坑（`docker exec` 把进程启动开销算进查询耗时）是同一类：
> **测量工具的输出不能照字面读，要拆开看它到底在数什么。**

## 七、面试话术

> 首页有 3 条 `COUNT(*)` 聚合，在 30 万行的订单表上单次回源 58ms。
> 我加了 Redis 做 cache-aside，TTL 60 秒，并且做了降级——Redis 连不上就直连 MySQL，
> 不让缓存成为可用性单点。
>
> 压测用 ab，500 请求 20 并发，QPS 从 12.6 提到 794，服务端耗时从 79ms 降到 1.26ms。
>
> 但我觉得更值得说的是瓶颈的变化：缓存把数据库的压力消掉之后，
> 瓶颈转移到了 PHP-FPM 的 worker 数上，20 并发时 8 个 worker 不够用，
> 排队时间让用户侧延迟还有 25ms。所以下一步不是继续调缓存，
> 而是调 `pm.max_children` 或者加 PHP 副本。

**如果被追问「压测里 Failed requests 有 98 个，是不是有问题」**：

> 那是 ab 的 `Length` 计数，不是 HTTP 失败。因为页面里带了会话 ID 和实时耗时，
> 每次响应长度都不一样。我用 `Non-2xx responses` 这一行确认过，一个 4xx/5xx 都没有，
> `Connect`、`Receive`、`Exceptions` 也都是 0。

**这一段答出来，比报任何数字都更能说明你真的读过压测报告。**
