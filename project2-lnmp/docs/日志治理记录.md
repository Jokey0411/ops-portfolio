# 日志治理：两个出口，两层配置

> 对应简历：「容器日志上限（json-file 10m×3 轮转）+ 挂载日志 logrotate 按天归档，
> 避免 2C2G / 50G 小机器被日志写满」
>
> 本文所有数字都是 2026-11-03 在本机实测。

---

## 一、先分清两个出口

多数人配日志上限只做一件事：`daemon.json` 里写个 `max-size`，然后以为万事大吉。
**实际上 Docker 只管一半。**

| 出口 | 物理位置 | 谁在写 | 谁负责轮转 |
|---|---|---|---|
| **A. 容器 stdout/stderr** | `/var/lib/docker/containers/<id>/<id>-json.log` | 进程的 fd 1 / fd 2 | Docker 的 `max-size` + `max-file` |
| **B. 应用写的文件** | `/opt/ops/project2-lnmp/logs/` | 应用自己 `open()` | **没人，除非你配 logrotate** |

项目二两个出口都有日志：

- **走 A**：php-fpm 的报错（`php.ini` 里 `error_log = /proc/self/fd/2`）、redis 启动日志
- **走 B**：nginx 的 `access.log`（**每请求一行，涨得最快**）、`error.log`、mysql 的 `slow.log` / `error.log`

为什么 B 会被漏掉：`logs/` 是 bind mount 进容器的宿主机目录。对 Docker 来说那只是
「容器挂了个卷」，里面写什么、写多大，它既不知道也不关心。

> **一句话**：`max-size` 管的是「容器说了什么」，不是「应用写了什么」。

## 二、出口 A：容器 stdout 的上限

### 配置方式的选择

有三层可以配，优先级从高到低：

| 层级 | 写法 | 生效范围 | 适合场景 |
|---|---|---|---|
| 单容器 | `docker run --log-opt max-size=10m` | 当前容器 | 临时排查 |
| compose | 服务下 `logging:` | 该服务 | **推荐，跟着代码走** |
| 宿主机默认 | `/etc/docker/daemon.json` | 之后新建的所有容器 | 兜底，防手动 `docker run` 忘了配 |

本项目**两层都配**：

- `daemon.json` 里已有 `"log-opts": {"max-size":"20m","max-file":"3"}`（`00-init-server.sh` 第 6 步），
  管住以后任何 `docker run` 起的临时容器
- `docker-compose.yml` 里用 YAML 锚点给四个服务统一压到 `10m×3`

```yaml
x-logging: &default-logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

services:
  nginx:
    logging: *default-logging
```

**为什么用 `x-logging` 锚点而不是每个服务抄一遍**：四份重复配置只要有一个人改了其中一份，
就会出现「nginx 10m、mysql 20m」这种不一致，而且看 diff 时很难发现。
锚点让「所有服务共用一套日志策略」成为代码结构上的事实。

**为什么不用 `daemon.json` 一把梭**：它是**宿主机状态**，不在 git 里。
换台机器、重装 Docker、别人 clone 你的仓库——日志上限全没了，而且没人会记得补。

### 一个必须知道的生效时机

> **Docker 的日志配置在「容器创建」时写进 `HostConfig`，之后改任何配置都不会影响已存在的容器。**

`docker restart` 也没用——重启只是重启进程，容器对象还是原来那个。
必须 **recreate**：

```bash
docker compose up -d              # 检测到 logging 变化会自动 recreate
docker compose up -d --force-recreate   # 不放心就强制重建
```

重建会中断服务 20~40 秒。mysql 数据在 named volume 里，容器删了数据还在。

### 验证：配置对不对，和拦不拦得住，是两件事

**第一步，看配置**：

```bash
docker inspect --format '{{.Name}} {{json .HostConfig.LogConfig}}' lnmp-nginx lnmp-php lnmp-mysql lnmp-redis
```

`{{json .HostConfig.LogConfig}}` 取的是**容器实际生效的配置**，不是 compose 文件里写的。

实测四个容器全部返回：

```json
{"Type":"json-file","Config":{"max-file":"3","max-size":"10m"}}
```

**第二步，看行为**——往容器 stdout 灌 40 MiB，看它会不会停在 30 MiB：

```bash
docker run -d --name logtest \
  --log-driver json-file --log-opt max-size=10m --log-opt max-file=3 \
  redis:7-alpine \
  sh -c 'yes "log-pad-0123456789abcdef" | head -c 41943040'

sleep 5
LT=$(docker inspect --format '{{.LogPath}}' logtest)
sudo ls -lh "$LT"*
sudo du -ch ${LT}* | tail -1
```

实测结果：

```text
8.8M  ...-json.log
9.6M  ...-json.log.1
9.6M  ...-json.log.2
28M   total
```

**为什么不是整齐的三个 10M、总共 30M？**

1. **每个文件停在 9.6M**：Docker 是**写入前检查**——当「当前大小 + 这条日志」超过 10 MiB 时，
   先轮转再写。所以文件总在临界点之前停住，永远不会正好 10.0M
2. **总量 28M 而不是 30M**：灌了 40 MiB，按 9.6M 一个需要约 4.2 个文件，
   而 `max-file=3` 只留最近 3 个，最早那 1.2 个被删掉了

> **判据**：三个文件 + 总量明显小于输入量（28M < 40M）+ 总量接近 `3 × max-size`。
> 如果配置没生效，你会看到一个孤零零的 40M 文件。

### 副作用：`docker logs` 只能看到当前那个文件

轮转掉的 `.1` / `.2` 不在 `docker logs` 的读取范围内。这是拿「日志完整」换「磁盘安全」，
必须知情地接受。要留完整历史的话，得把日志驱动换成 `syslog` / `fluentd`，或者应用直接写文件（走出口 B）。

## 三、出口 B：挂载目录里的日志

### nginx 和 mysql 的轮转方式必须不同

这是整块最值得讲的地方，**照抄网上的配置最容易在这里出错**。

| 应用 | 轮转方式 | 原因 |
|---|---|---|
| nginx | `create` + `postrotate` 发 **USR1** | nginx 收到 USR1 会「重新打开日志文件」，连接不断、日志不丢 |
| mysql | `copytruncate` | mysqld **没有**「重新打开日志」的信号 |

**如果 mysql 也用 nginx 那套（rename + create）会怎样**：
logrotate 把 `slow.log` 改名成 `slow.log.1`，然后新建一个空的 `slow.log`。
但 mysqld 手里握的是**旧文件的 inode**，它继续往那个已改名的 `.1` 里写。
结果是：`slow.log` 永远 0 字节，日志全在 `.1` 里堆着——**看着轮转成功，实际一点没省空间**。

**为什么 nginx 在容器里也能收到 USR1**：宿主机上 `kill -USR1 $(cat /run/nginx.pid)`
拿不到容器内的 pid，但 `docker kill --signal=USR1 lnmp-nginx` 直接把信号发给容器内 PID 1，
效果一样。

### 完整配置

`project2-lnmp/logrotate/lnmp.conf`：

```text
/opt/ops/project2-lnmp/logs/nginx/*.log {
    daily
    maxsize 20M
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    create 0644 root root
    postrotate
        /usr/bin/docker kill --signal=USR1 lnmp-nginx >/dev/null 2>&1 || true
    endscript
}

/opt/ops/project2-lnmp/logs/mysql/*.log {
    daily
    maxsize 50M
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
    su root root
}
```

几个参数的理由：

| 参数 | 作用 |
|---|---|
| `daily` + `maxsize` | 两个是「或」的关系：到了 20M 立刻转，没到就等第二天 |
| `rotate 7` | 留 7 份，配合备份脚本的 7 天保留，磁盘占用可预测 |
| `delaycompress` | 延迟一轮再压缩。刚轮转的 `.1` 还保持明文，出问题能直接 `tail` |
| `missingok` | 文件不存在不报错（容器暂时没起时也能正常跑） |
| `notifempty` | 空文件不转，避免产生一堆 0 字节的 `.1` |
| `su root root` | 某些发行版下 logrotate 会因目录权限检查失败，显式声明运行身份 |

### 部署与验证

```bash
cd /opt/ops/project2-lnmp
sudo cp logrotate/lnmp.conf /etc/logrotate.d/lnmp
sudo chmod 644 /etc/logrotate.d/lnmp      # 组可写会被 logrotate 拒绝加载
sudo logrotate -d /etc/logrotate.d/lnmp   # -d 只演练，先看有没有 error
sudo logrotate -f /etc/logrotate.d/lnmp   # -f 强制立刻转一次
```

**实测（nginx）**：

```text
轮转前   lnmp_access.log     337087 字节（约 330KB，几小时测试流量）
轮转后   lnmp_access.log           92 字节
         lnmp_access.log.1     337087 字节
```

新文件里的 92 字节正是轮转之后那次 `curl` 的请求记录：

```text
172.30.0.1 - [03/Nov/2026:06:14:20 +0000] "GET / HTTP/1.1" 200 rt=0.064 urt=0.065 body=3086
```

**这才是 USR1 生效的铁证**。如果信号没送到，这 92 字节会跑进 `.1` 里，而 `.log` 永远是 0
——**光看「`.1` 出现了」是判断不出来的**。

顺带一个观察：新文件属主是 `101 root`（nginx 用户），不是配置里写的 `root root`。
因为 USR1 之后是 **nginx 自己** open 的新文件，`create` 参数只在 logrotate 主动创建时才生效。
nginx 用 uid 101 能写自己的文件，所以没问题；如果哪天报 `Permission denied`，
把 `create` 改成 `create 0644 101 101`。

**实测（mysql）**：

```text
轮转前   slow.log       273 字节
logrotate -f 后
         slow.log         0 字节      ← 被截断
         slow.log.1     273 字节      ← 原内容
         slow.log.2.gz 1620 字节      ← 更早的，已压缩

再跑一条查询后
         slow.log       289 字节      ← ★ 写回原文件名了
         slow.log.1     273 字节      ← 保持不变
```

`slow.log` 从 0 涨到 289 字节，说明 `copytruncate` 之后 mysqld 的 fd 依然有效、
继续往同一个 inode 写。**如果这里变成「`.1` 在涨、`slow.log` 一直是 0」，
就是轮转方式和应用不匹配。**

### 造慢查询时的口径差异

验证过程中发现一个容易误判的点：两条查询，一条记录成功，一条没有。

| 查询 | Query_time | Rows_examined | 是否记录 |
|---|---|---|---|
| `status='paid' ORDER BY amount DESC LIMIT 5000` | 0.228s | 305000 | ✅ |
| `status='pending' ORDER BY amount DESC LIMIT 5000` | — | < 1000 | ❌ |

`my.cnf` 里三个参数在起作用：

```ini
long_query_time = 0.5                          # 超过 0.5 秒算慢
log_queries_not_using_indexes = 1              # 没走索引的也记
min_examined_row_limit = 1000                  # 但扫描少于 1000 行的直接跳过
```

`paid` 那条**只有 0.228 秒，根本没到 0.5 秒门槛**，它是靠「没走索引 + 扫描 30 万行」被记下来的。
`pending` 单子少，扫描行数不够 1000，**在判断慢不慢之前就被过滤了**。

所以「我造了慢查询但日志里没有」时，先看 `Rows_examined`，别急着怀疑日志配置。

## 四、自动化：确认它真的会自己跑

配好不等于会跑。RHEL 系（OpenCloudOS 属于这类）走的是 `cron.daily` 这条路，不是 systemd timer：

```bash
ls -l /etc/cron.daily/logrotate      # 发行版自带的包装脚本
systemctl is-active crond            # active 才算数
sudo grep -i logrotate /var/log/cron | tail -5
sudo cat /var/lib/logrotate/logrotate.status | grep project2
```

实测：

```text
/etc/cron.daily/logrotate   存在（2018 年的系统自带文件）
crond                       active
/var/log/cron               11-01 03:13 / 11-02 03:11 / 11-03 03:48 每天都有记录
logrotate.status            6 个项目二日志文件全部登记
```

**两个容易误判的现象**：

1. **每天执行时间不一样**（03:11 / 03:48 / 03:13）——这是 `/etc/anacrontab` 里
   `START_HOURS_RANGE` + 随机延迟的效果，避免一批机器同一秒集中跑 logrotate 把磁盘打满。
   服务器上这是好事，不用调。
2. **`systemctl is-active anacron` 返回 inactive，不代表 cron.daily 不会跑**。
   anacron 有两个身份：systemd 常驻服务，和一个能被当场调用的普通程序。
   RHEL 系走的是 `/etc/cron.hourly/0anacron` 每小时调用一次程序这条路。
   **但如果换成会关机的环境**，要 `systemctl enable anacron` 才有「错过时间后补跑」的能力。

## 六、面试怎么讲

**Q：日志把磁盘写满了，你怎么处理？**

> **先分两个出口**，因为处理方式完全不同。
>
> 容器的 stdout/stderr 落到 `/var/lib/docker/containers/<id>/<id>-json.log`，
> 这块归 Docker 的 `max-size` 管；但应用自己写进挂载目录的文件
> （nginx 的 `access.log`、mysql 的 `slow.log`）Docker 完全不管，
> 只配 `max-size` 等于只锁了前门。
>
> 我在 compose 里用 YAML 锚点给四个服务统一了 `10m×3`，这样配置跟着代码走；
> `daemon.json` 里留 `20m×3` 做兜底，管住以后手动 `docker run` 的临时容器。
> 挂载目录那部分用 logrotate，按天 + 20M 上限轮转，留 7 份。
>
> **这里有个坑值得说**：nginx 和 mysql 的轮转方式必须不一样。nginx 能收 USR1 重新打开日志文件，
> 所以用 rename + create；mysqld 没有这个信号，只能 `copytruncate`——先复制再截断原文件。
> 如果照抄 nginx 的写法，mysqld 会一直写那个已经被改名的旧文件，
> **新的 `slow.log` 永远是 0 字节，看着轮转成功但一点空间都没省下来**。

**追问：你怎么验证配置真的生效了？**

> **配置和机制要分开验。**
>
> `docker inspect --format '{{.HostConfig.LogConfig}}'` 只能证明配置写进去了，
> 证明不了它拦得住。所以我起一个临时容器，参数和线上完全一致，让它往 stdout 灌 40MiB，
> 看结果是三个文件、合计 28M 就说明上限真的起作用了。
>
> 28M 而不是 30M 也有原因：Docker 是写入前检查，每个文件停在 9.6M 左右；
> 40MiB 按 9.6M 算需要 4.2 个文件，`max-file:3` 只留 3 个，最早的被删掉。
>
> nginx 那边，光看到 `.1` 出现是不够的——必须再发一次请求，看**新建的 `.log` 有没有新内容**。
> 如果信号没送到，nginx 还握着旧文件的 fd，会继续往 `.1` 里写，
> 而 `.log` 永远是 0：**轮转看着成功，日志其实全丢了**。
