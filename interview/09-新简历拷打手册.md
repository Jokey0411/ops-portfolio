### Q2. ★ 你只有一台服务器，为什么简历写"双节点集群"？

**背**：
> 主动交底：只有一台 2C2G 的腾讯云轻量服务器。我用 Docker Compose 的自定义 bridge 网络把两个应用节点做成独立的网络命名空间，每个容器有独立 IP、独立的进程和文件系统，模拟双节点的行为。负载均衡、故障切换、主从复制的**机制都是真的**，只是没有物理机级别的隔离。我把它明确写在项目背景里，因为我觉得被追问出来比主动说掉价十倍。

**懂**：这个问题的本质是考诚信 + 补救能力。标准答案结构：①承认限制 ②说明哪些是真的（机制、配置、演练）③说明这个方案的收益（2C2G 预算内学完整套高可用机制）④主动说不足（没有跨机网络抖动、真机房故障）。

**追**：
- 「单机和真双机差在哪？」→ 跨机才有网络分区、带宽竞争、时钟漂移；单机上容器间通信走本机 bridge，延迟微秒级，练不出网络故障场景
- 「为什么不租两台？」→ 学生预算内 2C2G 跑 9 个容器已经吃紧；机制学习优先于硬件堆叠，后面有预算再扩

## 二、项目一逐条拷打

### Q3. 集群搭建：bridge 网络和数据卷是怎么回事？

**背**：
> Compose 会创建一个自定义 bridge 网络，并启动内嵌 DNS，容器之间直接用服务名通信，比如 Nginx 的 upstream 写应用节点名、应用连数据库写 `mysql`，不写死 IP。每个服务我又配了固定内网 IP，双保险。数据卷分两类：网站代码用 bind mount，改代码立即生效；数据库用 named volume，由 Docker 管理权限，`docker compose down` 不会删卷，数据不丢。

**懂**：
- 默认 docker0 bridge **不支持容器名 DNS**，自定义 bridge 支持——这是必须自定义网络的原因
- bind mount（宿主机目录直通，开发方便，但有 uid/SELinux 坑）vs named volume（Docker 托管，权限干净，备份迁移方便）——MySQL 选 volume 就是避开了 uid 999 属主这个 11 号坑
- 配置文件挂载用 `:ro` 只读，防容器内误改，也保证配置以 git 里的为准

**追**：
- 「容器重启后数据还在吗？」→ 在。down 不删卷，`down -v` 才删
- 「两个应用节点怎么隔离的？」→ 网络命名空间：独立网卡、独立 IP、独立端口空间；进程和文件系统也是隔离的

### Q4. ★ 负载均衡：故障摘除 6 秒到 2 秒是怎么做到的？

**背**：
> 我用的是 Nginx 开源版的**被动健康检查**：请求打到故障节点，连接失败或超时后，Nginx 把这个节点标记为失败并按 fail_timeout 摘除一段时间，然后把请求转给健康节点。摘除慢的原因是 `proxy_connect_timeout` 原来配了 3 秒——请求要在坏节点上干等 3 秒才知道它死了。我把它调到 1 秒，加上重试时间，故障感知从约 6 秒缩短到 2 秒，而且切换期间用户请求没有失败，只是慢了一下。

**懂**：
- 开源版 Nginx **没有主动健康检查**（主动探测是 Nginx Plus / tengine 的功能），被动检查 = 真实请求踩雷后才摘除
- 参数分工：`proxy_connect_timeout` 管「建立连接等多久」；`proxy_next_upstream` 管「什么情况重试下一个节点」（默认 error + timeout）；`fail_timeout` + `max_fails` 管「失败几次、摘多久」
- 摘除时间的构成：坏节点超时时间 + 重试到好节点的时间。所以砍超时时间是最直接的提速

**追**：
- 「主动健康检查怎么做？」→ 开源方案用 nginx_upstream_check_module 补丁或 tengine；定期发探测请求，失败 N 次标记 down，不用真实用户流量踩雷
- 「被动检查的缺点？」→ 第一个用户要当小白鼠，请求变慢；流量小时摘除更慢（踩雷频率低）
- 「健康检查路径配的什么？」→ `/health`，只返回 200，不做业务查询（坑 #5：health 路径曾被 location 前缀匹配到业务页面返回 HTML）

### Q5. ★ 主从复制：原理 + SQL_Running: No 怎么排查的？

**背**：
> 主从复制的链路是：主库把变更写进 binlog，从库的 **IO 线程**拉取 binlog 写入本地 relay log，**SQL 线程**重放 relay log。我搭的时候遇到过 `Slave_SQL_Running: No`——IO 线程正常、SQL 线程挂了，说明是**重放阶段**出的问题。排查思路是 `SHOW SLAVE STATUS\G` 里看 Last_SQL_Error，根因是我初始化从库时用了带 GTID 信息的全量备份，和从库自己的 GTID 集合冲突，重放卡住。解决是导出时加 `--set-gtid-purged=OFF`，重新初始化从库，复制恢复正常。

**懂**：
- 两个线程分工：IO 线程挂 = 网络或认证问题；SQL 线程挂 = **数据层面**冲突（主键冲突、GTID 重复、库表缺失）。先看哪个线程 No，就往哪个方向查——这是定位口诀
- GTID 是全局事务标识，一个事务在集群里只该被执行一次；备份文件里带了主库的 GTID 历史，从库重放时发现「这个 GTID 我做过」，就停了
- `SHOW SLAVE STATUS\G` 重点看四个值：Slave_IO_Running、Slave_SQL_Running、Seconds_Behind_Master、Last_Errno

**追**：
- 「主从延迟怎么办？」→ 看 Seconds_Behind_Master；从库写压力大时开并行复制（MTS）；业务上读写分离要容忍短暂延迟
- 「binlog 三种格式？」→ statement（记语句，可能主从不一致）、row（记行变更，最安全、日志大）、mixed。MySQL 8.0 默认 row
- 「怎么验证主从数据一致？」→ 两边各 count 关键表；严格做法用 pt-table-checksum

### Q6. 备份与恢复：备份脚本里最关键的参数是什么？

**背**：
> mysqldump 我加了四个关键参数：`--single-transaction` 在 RR 隔离级别下打一致性快照，**不锁表**，InnoDB 业务无感知；`--quick` 逐行读，不把大表整个加载进内存，2G 小机器上防 OOM；`--set-gtid-purged=OFF` 去掉 GTID 信息，避免恢复时冲突——这是我主从那件事之后补的；再加 `--routines --triggers` 把存储过程和触发器带上。全量加按库各备一份，gzip 压缩，find -mtime 保留 7 天。

**懂**：
- `--single-transaction` 的前提是**全 InnoDB**；有 MyISAM 表就得 `--lock-all-tables`，那才会锁业务
- 7 天保留用 `find -mtime +7 -delete`，磁盘占用可预测
- cron 环境的坑：第一行必须写 PATH（cron 的 PATH 只有 /usr/bin:/bin，找不到 docker）；脚本必须有执行位（直接路径执行要 x 位，`bash x.sh` 只要 r 位——这两个坑我都真实踩过）

**追**：
- 「备份文件怎么确认能用？」→ ★ 我的答案不是「我检查过」，是**恢复演练**：起一个临时 MySQL 容器，把最新全量灌进去，校验表数、orders 行数、索引数三项和生产一致。实测 8.3M 备份 17 秒恢复完，30 万行一致。「备份不验证等于没备份」
- 「演练踩过什么坑？」→ 两个：①用 `mysqladmin ping` 判断临时库就绪，但它**认证失败也返回 0**，导致在 MySQL 初始化没完成时就开导，第一条语句 Access denied；②全量备份包含 mysql 系统库，恢复时把 root 密码覆盖成生产密码，临时库换密码就连不上了
- 「mysqldump 备份 100G 大表还合适吗？」→ 不合适，导出+恢复都太慢，且是逻辑备份。该上 XtraBackup 物理备份或 xtrabackup + binlog 增量

### Q7. 监控告警：Zabbix 的链路讲一遍

**背**：
> 链路是「采集 → 判定 → 通知」：agent2 采集主机指标存进 Zabbix server（我用的 PostgreSQL 做后端），**触发器**对指标做阈值判定，比如「复制落后 > 60 秒」「磁盘使用率 > 85%」，状态从 OK 变 PROBLEM 就触发**动作**，经 Webhook 推到钉钉机器人。我配了 4 条触发器，专门验证过完整闭环：手动把磁盘占满，看到告警进来；释放空间，看到自动恢复（RESOLVED）。

**懂**：
- item（采集什么）→ trigger（什么算异常，severity 分级）→ action（触发了干什么）→ media type（从哪发出去）——四层缺一不可
- 踩过的坑 #20：**告警媒介的收件人为空时，Zabbix 会静默丢弃**，界面 Action log 一片空白、连失败记录都不写。排查只能逐层看数据库。教训：告警链路每接一层，都要发一条真实告警验证
- 复制监控不是 agent 自带的，用自定义 item + 用户参数从 `SHOW SLAVE STATUS` 取值

**追**：
- 「告警太多怎么办？」→ 分级（ Average/High/Disaster ）、收敛（同类合并）、治理阈值（连续 N 次才触发）
- 「你怎么知道监控自己没坏？」→ 心跳类指标：让被监控对象定期上报「我还活着」，超时本身触发告警——和我备份的心跳脚本同一个思路

## 三、项目二逐条拷打

### Q8. ★ 启动故障排查：怎么定位 nginx 容器起不来的？

**背**：
> 我的第一反应是看 `docker compose ps`，发现 nginx 是 `Created` 状态。**Created 和 Exited 是两种完全不同的失败**：Created 说明容器对象建好了但进程一次都没执行过，`docker logs` 是空的，看日志是白看；Exited 说明进程跑过又退了，日志里一定有原因。我先怀疑 8080 端口被占，`ss -tlnp` 一查端口是空的，假设被否掉。重新 up 后变成 Exited(1)，日志给出真因：`"log_format" directive is not allowed here`——log_format 只能写在 http 上下文，而 `conf.d/*.conf` 本身就是被 http{} include 的，所以把这段挪到文件顶层就修好了，内容一个字没改。以后改 nginx 配置第一反应是 `nginx -t`，三秒出结果，还带文件名行号。

**懂**：
- 指令合法性看的是**最终落在哪一层花括号**，不是写在哪个文件
- 排查容器问题的分层顺序：容器活着吗（ps -a）→ 端口在听吗（ss -tlnp）→ 日志说了什么（logs）→ 配置对吗（-t / config 校验）

**追**：
- 「nginx -t 在容器里怎么跑？」→ `docker exec lnmp-nginx nginx -t`
- 「nginx reload 和 restart 区别？」→ reload 发 HUP，master 重读配置、平滑换 worker，不断连接；restart 会断

### Q9. ★★ 慢查询优化：133ms 到 0.11ms，具体怎么做的？

**背**：
> 先说测量方法，因为这里我踩过一个大坑：最初我用 docker exec 外面包 date 计时，测出来 4 条查询里 JOIN 那条优化前后都是 66 毫秒，得出「索引无效」的错误结论。后来发现多个无关查询耗时收敛到同一个值，说明测的是工具不是查询——docker exec 启动进程要 30-70ms。换成 `EXPLAIN ANALYZE` 看服务端 actual time，JOIN 那条实际只要 0.14 毫秒，根本不用优化。
> 真正的优化是对分页查询建复合索引 `(user_id, status, created_at)`：EXPLAIN 的 type 从 ALL 变 ref，rows 从全表 30 万变 20，**服务端耗时 133ms 降到 0.11ms**。原理是索引把「全表扫 30 万行」变成「B+ 树定位读 20 行」。

**懂**：
- 复合索引**最左前缀**：列序原则是「等值 → 等值 → 排序」；范围条件之后的列在 B+ 树里无序，ORDER BY 用不上索引
- 三条「没变快」的结论更有价值：Q2 分组统计只有 2.2 倍——索引减少的是回表，**减少不了必须扫的行数**，聚合命中比例高时该上预聚合；Q3 范围+排序只有 1.24 倍——filesort 还在，这条索引解决不了；Q4 本来就快——判断「不需要优化」也是能力
- Extra 关键值：Using index（覆盖索引，免回表）、Using filesort（排序没走索引）、Using index condition（ICP 下推）

**追**：
- 「为什么分页能快 1200 倍，分组只有 2.2 倍？」→ 分页 LIMIT 20 只取 20 行，索引直接定位；分组要聚合 6 万行，扫描行数是硬底线
- 「索引是不是越多越好？」→ 不是。每个索引都是一棵要维护的 B+ 树，写入时全部要更新，还占空间。读多写少的表才适合多建
- 「怎么发现慢查询？」→ 慢查询日志（long_query_time=0.5，log_queries_not_using_indexes），mysqldumpslow 排序汇总
- 「B+ 树为什么适合索引？」→ 矮胖（3 层撑千万行）、叶子节点成链表利于范围扫描；对比 hash 不支持范围、二叉树太深

### Q10. ★ Redis：缓存怎么设计的？为什么这么快？

**背**：
> 用的 cache-aside 模式：读请求先查 Redis，命中直接返回（0.4ms）；未命中查 MySQL（58ms），把结果写回 Redis 带 60 秒 TTL。四个设计决定：**TTL 60 秒**——缓存是副本不是真相，TTL 是能容忍脏数据的窗口；**maxmemory 64m + allkeys-lru**——不设上限 Redis 会把 2G 机器吃光，LRU 保证到顶时淘汰最久未用的而不是拒绝写入；**关 RDB 持久化**——缓存丢了可以回源重建，fork 的写时复制在 2G 机器上很伤；**连不上就降级直连 MySQL**——缓存是性能组件，不能变成可用性单点。另外 PHP session 也放进了 Redis，不然 PHP 扩副本时用户会话散落在各容器，必须会话粘滞，等于放弃水平扩容。

**懂**：
- 页面首次访问 MISS 回源 58ms，第二次 HIT 0.4ms；用 `?nocache=1` 强制回源做对照组，保证压测两组数字可比
- 回源 58ms 的构成：3 条 COUNT 聚合，扫描 30 万行
- 效果验证是页面直接打印 HIT/MISS 状态 + 取数耗时，不是「感觉变快了」

**追**：
- 「缓存和数据库一致性怎么办？」→ 我的数据 60 秒自然过期，业务能容忍；强一致场景用「更新库后删缓存」（cache-aside 标准写法），再加延迟双删；真要强一致就不该上缓存
- 「缓存雪崩/穿透/击穿？」→ 雪崩=大量 key 同时过期，加随机 TTL；穿透=查不存在的数据，缓存空值或布隆过滤器；击穿=热 key 过期瞬间打穿，互斥锁或逻辑过期
- 「Redis 为什么快？」→ 内存操作 + 单线程无锁竞争 + IO 多路复用（epoll）+ 高效数据结构
- 「RDB 和 AOF？」→ RDB 快照恢复快、可能丢数据；AOF 追加命令丢失少、文件大恢复慢。纯缓存场景都可以关

### Q11. ★★ 压测：QPS 12.6 到 794，数据可信吗？

**背**：
> 用 ab 压 500 请求、20 并发，跑了两组做对照：一组加 `?nocache=1` 强制回源，一组走缓存。每组跑两次：回源组 12.62 和 12.63，缓存组 819.74 和 793.93，**两次偏差小于 3%，可复现**。QPS 提升约 63 倍。这里有个解读细节：ab 的 Failed requests 显示几百个失败，看着吓人，但拆开看 Connect、Receive、Exceptions 全是 0，全部是 **Length**——页面里有实时耗时和 session ID，每次响应长度都不同，ab 把「响应长度变化」也计为 failed，这不是真错误。判断标准是 Non-2xx responses 没有出现。

**懂**：
- 两个 Time per request 的区别：一个是所有请求的平均（倒数=QPS），一个是每个连接的平均（≈前者×并发数）。看错列数字差 20 倍
- 瓶颈分析比数字重要：回源组慢在 58ms 的重复聚合（1000÷79≈12.6 可反推验证）；缓存组瓶颈**转移**到 PHP-FPM 的 `pm.max_children=8` 和 2 核 CPU——**缓存不会让 QPS 无限涨，瓶颈永远在下一个环节**
- 压测的变量控制：同一台机器、同一份数据、nocache 参数只差缓存路径

**追**：
- 「为什么不用 jmeter / wrk？」→ ab 够轻量，目标是对比缓存开关两个稳态，不是模拟复杂用户场景
- 「现在 QPS 到 800 之后还想加，怎么办？」→ 下一瓶颈是 PHP-FPM：调大 pm.max_children（受内存预算约束）、加 opcache，再往后是水平扩 PHP 副本——这就是 session 放 Redis 的意义
- 「压测把生产打挂了怎么办？」→ 我这是独立演练环境；生产压测要限速、错峰、有回滚预案，从低并发起步观察

### Q12. ★★ 日志与资源治理：这条具体做了什么？（新加的，必被问）

**背**：
> 我发现日志其实有**两个出口**：容器的 stdout/stderr 落在 `/var/lib/docker/containers/` 下，归 Docker 的 max-size 管；但 nginx 的 access.log、mysql 的 slow.log 是应用写进挂载目录的**普通文件**，Docker 完全不管——只配 max-size 等于只锁了前门。所以做了两层：容器层在 compose 里用 YAML 锚点统一 10m×3，实测灌 40MiB 进去，最后停在 3 个文件共 28M；文件层配 logrotate 按天加 20M 上限，留 7 份。这里有个不能照抄的点：**nginx 和 mysql 的轮转方式必须不同**——nginx 能收 USR1 重新打开日志文件，所以用 rename + create；mysqld 没有这个信号，只能 copytruncate 先复制再截断。如果给 mysql 照抄 nginx 的写法，它会一直写那个已改名的旧文件，新的 slow.log 永远是 0 字节。

**懂**：
- 验证做到了行为层：光看到 `.1` 出现不算成功，**轮转后再发一次请求看新 `.log` 有没有内容**——USR1 没送到时，日志会全丢在 `.1` 里，目录结构看着完全正常
- 28M 不是 30M 的原因：Docker 写入前检查，每个文件停在 9.6M；40MiB 需要 4.2 个文件，max-file=3 只留 3 个，最旧的被删
- daemon.json 留 20m×3 做全局兜底；compose 里是服务级精确控制。两层的原因：daemon.json 是宿主机状态，不在 git 里，换台机器就丢

**追**：
- 「docker logs 看不到轮转掉的历史，怎么办？」→ 接受这个取舍，换 syslog/fluentd 驱动或应用直接写文件能保留，但磁盘要自己管
- 「logrotate 怎么保证每天真的在跑？」→ RHEL 系走 `/etc/cron.daily/logrotate` + crond，我查了 `/var/log/cron` 确认每天 03:xx 有执行记录，`logrotate.status` 里登记了 6 个日志文件
- 「nginx 收 USR1 会怎样？」→ 重新打开所有日志文件的 fd，连接不断；容器场景用 `docker kill --signal=USR1 lnmp-nginx` 发给容器内 PID 1

### Q13. ★★ 内存上限和重启自愈：预算怎么算的？

**背**：
> 出发点是两个真实风险：三个服务都没有 restart 策略，服务器一重启网站就躺平；都没有 mem_limit，2G 机器上谁内存失控，OOM Killer 会挑 RSS 最大的进程杀——很可能错杀 mysql。内存预算我按「配置允许的理论峰值」算，不按当前 RSS——当前 mysql 只占 190M，但 buffer pool 配了 256M，空载数字做不了规划。mysql = buffer pool 256 + log buffer 16 + 基础开销 200 + 连接 buffer，约 480M，给 768；php = max_children 8 × 30M 给 384；nginx 128；redis 96。合计 1376M，加系统常驻 295M，占总内存 1975M 的 85%，留 15% 余量。改完真做了一次 reboot 验证：四个容器全部自动拉起，页面 200，数据 30 万行完好。

**懂**：
- `restart: unless-stopped` 语义：daemon 重启、服务器重启都会自动拉起，**手动 docker stop 过的不会自己回来**——这个语义正好符合预期（主动停的服务不该被拉起）
- mem_limit 落在 cgroup 上；`docker stats` 的 LIMIT 列从 1.929GiB 变成各自的值，就是生效证据
- 预算必须把腾讯云常驻组件算进去：YDService 69M + barad_agent 16M，删不掉

**追**：
- 「你怎么验证上限真的拦得住？」→ 两个层面：inspect/stats 看配置，再起临时容器灌 40MiB 内存看会不会被 OOM Kill——配置和行为分开验，是我从日志那次得到的教训
- 「重启验证用的什么方式？」→ 直接 reboot。因为 daemon.json 里配了 `live-restore: true`，systemctl restart docker 时容器根本不停，restart 策略没机会触发——用 restart docker 验证是假阳性，必须整机重启
- 「mysql 被限制到 768M，超了会怎样？」→ 不设 memswap_limit 时先往 swap 挤，慢但不死；我把取舍定为「宁可慢一点也别死」，如果出现 swap 抖动再收紧

## 四、专业技能逐条考点

### Q14. 容器：镜像和容器的关系？数据卷三种挂载？

**背**：镜像是分层只读模板，容器 = 镜像 + 一个可写层（copy-on-write），删容器丢可写层，所以数据要放卷。挂载三种：volume（Docker 托管，数据库）、bind mount（宿主机目录，配置和代码）、tmpfs（内存，临时敏感数据）。

**追**：镜像分层怎么联合的（overlay2：lowerdir + upperdir + workdir）；容器里 PID 1 是什么（镜像的启动命令，僵尸进程问题）；怎么进一个没有 shell 的容器（docker exec 不行就用 nsenter）。

### Q15. Linux：free -m 里看哪一列？

**背**：看 **available**，不是 free。free 是完全没用过的，buff/cache 是内核缓存、随时可回收；available = free + 可回收缓存，才是程序真实可用的量。我 2G 机器 available 约 1.3G。

**追**：
- 「load average 怎么看？」→ 1/5/15 分钟平均负载，对比 CPU 核数，2 核机器 load 4 就是过载；load 高但 CPU 低 = IO 等待
- 「df 和 du 不一致？」→ 文件被删除但进程还握着 fd，du 看不到、df 还算着。`lsof | grep deleted` 找到进程，重启或 truncate 释放——这是日志没轮转的经典后果
- 「ss 和 netstat？」→ ss 快（直接读内核），netstat 遍历 /proc 慢；常用 `ss -tlnp`

### Q16. Nginx：master-worker 模型？reload 原理？

**背**：master 管配置和 worker 生命周期，worker 干活，每个 worker 单线程 + epoll 处理多连接，核数 = worker 数。reload 发 HUP：master 校验新配置，起新 worker 用新配置，旧 worker 处理完存量连接后退出——平滑不断连。

**追**：502 vs 504（502=上游返回非法/连不上，504=连上了但超时）；反向代理是什么（代理后端集群，客户端无感知）。

### Q17. MySQL：事务隔离级别？三大日志？

**背**：默认 RR（可重复读），MVCC 实现；读未提交/读已提交/可重复读/串行化。三大日志：redo（物理，崩溃恢复，WAL）、undo（逻辑，回滚 + MVCC 读旧版本）、binlog（Server 层，复制和恢复）。

**追**：RR 下的幻读（快照读靠 MVCC 防了，当前读要间隙锁）；count(*) 慢的原因（要扫行）；连接数满了的现象和处置（show processlist，杀长事务）。

### Q18. Redis：为什么单线程还快？

**背**：纯内存操作（微秒级）；单线程避免锁和上下文切换；epoll IO 多路复用同时监听大量连接；数据结构为场景优化（跳表、压缩列表）。6.0 的多线程只用于网络 IO，命令执行还是单线程。

**追**：过期删除策略（惰性 + 定期采样）；LRU 是近似 LRU（采样淘汰，不是全量排序）。

### Q19. 监控：什么指标必监控？

**背**：四个方向——**利用率**（CPU/内存/磁盘/连接数）、**饱和度**（排队、负载）、**错误率**（5xx、复制中断）、**延迟**（接口 RT、主从 lag）。再加心跳兜底：被监控对象定期上报存活，监控自身故障也能暴露。

### Q20b. 网络基础：三次握手、TIME_WAIT、常见状态码（新加技能条，会考）

**背**：
> 三次握手：客户端 SYN → 服务端 SYN+ACK → 客户端 ACK。三次的目的是**双方都确认自己和对方的收发能力**，两次不能确认服务端能收到。四次挥手因为 TCP 全双工，两个方向要分别关闭；主动关闭方最后进 TIME_WAIT，等 2MSL（约 60 秒），保证最后一个 ACK 丢了对方重发 FIN 时还能应答。
> TIME_WAIT 出现在**主动关闭的一方**。我在端口冲突排查里用 `ss -tan state time-wait` 看过它——服务器上出现大量 TIME_WAIT 通常是自己作为客户端频繁短连接（比如压测、健康检查），不是故障；要减少就上长连接或连接池，不要乱改 tcp_fin_timeout。
> 状态码我都是在排错里见到的：499 是 Nginx 特有——**客户端等不及先断了**，我负载均衡演练时 curl 超时主动断开，Nginx 日志就记 499，它不是错误是「客户走了」；502 是上游返回非法响应或连不上，504 是连上了但超时——一个「连不上」，一个「连上了没回话」，处置方向完全不同。

**追**：
- 「服务器大量 TIME_WAIT 要紧吗？」→ 占端口和内存但会自动回收；真正的代价是源端口耗尽（压测机常见）。应对：长连接、连接复用、`tcp_tw_reuse`（仅出方向）
- 「三次握手每次丢包会怎样？」→ SYN 丢：客户端重传（1s、2s、4s 指数退避）；最后 ACK 丢：服务端重发 SYN+ACK
- 「HTTP 里 301 和 302 区别？」→ 301 永久重定向（浏览器缓存），302 临时（每次都问服务器）



### Q20. Shell：脚本开头写什么？

**背**：`set -uo pipefail`。set -e 让命令失败即退出（但条件语句里的失败不触发）；-u 未定义变量报错；pipefail 让管道中任一环失败整条失败——默认只看最后一个命令，`zcat x | head` 这种管道的错误会被吞。需要捕获每环退出码用 `PIPESTATUS` 数组——我在恢复演练脚本里用它抓过 zcat 被提前关管道的 141 错误。

**追**：`$$` 是什么（当前 shell PID，我拿它给临时容器起唯一名）；单引号 vs 双引号（单引号全字面，双引号会展开变量）；怎么调试（bash -x）。

### Q21. 印象最深的故障 / 最有成就感的事

**背**（用第 24 坑，结构最完整）：
> 第一次跑备份恢复演练直接失败，报 Access denied，而且**耗时 0 秒**。0 秒是最关键的信号——8M 的库不可能 0 秒恢复完，说明数据根本没被消费。如果是备份文件坏了会报 SQL 语法错；报认证错，说明问题在连接阶段。根因是我用 `mysqladmin ping` 判断容器就绪，它**在认证失败时也返回 0**，因为它只问服务器有没有响应。而 mysql 镜像启动时会先起一个临时实例做初始化，那会儿 socket 在听、root 还没密码——ping 通过但带密码连接被拒，我等于在 MySQL 没准备好时就开导了。改成 `mysql -e 'SELECT 1'` 之后，就绪等待从 0 秒变成 16 秒，这 16 秒就是被 ping 漏掉的时间。这件事教我的是：**「服务活着」和「服务可用」是两件事，就绪判断要验到业务层。**
