# 14 · 踩坑 × 简历：25 条坑对应的面试题

> **定位**：`docs/08-踩坑与修复记录.md` 的 25 条真实坑 × `09-新简历拷打手册.md` 的简历条目，做成**问题集**。
> **和 09 的区别**：09 按简历条目给"答案"（我要说什么）；这份按坑给"问题"（他会怎么问、我哪句话会引他下手、什么时候会被反将）。
> **为什么踩坑题最值钱**：简历上的数字只能证明"做完了"，坑才能证明"**真的跑过**"——编不出"我连续猜错两次"这种细节。所以每个坑都是一颗子弹，前提是你能说清**怎么排除的**，而不是"我改了下就好了"。

---

## 用法

1. 先看总表，找出**你简历上最容易被拿来开刀的三行**（一般是：双节点集群、QPS 794、25 条踩坑）。
2. 每道题**先只看问法，自己说一遍**，再看骨架对照。
3. 每题的「陷阱」是最容易翻车的地方——考试时你说得越顺，面试官越要在这里下刀。
4. 「交底话术」不是认输，是**把不会的部分变成可控的边界**。

# 第一部分 · 项目一：高可用集群（P01–P12）

## P01 · 「你 9 个容器的启动顺序是怎么保证的？」

**触发句**：简历「用 Docker Compose 编排双节点应用 + MySQL 主从 + Zabbix，共 9 个容器」

**答题骨架**
- **现象**：`docker compose up -d` 之后 `compose ps` 只有 6 个容器，三个 nginx 是 `Created` 状态，`docker logs` 一个字都没有。
- **排除**：先怀疑端口占用，`ss -tlnp | grep 80` 是空的；再怀疑配置语法，`nginx -t` 通过。两个假设都否掉。
- **根因**：nginx **启动时就要解析 upstream 里的主机名**，那时应用容器还没进 DNS，解析失败直接退出——而且退出发生在日志初始化之前，所以连报错都看不到。
- **修法**：两道保险。① `depends_on` 配 `condition: service_healthy`，等服务真的健康再起；② upstream 用**固定内网 IP**，不依赖 DNS 解析时机。
- **验证**：`compose down && up -d` 连续三次，每次 `ps` 都是 9 个 `Up`；`curl` 打三次都能通。

**关键句**：「`depends_on` 默认只保证**启动顺序**，不保证**对方可用**——这是它和 `condition: service_healthy` 的本质区别。」

**追问连击**
1. 「`depends_on` 短语法和长语法区别？」→ 短语法只排启动顺序；长语法的 `service_healthy` 才是"等健康"。
2. 「上游用固定 IP，扩缩容怎么办？」→ 固定 IP 是为了让上游不依赖 DNS 时机；真要弹性扩缩，用变量 + `resolver 127.0.0.11 valid=10s` 让 nginx 动态解析。
3. 「`Created` 和 `Exited` 区别？」→ Created = 进程一次都没跑过（看日志白看）；Exited = 跑过又退了（日志里必有原因）。**这个区分是本项目的定位起点。**

**陷阱**：说"加了 `depends_on` 就好了"会被立刻反杀——因为默认 `depends_on` 解决不了这个问题，必须说 `condition: service_healthy`。

## P02 · 「数据库还没起来的时候，你的应用在干什么？」

**触发句**：简历「双节点应用节点 + MySQL 8.0 主从」

**答题骨架**
- **现象**：应用起来就报 `Can't connect to MySQL server on 'mysql'`，容器变成 `Exited`。
- **根因**：`docker compose ps` 里 MySQL 显示 `Up`，但 `Up` 只是"容器进程在跑"——它还要经过**临时实例初始化 → 建库导数据 → 关临时实例 → 正式实例启动**四个阶段，这期间端口是听着的，但认证和库都还没就绪。
- **修法**：应用侧**重试 40 次**（日志里能看到 `waiting DB (1/40)` 逐秒递增），compose 侧 `healthcheck` + `service_healthy`。两层都要，因为重试解决"启动期"，健康检查解决"编排期"。
- **验证**：`compose down` 后 `up`，应用日志从 `waiting (1/40)` 到 `(8/40)` 连上，全程没有一次退出。

**关键句**：「`Up` 只说明进程活着，`healthy` 才说明服务可用——所以我的就绪判断一律落到业务层，不看进程状态。」

**追问连击**
1. 「重试一直失败会怎样？」→ 40 次后退出的同时发告警（否则就是无限等，问题被藏起来）。
2. 「为什么不用 `sleep 30`？」→ 慢机器上 30 秒不够、快机器上白等 30 秒，而且掩盖真实故障。要等"条件成立"，不是"时间过去"。
3. 「健康检查怎么写的？」→ 这里会接到坑 24：`mysqladmin ping` 在认证失败时也返回 0，所以我用 `mysql -e 'SELECT 1'` 做真实查询。

**陷阱**：只答"我加重试了"是 L1；要答出"**Up 的三个阶段**"才是 L3。

## P03 · 「你的 upstream 是怎么配的？容器 IP 会变吗？」

**触发句**：简历「Nginx 反向代理两个应用节点，被动健康检查」

**答题骨架**
- **现象**：自动化健康检查脚本把两个节点 IP 拼成了 `172.20.0.12172.22.0.11`（两个网段的 IP 粘在一起），curl 直接返回 `000`。
- **根因**：Go 模板里 `{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}` 是**遍历所有网络**，容器接了两个网络，两个 IP 就被无分隔地拼成一串。
- **修法**：用 `{{index .NetworkSettings.Networks "项目_默认网络"}}` 精确定位到某个网络再取 `IPAddress`；或者 `docker inspect -f` 里指定网络名。
- **验证**：脚本输出单行单 IP，`curl` 返回 200，不再出现 `000`。

**关键句**：「`range` 是遍历，`index` 是取值——**取值要用 index，不然多网卡就拼串**。这个坑的本质是"数据结构没想清就开始拼字符串"。」

**追问连击**
1. 「为什么不直接用容器名？」→ 可以（自定义 bridge 有内嵌 DNS），我两个都配了：DNS 优先、固定 IP 兜底。
2. 「固定 IP 有什么风险？」→ 容易和别的服务撞 IP，且扩缩容要改配置；所以只在小规模、稳定的编排里用。
3. 「`000` 是什么？」→ curl 的"连接根本没建立"，不是 HTTP 状态码——**这个细节在坑 18 里还会用一次**。

**陷阱**：如果你说"我用了 `{{range}}`"，懂 Go 模板的面试官会立刻问"两个网络怎么办"。

## P04 · 「`/health` 为什么单独开一个路径？」

**触发句**：简历「Nginx 被动健康检查，`/health` 返回 200」

**答题骨架**
- **现象**：`/api/stats` 正常，`/health` 一直失败，负载均衡认为两个节点全挂。
- **根因**：`location /health` 是**前缀匹配**，被更宽松的 `location /` 或 `location ~ \.php$` 抢走了，请求被转到业务首页，返回 HTML 而不是 `200 OK`。
- **修法**：改成 `location = /health`（**精确匹配**，优先级最高），让它不被任何前缀/正则规则抢走。
- **验证**：`curl -I http://节点/health` 看到裸 `200`，`Content-Type` 不是 `text/html`。

**关键句**：「location 匹配优先级是 `=` 精确 > `^~` 前缀 > 正则 > 普通前缀，**健康检查这种"必须命中"的路径只能用 `=`**。」

**追问连击**
1. 「健康检查要不要查数据库？」→ 我的 `/health` 只返回 200，不查库——查库会让"数据库抖动"变成"节点全部摘除"，风险放大。
2. 「那怎么发现数据库挂了？」→ 单独一条告警（坑 21 的复制状态监控 + 应用层错误率），而不是靠 LB 摘节点。
3. 「`^~` 和 `=` 区别？」→ `^~` 是"前缀匹配但不再试正则"，`=` 是"必须完全相等"。

**陷阱**：说"加了个 location"就完了会被追问优先级；这是纯 nginx 基本功。

## P05 · 「你怎么验证轮询真的生效了？」

**触发句**：简历「双节点轮询负载均衡」

**答题骨架**
- **现象**：`curl` 连打十次，节点 A/B 交替出现；但**浏览器刷新页面，永远同一个节点**。
- **排除**：先怀疑配置写错，`nginx -T` 看到 upstream 确实是默认轮询；再怀疑缓存，加了 `no-cache` 头还是一样。
- **根因**：**一次页面刷新不是一个请求**——浏览器会并发发 favicon、静态资源等多个请求，加上 keep-alive 复用连接，视觉上就"总落在同一个节点"。
- **修法**：验证方法改成"**逐条 curl**"或看 access log 里的 upstream 字段统计，不看浏览器观感。
- **验证**：`awk` 统计日志里两个上游的请求数，比例接近 1:1。

**关键句**：「**观测方式本身可能制造假象**——不是负载均衡没生效，是我的观测粒度错了。」

**追问连击**
1. 「keep-alive 会破坏轮询吗？」→ 会。同一连接上的请求都走同一上游，所以要么关 keep-alive，要么用连接数/最少连接算法。
2. 「日志里怎么看出打到哪个节点？」→ 自定义 log_format 里加 `$upstream_addr`、`$upstream_response_time`——这也是坑 22 的由来。
3. 「默认算法是什么？」→ 加权轮询（weight 默认 1）。

**陷阱**：这题和坑 18、23 是同一类——**"你凭什么相信你看到的"**。三题答案要一致，不能一题说"看日志"、一题说"看页面"。

## P06 · 「你说的超时，是连不上，还是连上了不回话？」

**触发句**：简历「故障摘除 6s→2s，`proxy_connect_timeout` 3s→1s」

**答题骨架**
- **现象**：日志里两种 `upstream timed out`：`while connecting to upstream` 和 `while reading response header from upstream`，我一开始当成一回事。
- **根因**：这是**两个阶段、两种病**。connecting 超时 = TCP 都没建起来（节点死了/网络不通/端口没开），对应 `proxy_connect_timeout`；reading 超时 = 连上了但后端不回话（应用卡住、SQL 慢、死锁），对应 `proxy_read_timeout`。
- **修法**：分而治之。`connect_timeout` 从 3s 砍到 1s（快速识别死节点，这是摘除时间 6s→2s 的来源）；`read_timeout` 保持较长（后端真的慢时不该被误杀）。
- **验证**：`docker stop` 一个节点，摘除时间从 6s 降到 2s，且切换期间请求**变慢但不失败**；反过来造一个"连得上但慢"的场景，请求走的是 read 超时不是 connect 超时。

**关键句**：「**连不上和连上了不回话，根因和修法完全不同**——一个要缩短超时快速摘除，一个要延长超时避免误杀。混在一起调，必然一边治好了另一边恶化。」

**追问连击**
1. 「摘除时间怎么算的？」→ `max_fails × (connect_timeout + 重试)`，2 × 1s ≈ 2s；原来是 2 × 3s = 6s。
2. 「`proxy_next_upstream` 默认重试什么？」→ `error timeout`，所以连接失败会换节点；但 POST 非幂等请求要谨慎。
3. 「后端真的慢怎么办？」→ 那是 `request_slowlog_timeout` + 慢日志的活（坑 15），不是靠调 nginx 超时解决。

**陷阱**：这是 25 条里最"一句反问显功力"的题（踩坑记录原话）。**如果面试官只问"超时怎么调"，你要主动把这句反问抛回去**——"您说的超时是连接阶段还是读取阶段？"——这是加分动作，不是抬杠。

## P07 · 「主从断了你怎么定位？先看什么？」

**触发句**：简历「MySQL 8.0 主从复制，延迟告警」

**答题骨架**
- **现象**：`SHOW SLAVE STATUS\G` 里 `Slave_IO_Running: Yes`、`Slave_SQL_Running: No`，数据不再更新。
- **排除/定位**：先看**哪个线程是 No**——IO 线程挂 = 网络/认证/主库 binlog 问题；SQL 线程挂 = 数据层冲突。我这台是 SQL 线程挂，直接看 `Last_SQL_Error`。
- **根因**：初始化从库用的是带 GTID 历史的全量备份，从库重放时发现"这个 GTID 我执行过"，直接停住。
- **修法**：导出时加 `--set-gtid-purged=OFF` 去掉 GTID 信息，清空从库重新初始化。
- **验证**：两个线程都 Yes、`Seconds_Behind_Master`（8.0.23+ 叫 `Seconds_Behind_Source`）归零、两边 `count(orders)` 都是 300000。

**关键句**：「**先看哪个线程挂，再决定往哪查**——IO 线程挂查网络，SQL 线程挂查数据。这个口诀能省掉一半排查时间。」

**追问连击**
1. 「GTID 是什么？」→ 全局事务标识，保证一个事务在集群里只执行一次；重放时按 GTID 去重。
2. 「主从延迟大怎么办？」→ 并行复制（MTS）、从库别跑重查询、必要时读写分离时容忍短暂延迟。
3. 「怎么验证主从一致？」→ 关键表 count + 校验和，严格用 `pt-table-checksum`。

**陷阱**：如果你说"重启从库就好了"，会被追问"那数据一致吗"——重启只是跳过错误，**会留下数据缺口**。

## P08 · 「你的主从延迟告警，是怎么确认有效的？」

**触发句**：简历「Zabbix 4 条触发器：复制落后 > 60s、磁盘 > 85%…」

**答题骨架**
- **现象**：故意让从库停掉复制、延迟涨到几分钟，Zabbix 里**一条告警都没有**。
- **排除**：触发器表达式看了没问题、item 有数据、action 也 enabled——三层都"对"。
- **根因**：从 **MySQL 8.0.23** 起，`Seconds_Behind_Master` 字段**改名成 `Seconds_Behind_Source`**，我的监控脚本还在 grep 老字段名，取到空值，条件永远不成立。
- **修法**：正则改成 `Seconds_Behind_(Source|Master)` 兼容两个版本；再把取值为空的场景单独做成一条"监控项异常"告警——**取不到值本身就该告警**。
- **验证**：再次制造延迟，60 秒内收到告警；恢复后收到 RESOLVED。

**关键句**：「字段改名不会报错，只会**静默地取到空值**——所以监控脚本必须带"取不到值就告警"的兜底，否则版本升级就是监控集体失明。」

**追问连击**
1. 「还有哪些 8.0 的改名？」→ `SHOW SLAVE STATUS` → `SHOW REPLICA STATUS`，`master_*` 系列变量 → `source_*`。
2. 「为什么取空值要单独告警？」→ 因为空值会让所有阈值判断失效，属于"监控自己坏了"，必须和业务告警分开报。
3. 「灰度升级时怎么避免？」→ 监控脚本先兼容两套字段，再升级数据库。

**陷阱**：这题很容易被追问成"你怎么做版本兼容"，答"我在脚本里用正则兼容"比"我升级了脚本"高一级——**兼容 > 修正**。

## P09 · 「你说容器日志限制到 10m×3，那磁盘为什么还会涨？」

**触发句**：简历「容器 json-file 10m×3，灌 40MiB 实测 28M」

**答题骨架**
- **现象**：`max-size` 配好了，`docker inspect` 里也能看到，但 `logs/nginx` 目录下的文件只增不减，最后把磁盘吃满。
- **根因**：日志有**两个出口**。容器 stdout/stderr 落在 `/var/lib/docker/containers/` 下，归 Docker 的 `max-size` 管；而 nginx 的 `access.log`、mysql 的 `slow.log` 是应用**写进挂载目录的普通文件**，Docker 完全不管——**只配 max-size 等于只锁了前门**。
- **修法**：两层。容器层 compose 里用 YAML 锚点统一 `10m×3`（实测灌 40MiB 停在 3 个文件共 28M）；文件层 `logrotate` 按天 + 20M 上限、留 7 份。
- **验证**：轮转后**再发一次请求**看新的 `.log` 有没有内容——光看到 `.1` 出现不算成功。

**关键句**：「`max-size` 只管 stdout，**应用自己写的文件它当普通文件**。所以日志治理要按"谁在写"分，不是按"哪里看"分。」

**追问连击**
1. 「为什么是 28M 不是 30M？」→ Docker 写入前检查，每个文件停在 9.6M 左右；40MiB 需要 4.2 个文件，`max-file=3` 只留 3 个，最旧的被删。
2. 「nginx 和 mysql 的轮转方式能一样吗？」→ **不能**。nginx 收 USR1 重开 fd，用 rename + create；mysqld 没这个信号，只能 `copytruncate`。照抄的话 mysqld 会一直写已改名的旧文件，新 `slow.log` 永远是 0 字节。
3. 「`docker logs` 看不到轮转掉的历史怎么办？」→ 这是取舍：要长期保留就换 syslog/fluentd 驱动或应用直接写文件，代价是磁盘自己管。

**陷阱**：这题的关键不是"我加了 logrotate"，而是**"我发现有两个出口"**——面试官想听的是你的模型对不对，不是命令。

## P10 · 「`Errcode 13` 是什么？为什么容器写不了挂载目录？」

**触发句**：简历「bind mount 挂载配置与代码」

**答题骨架**
- **现象**：MySQL 容器起不来，日志 `mysqld: Can't create/write to file ... (Errcode 13 - Permission denied)`。
- **根因**：bind mount 时内核比对的是**数字 UID**。镜像里的 `mysql` 用户是 **UID 999**，宿主机目录属主是 root，容器内 999 没有写权限。
- **修法**：宿主机 `chown -R 999:999 data logs/mysql`——**必须写数字**，写 `mysql:mysql` 会报 `invalid user`，因为宿主机上根本没有这个用户。
- **验证**：`ls -ln` 看到属主是 `999 999`，容器起来且 `healthy`，`docker exec` 进去能写文件。

**关键句**：「**内核只认数字 UID，不认用户名**。跨宿主机和容器谈权限，一律用数字。」

**追问连击**
1. 「怎么确认镜像是 999？」→ `docker run --rm mysql:8.0 id mysql`，或者 `docker image inspect mysql:8.0 --format '{{.Config.User}}'`。
2. 「为什么数据库用 named volume 就没这问题？」→ volume 由 Docker 创建，会按镜像里的属主初始化，权限天然正确。
3. 「SELinux 开着还会怎样？」→ 除了 uid，还有标签问题，要加 `:z` 或 `:Z`。

**陷阱**：这题答完 uid，面试官常顺手问 SELinux——两个都是"权限对但写不了"，别混为一谈（一个是 DAC，一个是 MAC）。

## P11 · 「`compose` 报 `no configuration file provided`，为什么？」

**触发句**：简历「一键 `docker compose up -d` 部署」

**答题骨架**
- **现象**：在项目根目录执行能跑，写进脚本后报 `no configuration file provided: not found`。
- **根因**：compose **只在当前工作目录**找 `compose.yaml`/`docker-compose.yml`，脚本里如果没先 `cd` 过去（或被 cron 在别处调起），就找不到。**不是 `-f` 没写的问题，是工作目录的问题**。
- **修法**：脚本里显式 `cd "$(dirname "$0")/.."`，或者每次都带 `-f /绝对路径/docker-compose.yml -p 项目名`。我选前者 + `-p` 固定项目名，避免目录名带下划线之类的意外。
- **验证**：从 `/tmp` 用绝对路径调脚本，同样能起来。

**关键句**：「**脚本里的相对路径一律不可信**——要么 `cd` 到脚本所在目录，要么全用绝对路径。这个坑在坑 17 里又踩了一次（换台机器脚本跑不起来）。」

**追问连击**
1. 「`-p` 有什么用？」→ 固定项目名，容器和网络前缀不变；不写就取目录名，改名目录会导致"新起一套"。
2. 「cron 里怎么保证能跑？」→ 脚本内自己 `cd`，不依赖调用者的 cwd（坑 13 的同类问题）。
3. 「`compose` 和 `docker-compose` 区别？」→ v2 是插件（`docker compose`），v1 是独立 python 程序；v1 已停止维护。

**陷阱**：这题看着简单，但**它和坑 13、17 是同一条主线：环境假设**。能主动把三者串起来说，会给面试官"这人知道自己在踩什么"的印象。

## P12 · 「你的 Zabbix 告警链路，怎么保证不是自己坏了？」

**触发句**：简历「Zabbix 7.0，4 条触发器，Webhook 推钉钉，验证过 PROBLEM 和 RESOLVED」

**答题骨架**
- **现象**：触发器有事件、Action log 一片空白、钉钉一声不响，而且**连失败记录都没有**。
- **排除**：触发器表达式对、action 启用、webhook 脚本能单独跑通——每层都"对"。
- **根因**：**告警媒介的收件人为空时，Zabbix 会静默丢弃**，直接不投递、不写日志。所以"配置全对但没发出去"是可能的，而且不留痕。
- **修法**：给媒介配收件人（用户 → 媒介 → 收件地址三层都要填）；同时加一条**自检告警**：每天定时发一条测试消息，收不到就说明通道坏了。
- **验证**：手动制造一次 PROBLEM，钉钉收到；恢复后收到 RESOLVED；再跑一次测试告警。

**关键句**：「**没有告警 ≠ 一切正常，可能只是告警坏了。** 所以监控系统自己也要被监控——这就是我加心跳的原因。」

**追问连击**
1. 「怎么发现监控自己挂了？」→ 心跳：被监控对象定期上报"我还活着"，**超时本身触发告警**；或者用第二个通道交叉验证（邮件 + 钉钉）。
2. 「告警太多怎么办？」→ 分级（Average/High/Disaster）、同类合并、连续 N 次才触发。
3. 「RESOLVED 也要发吗？」→ 要。只发故障不发恢复，人会一直以为还在故障里。

**陷阱**：这题是全套里**最容易被"聪明人"误判**的一条（踩坑记录原话：三种特征集齐）。如果你能说出"每一层都查过且都对，所以只能逐层看数据库表把假设一个个否掉"，比说结论更有说服力。

## P13 · 「133ms 降到 0.11ms，这个数字你是怎么测的？」

**触发句**：简历「慢查询优化：分页查询 133ms → 0.11ms」

**答题骨架**
- **现象**：优化前后四条查询，JOIN 那条**两轮都是 66ms**，看着像"索引完全没用"。
- **排除**：查了执行计划，type 确实变 ref 了；再看四条的耗时——**多个无关查询收敛到同一个值**，这不可能，说明测的不是查询。
- **根因**：我用 `date` 包在 `docker exec` 外面计时，**docker exec 启动进程本身要 30–70ms**，把 0.1ms 的查询差异彻底淹没了。**测量工具成了瓶颈。**
- **修法**：换成 `EXPLAIN ANALYZE` 看服务端 `actual time`，或者干脆在库内用 `profiling`/慢日志。JOIN 那条实际只要 0.14ms，根本不用优化。
- **验证**：同一个指标换工具复测，数值稳定；再用 `EXPLAIN` 的 `rows` 从全表 30 万变 20 做交叉验证。

**关键句**：「**先怀疑测量，再怀疑结论。** 四条无关查询给出同一个数字，就是工具在报时，不是数据库在报时。」

**追问连击**
1. 「分页为什么能快 1200 倍？」→ `LIMIT 20` 只要定位到起点读 20 行，索引把"扫 30 万行"换成"B+ 树定位"。
2. 「分组那条为什么只有 2.2 倍？」→ 索引减少的是**回表**，减少不了**必须扫的行数**；聚合命中比例高时该上预聚合。
3. 「哪条你判断不用优化？」→ Q4 本来就快——**判断"不需要优化"也是能力**，别为了显得努力去改一个不慢的查询。

**陷阱**：这题最危险的地方是"你优化了四条，但只有一条有效果"。如果你把三条"没变快"藏起来只说最好看的那条，被追问"另外三条呢"就崩了。**主动说三条没变快，反而是加分项。**

## P14 · 「QPS 从 12.6 到 794，63 倍提升可信吗？」

**触发句**：简历「ab -n 500 -c 20，QPS 12.6 → 794」

**答题骨架**
- **方法**：两组对照（`?nocache=1` 强制回源 vs 走缓存），每组跑两次：回源 12.62 / 12.63，缓存 819.74 / 793.93，**两次偏差 < 3%**。
- **为什么可信**：同一台机器、同一份数据、只差一个参数；而且 12.6 能反推验证——回源 79ms/请求，1000÷79≈12.6。
- **关键解读**：ab 的 `Failed requests` 有几百，看着吓人，但拆开 Connect/Receive/Exceptions 全是 0，**全是 Length**——页面里有实时耗时和 session id，每次响应长度不同，ab 把"长度变化"也记成 failed。判断标准是看 **Non-2xx** 有没有出现。
- **边界**：瓶颈已经转移。800 QPS 时 PHP-FPM 的 `pm.max_children=8` 和 2 核 CPU 到顶了——**缓存不会让 QPS 无限涨，瓶颈永远在下一个环节**。

**关键句**：「压测报告里最该看的不是 QPS，是**失败请求的构成**和**下一个瓶颈在哪**。」

**追问连击**
1. 「两个 Time per request 看哪个？」→ 一个是所有请求的平均（倒数=QPS），一个是每连接平均（≈前者×并发），看错列数字差 20 倍。
2. 「为什么不用 wrk/jmeter？」→ 目标是对比缓存开关两个稳态，ab 够轻；要模拟复杂场景才上 jmeter。
3. 「生产上能这么压吗？」→ 不能。生产压测要限速、错峰、有回滚预案，从低并发起步。

**陷阱**：「600 个失败请求」是这道题的**地雷**。面试官看到这个数字大概率会问"为什么有失败"，答不出"Length ≠ 真失败"就等于承认压测结果不干净。

## P15 · 「恢复演练 17 秒，你怎么判断库真的好了？」

**触发句**：简历「备份恢复演练：8.3M 全量，17 秒恢复，orders 30 万行一致」

**答题骨架**
- **现象**：演练报告"恢复完成，耗时 **0 秒**"，同时报 `Access denied`。
- **排除**：**0 秒是最关键的信号**——8M 的库不可能 0 秒灌完，说明数据根本没被消费。如果是包坏了会报 SQL 语法错；报认证错，说明问题在连接阶段。
- **根因**：我用 `mysqladmin ping` 判断临时库就绪，但它**只问服务器有没有响应，认证失败也返回 0**。而 mysql 镜像启动时会先起一个临时实例做初始化，那会儿 socket 在听、root 还没密码——ping 通过、带密码连被拒，我等于在 MySQL 没准备好时就开始导。
- **修法**：改成 `mysql -e 'SELECT 1'`（**验到业务层**），就绪等待从 0 秒变成真实的 16 秒。
- **验证**：三项对账——表数量、`orders` 行数 300000、索引数量，全和生产一致。

**关键句**：「**"服务活着"和"服务可用"是两件事**，就绪判断要验到业务层。0 秒不是快，是没干活。」

**追问连击**
1. 「还有哪个坑？」→ 全量备份包含 `mysql` 系统库，恢复时把 root 密码覆盖成生产密码，临时库换密码就连不上——所以恢复脚本要么带上原密码，要么只恢复业务库。
2. 「怎么防止假阳性复盘？」→ 报告里必须有一个"**不可能为 0** 的指标"（比如耗时、行数），为 0 就直接判定失败。
3. 「为什么用临时容器而不是恢复到生产库？」→ 演练不能碰生产；临时容器用完即删，干净且可重复。

**陷阱**：这是**印象最深故障的首选素材**。讲的时候顺序必须是 现象（0 秒）→ 排除（不是包坏）→ 根因（ping 假阳性）→ 修法 → 验证，**不能一上来就说"我用了 mysqladmin ping 有问题"**——那就变成了背答案。

## P16 · 「备份脚本怎么拿到主从状态的？为什么不用 sed 直接切？」

**触发句**：简历「备份脚本自动记录复制状态，异常告警」

**答题骨架**
- **现象**：同一句 SQL，我在终端里跑得好好的，脚本里却报 `running=0`（明明两个 Yes）。
- **根因**：脚本为了去掉表格线用了 `mysql -B`（batch，制表符输出），而 `-B` **覆盖了 `\G` 的垂直输出**——`\G` 本来把每行变成 `字段: 值`，被 `-B` 一压就成了横向表格，我的 `sed` 一条都匹配不上。
- **修法**：要么去掉 `-B` 保留 `\G` 用 `sed -n 's/.*Slave_SQL_Running: //p'`，要么保留 `-B` 改成 `awk -F'\t'` 按列取。
- **验证**：脚本输出 `io=Yes sql=Yes lag=0`，并在从库停掉复制时能正确报 `sql=No`。

**关键句**：「**两个都能"去格式"的参数叠在一起会互相打架**——`-B` 和 `\G` 只能留一个。」

**追问连击**
1. 「`\G` 是什么？」→ mysql 客户端的行结束符，把结果竖向展开，适合宽表。
2. 「为什么不用 `--skip-column-names`？」→ 那个只去表头，不改变分隔方式，和 `-B` 是互补的，不冲突。
3. 「怎么让脚本更稳？」→ 用 `mysql --batch --skip-column-names -e "SHOW REPLICA STATUS"` + `awk` 按 `\t` 取字段，避免依赖任何客户端渲染。

**陷阱**：这题的真相是"**命令在交互式和脚本里行为不同**"，和坑 13（cron）、坑 17（换机器）是同一族。

---

## P17 · 「你的备份包排除规则是怎么写的？」

**触发句**：简历「备份脚本排除临时文件与旧包」

**答题骨架**
- **现象**：`tar: --exclude ... has no effect`，或者排除了等于没排除，备份包还是把 `logs/` 全带上。
- **根因**：GNU tar 的 `--exclude` **位置敏感**——写在被操作的文件名**之后**就不生效，因为它已经把参数解析完了。而且我 `bash -n` 检查过，语法完全合法，跑起来只报两个字的"失败"。
- **修法**：`--exclude` 必须放在**文件名之前**：`tar -czf out.tar.gz --exclude='./tmp' -C /src .`；模式要和归档内路径一致（`./tmp` 而不是 `tmp`）。
- **验证**：先 `tar -tzf` 看清单里有没有该排掉的东西，再对比包大小。

**关键句**：「**语法合法 ≠ 参数生效。** 我在这条上连续猜错两次（先猜通配符跨 `/`，再猜磁盘满），最后是让命令自己说话——把 stderr 打出来才看到那句 `has no effect`。」

**追问连击**
1. 「为什么 `bash -n` 查不出来？」→ 它只查语法，不查选项语义。
2. 「还有哪些命令位置敏感？」→ `find` 的 `-delete` 必须在末尾、`rsync` 的 `--exclude` 顺序、`tar` 的 `-f` 要在文件名前。
3. 「怎么避免？」→ 危险命令先在临时目录小样本验证，把 stderr 完整打出来，不吞错误。

**陷阱**：这题最值钱的是"**我连续猜错两次**"的坦白。面试官听多了"一次就找到"，反而会怀疑。

---

## P18 · 「改了代码，容器里为什么没变化？」

**触发句**：简历「代码 bind mount 热更新，配置只读挂载」

**答题骨架**
- **现象**：本地改了 PHP 文件，刷新页面行为没变。
- **排除**：`docker exec` 进去 `cat` 那个文件——**容器里还是旧内容**，说明文件根本没同步进去。
- **根因**：这个服务在 Dockerfile 里用 `COPY` 把代码**打进镜像**了，而 compose 里没给它配 bind mount。改的是宿主机文件，跑的是镜像里的副本。
- **修法**：要么 compose 里加 bind mount（开发），要么 `--build` 重建镜像（生产）。**两种语义不能混**：镜像里的代码是"发布物"，挂载的代码是"开发态"。
- **验证**：改一行注释，容器内 `cat` 能看到；`docker inspect` 看 `Mounts` 确认挂载生效。

**关键句**：「`COPY` 是**某一刻的快照**，挂载是**实时视图**。问"改了为什么没生效"，先问"这个文件是从镜像来的还是挂载来的"。」

**追问连击**
1. 「生产为什么不用挂载？」→ 发布不可控，回滚要改宿主机文件；镜像才是可版本化、可回滚的发布物。
2. 「`--build` 每次都全量重建吗？」→ 不，BuildKit 有层缓存，只有变动的层和之后的重建。
3. 「怎么确认容器用的是哪个镜像？」→ `docker inspect -f '{{.Image}}'` + `docker images --digests`。

**陷阱**：这题会和"镜像分层 / 可写层"连着问，准备一句「容器 = 镜像只读层 + 一个可写层，挂载是外挂的另一块存储」兜住。

## P19 · 「配了镜像加速器，为什么拉取还是慢？」

**触发句**：简历「配置 Docker 镜像加速器」

**答题骨架**
- **现象**：`docker pull` 快，但 `Dockerfile` 里 `FROM` 一个手写全域名的镜像就报 `pull access denied` / 超时。
- **根因**：加速器（`registry-mirrors`）只对**短名**（如 `mysql:8.0`）生效，它帮你补 `docker.io/library/` 前缀再走镜像站；如果你写全了 `docker.io/library/mysql`，就**绕过**了 mirror 直接连源站。
- **修法**：Dockerfile 和 compose 里统一用短名；确实要用别的仓库（如 `ghcr.io`）就单独配 `--build-arg` 或提前 `docker pull` + 本地 tag。
- **验证**：`docker info` 看 `Registry Mirrors`，然后 `docker pull` 一个有 `FROM` 的镜像观察下载速度。

**关键句**：「加速器是**对短名的重写**，不是全局代理——写全域名等于自己绕开了它。」

**追问连击**
1. 「`apk add` 慢能靠加速器吗？」→ 不能。加速器只管镜像层，apk 包要从 Alpine 的 CDN 下，得单独换源（`sed -i` 换清华源），这也是我 Dockerfile 里那行 `sed` 的由来。
2. 「daemon.json 改了要重启 docker 吗？」→ 要（`systemctl reload docker` 也行，但镜像加速一般建议 restart）。
3. 「还有哪些地方会绕过加速器？」→ `docker build` 的 `FROM`、`compose` 的 `build.context` 外网依赖、`ADD` 远程 URL。

**陷阱**：这题是很好的"知其所以然"题——很多人配了加速器但说不清它作用于哪一层。

## P20 · 「cron 里的备份任务，为什么手动能跑、定时不跑？」

**触发句**：简历「cron 每日 03:00 备份，7 天保留」

**答题骨架**
- **现象**：手动 `bash mysql_backup.sh` 一切正常，第二天看备份目录是空的，`/var/log/cron` 里却有执行记录（说明 cron 真的触发了）。
- **排除顺序**：① `systemctl status crond` 活着 ② `/var/log/cron` 有该时刻记录 ③ 脚本有可执行位 ④ 手动跑成功 → 说明问题在**执行环境**，不在脚本逻辑。
- **两个根因**：
  - **PATH**：cron 的 PATH 只有 `/usr/bin:/bin`，脚本里调 `docker`/`mysqldump` 找不到 → crontab 首行显式 `PATH=`，脚本内用绝对路径。
  - **CRLF**：脚本在 Windows 上编辑过，第一行 `#!/bin/bash\r` → 报 `/bin/bash^M: bad interpreter` → `dos2unix` 转成 LF。
- **验证**：`bash -x` 在 cron 环境里跑（`env -i` 模拟），日志里带 `date` 时间戳确认是定时触发的。

**关键句**：「cron 的失败是**静默的**——输出当邮件发，邮件没配就等于扔了。所以任务必须自己写日志，还要有"成功也写一行"的心跳。」

**追问连击**
1. 「怎么模拟 cron 环境？」→ `env -i /bin/bash --noprofile --norc script.sh`，PATH 只剩默认值，能复现大部分问题。
2. 「怎么防重叠？」→ `flock -n`，大库备份跑不完时下一天不该再起一个。
3. 「为什么还要心跳？」→ 脚本告警只能覆盖"跑了但失败"，**没跑**的情况（cron 挂了、机器重启）只有心跳能发现。

**陷阱**：三坑（PATH/CRLF/权限）要能一句话分清，别说着说着混起来。

## P21 · 「你说故障演练 20 次全成功，那 9 次失败是怎么回事？」

**触发句**：简历「故障演练 20 次，切换成功率 100%」

**答题骨架**
- **现象**：演练报告写了 20 次，9 次标记失败，失败原因全是 `000`，每次耗时约 3 秒。
- **排除**：如果是真挂，`000` 应该连续出现；实际是**交替出现**（一次成功一次 000），而且失败的那次正好卡满 3 秒。
- **根因**：三件事叠在一起——① curl 的 `-m` 超时撞上了 nginx 的 `proxy_connect_timeout`；② 切换瞬间客户端连接被重置，curl 返回 `000`（连接未建立），这属于**切换的必然代价**，不是服务不可用；③ 请求实际上已经被后端处理了（日志里有 499），但客户端没等到响应。
- **修法**：判定标准从"curl 退出码"改成"**后端是否产生了 2xx/3xx 响应**"——499 是客户端主动断开，不该计入失败；演练脚本加"重试一次"的容错，因为用户真实场景也会重试。
- **验证**：改判定标准后重跑 20 次，失败数归零，且日志里能看到切换期间的 499 分布。

**关键句**：「**看起来挂了 9 次，其实一次都没挂**——挂的是我的判定标准，不是服务。」

**追问连击**
1. 「499 是什么？」→ nginx 自定义状态码：客户端在服务端响应前关闭了连接。
2. 「切换期间用户到底受影响吗？」→ 受影响的是那一次请求的延迟（约 3 秒后重试成功），不是可用性。
3. 「那 100% 是不是美化了？」→ 不是美化，是**定义**：可用性按"最终有正常响应"算，切换瞬间的重试不算故障。但我必须在报告里写清口径。

**陷阱**：这是**最容易讲出彩**的一条（踩坑记录把它排第一）。但一定要先承认"9 次失败是我一开始的判定"，再讲口径——**先认账再翻案**，顺序反了就成了狡辩。

# 第三部分 · 技能条与通用（P22–P26）

## P22 · 「nginx 配置语法没错，为什么容器起不来？」

**触发句**：简历「自定义 access log 格式（upstream_addr / response_time）」

**答题骨架**
- **现象**：`nginx -t` 通过（在宿主机上测的），容器 `Exited (1)`，日志 `"log_format" directive is not allowed here`。
- **根因**：`log_format` 只能写在 **http 上下文**，而我把它写进了 `server{}`。`conf.d/*.conf` 本身是被 `http{}` include 的，所以**同一行代码放在文件顶层就对，放在 server 块里就错**。
- **修法**：把 `log_format` 挪到文件顶层（http 上下文），`access_log` 引用格式名留在 `server{}` 里。**内容一个字没改，只动了位置。**
- **验证**：`docker exec lnmp-nginx nginx -t` 通过；再发请求看 access log 里 `up_addr=... rt=...` 有值。

**关键句**：「指令合法性看的是**最终落在哪一层花括号**，不是写在哪个文件里。所以 `nginx -t` 必须在**容器里**跑，宿主机上的 nginx 和容器的配置树不是一棵。」

**追问连击**
1. 「http / server / location 各能放什么？」→ `log_format`/`upstream`/`map` 在 http；`listen`/`server_name`/`location` 在 server；`proxy_*`/`access_log` 大多都能在 location。
2. 「怎么快速定位错误行？」→ `nginx -t` 会给出文件名和行号；容器里 `docker exec` 同一份配置，报的行号直接可查。
3. 「配置热加载怎么不生效？」→ `reload` 会先校验配置，校验失败就保持旧配置继续服务——**所以 reload "没报错"也不代表新配置生效了**，要看 worker 的启动时间。

**陷阱**：这题和 P18（改代码没生效）、P20（cron 环境）同属"**环境不同、结果不同**"家族，能主动归类会显得有体系。

## P23 · 「接口报 500，`Object of type Decimal is not JSON serializable` 怎么处理？」

**触发句**：简历「订单查询接口，30 万行订单数据」

**答题骨架**
- **现象**：`/api/stats` 正常，`/api/orders` 稳定 500，堆栈指向 `json.dumps`。
- **根因**：MySQL 的 `DECIMAL` 字段被驱动返回成 Python 的 `Decimal` 对象，**它不是 JSON 原生类型**，`json.dumps` 不认识就抛异常。**数据库类型 ≠ JSON 类型**，中间少了一层转换。
- **修法**：给 `json.dumps` 传 `default=str`（最简单），或者自定义 `JSONEncoder` 处理 `Decimal`/`datetime`：`Decimal` 建议 `str` 而不是 `float`，避免金额精度丢失。
- **验证**：接口返回 200，金额字段是 `"199.00"` 字符串，前端展示正常；再跑一次全量接口回归。

**关键句**：「跨系统传数据时，**类型系统一定有边界**——数据库的 decimal、datetime 都不是 JSON 的，必须显式转换，不能指望序列化库自己猜。」

**追问连击**
1. 「为什么用 str 不用 float？」→ 金额用 float 会丢精度（0.1+0.2），`str` 保留原值，前端自己决定怎么显示。
2. 「为什么只有订单接口挂？」→ 只有它查了 `DECIMAL` 字段（价格/金额），别的接口都是整数和字符串。
3. 「这算后端 bug 还是 ORM 的问题？」→ 是**序列化边界没处理**，不是 ORM 的错——ORM 忠实返回了数据库类型。

**陷阱**：回答"加个 default=str 就好了"只到 L1；要说出"**为什么会有这个边界**"才是 L2 以上。

## P24 · 「服务器上 curl 是通的，外网为什么访问不了？」

**触发句**：简历「腾讯云轻量 2C2G，安全组放行 80/443」

**答题骨架**
- **现象**：`curl 127.0.0.1` 200、`curl 内网IP` 200，但公网 IP 超时。
- **排除链**：① 服务在听吗 → `ss -tlnp` 看到 `0.0.0.0:80` ✅ ② 系统防火墙 → `firewall-cmd --list-all` 里 80 没放行 ❌ ③ 云安全组 → 也没放行 ❌。**两道门都关着。**
- **根因**：**云上永远有两层防火墙**——系统内 firewalld 和云平台安全组是独立的两套规则，缺一层就不通。
- **修法**：`firewall-cmd --add-service=http --permanent && firewall-cmd --reload`；控制台安全组加 80/443 入方向。
- **验证**：本机 `curl`、外网 `curl`、浏览器三条路都通；再故意关掉一层复现，确认两层都必要。

**关键句**：「**系统防火墙和云安全组是两道独立的门，都要开**。只查一层的人会在云上耗掉半天。」

**追问连击**
1. 「监听地址也有关系吗？」→ 有，第三层：服务监听 `127.0.0.1` 时外面永远连不上（php-fpm 默认就这样，容器里 nginx 连不上）。
2. 「Docker 的 `-p` 会绕过 firewalld 吗？」→ 会。Docker 直接写 nat 表 DNAT，firewalld 管不到，等于容器端口实际对外开放——要限制就绑 `127.0.0.1:8080:80`。
3. 「怎么快速排除安全组？」→ 临时加一条 `all/0.0.0.0/0` 测通，通了再收窄到具体端口——**但要记得收回来**。

**陷阱**：这题几乎必问（技术支持岗日常），而且**三层结构（监听地址 / 系统防火墙 / 安全组）**能一口气说完的人不多。

## P25 · 「出故障时你怎么保证有日志可查？」

**触发句**：简历「日志轮转、慢日志、保留 7 份」

**答题骨架**
- **现象**：一次接口变慢，翻遍 nginx 和 php 日志**什么都没有**，只能靠猜。
- **根因**：为了"减少磁盘占用"，我把日志级别调高、`request_slowlog_timeout` 关掉了——**排障最需要的那条信息，正好被我关掉了**。
- **修法**：常开"低开销但高价值"的诊断：php-fpm 的 `request_slowlog_timeout=3s` + `slowlog`、MySQL 的 `long_query_time=0.5` + `log_queries_not_using_indexes`、nginx 的 `$upstream_response_time`。高开销的（全量 debug）才需要临时开。
- **验证**：制造一次慢请求，`slowlog` 里出现完整调用栈；`pt-query-digest`/`mysqldumpslow` 能排出 TopN。

**关键句**：「**日志是排障的弹药，不能等到出事才想起装。** 但也要有取舍——只常开"低开销高价值"的那几项，否则日志本身变成故障源（P09）。」

**追问连击**
1. 「慢日志会不会拖慢数据库？」→ `long_query_time` 太低会写很多；0.5s 在我的数据量下可接受。
2. 「怎么分析慢日志？」→ `mysqldumpslow -s t -t 10`，或 `pt-query-digest` 按总耗时排序。
3. 「日志和监控怎么分工？」→ 监控答"现在好不好"，日志答"为什么不好"；告警消息里应该带日志链接/关键字。

**陷阱**：这题和 P09（日志治理）容易互相打架——一个说"要限制日志"，一个说"要保留日志"。**正确说法是分层：能轮转的控量、关键诊断常开、高开销按需临时开。**

## P26 · 「别人拿到你的脚本，能直接跑吗？」

**触发句**：简历「脚本随仓库交付，一键执行」

**答题骨架**
- **现象**：我本机跑得好好的脚本，在服务器上报 `bash: scripts/xxx.sh: No such file or directory`，或者某个 `curl` 参数不认。
- **两个根因**：
  - **相对路径**：脚本里写了 `scripts/xxx.sh`，依赖"从仓库根目录执行"这个前提；换到别的 cwd 就找不到。
  - **版本差异**：用了某个较新 curl 才有的参数，老系统上直接报 unknown option。
- **修法**：① 脚本内部 `cd "$(dirname "$0")"` 或全用绝对路径；② 用 `curl --version` 判断能力，或换兼容写法（`-w '%{http_code}'` 这类老版本也支持）；③ 关键依赖在脚本开头做 `command -v` 检查并给出明确报错。
- **验证**：在 `/tmp`、用 `env -i`（干净环境）、换一台机器三种条件下各跑一次。

**关键句**：「**脚本的隐含假设就是它的 bug**——cwd、PATH、shell 版本、命令版本，四个假设只要有一个不成立就崩。所以脚本开头要显式声明这些假设。」

**追问连击**
1. 「怎么做出可移植的脚本？」→ `#!/usr/bin/env bash`、`set -uo pipefail`、开头检查依赖、路径基于 `$0` 推导、环境变量给默认值。
2. 「`bash x.sh` 和 `./x.sh` 的区别在交付里意味着什么？」→ 前者只要读权限，后者要执行位；仓库里 git 不保留 x 位就是常见翻车点（`git update-index --chmod=+x`）。
3. 「怎么让别人一眼知道怎么用？」→ 脚本头部写用法注释 + `DRY_RUN` 模式先预演。

**陷阱**：这题最不像"坑"但最常撞（踩坑记录原话）。答的时候要给**四个假设的清单**，而不是"我改成绝对路径了"。

# 第五部分 · 主动埋钩子：把坑变成话题

面试是双向的——你也有权利**引导面试官往你准备好的地方问**。做法是在回答里放一个"可被追问的钩子"，但**只放你接得住的**。

| 场景 | 埋钩子的话 | 他大概率会追 | 你准备好的答案 |
|---|---|---|---|
| 讲备份 | 「备份不做恢复演练等于没备份」 | 「你演练踩过什么坑？」 | P15（0 秒假阳性） |
| 讲监控 | 「告警最怕的不是漏报，是静默失败」 | 「静默失败怎么发现的？」 | P12（收件人为空） |
| 讲日志 | 「日志其实有两个出口」 | 「哪两个？」 | P09（stdout vs 应用文件） |
| 讲压测 | 「失败请求数看着吓人，但要看构成」 | 「构成怎么看？」 | P14（Length ≠ 错误） |
| 讲高可用 | 「切换期间用户会感觉慢一下，但不会失败」 | 「你怎么证明？」 | P21（9 次失败是口径问题） |
| 讲索引 | 「四条查询我只优化了一条」 | 「另外三条呢？」 | P13（2.2 倍/1.24 倍/本来就快） |

**不要埋的钩子**（接不住就是自爆）：
- 别提"我还做过 K8s"——一问就露。
- 别提"我研究过内核参数调优"——除非能背出 `somaxconn` 和 `tw_reuse` 的适用条件。
- 别说"我做过压力测试到上万 QPS"——你的数字是 794，前后要对得上。

# 第六部分 · 止损话术：被问到自己没踩过的坑

25 条覆盖不了所有问题。**不会的时候，标准动作是四句话**：

1. **承认边界**：「这个我没有实际操作过，只在文档里看到过。」
2. **给出理解**：「我的理解是……（说原理，哪怕不完整）」
3. **给出路径**：「如果让我排查，我会先……（说出第一步命令和判断依据）」
4. **不编细节**：「具体现象我没见过，不敢乱说。」

> 反面教材：把别人的坑说成自己的。面试官只要追一层"当时是哪个版本的字段名"，编的就崩了——**被追问出来比主动交底掉价十倍**（这句话本身就可以用来回答"你怎么看诚信"）。
