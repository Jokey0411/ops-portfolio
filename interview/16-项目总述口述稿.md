# 16 · 项目总述口述稿（"介绍你最复杂的项目"）

> **这题什么时候出现**：一面开场、二面、HR 面、终面，几乎 100% 会问，且通常是**第一个技术问题**。
> **怎么用**：先背 90 秒版（骨架），再用 3 分钟版（血肉）。**六段顺序不能换**——面试官的追问是按这个顺序走的。
> **核心原则**：这题不是"介绍项目"，是**给面试官递刀**。你主动说出的每一个数字，都要准备好被挖三层。

---

## 一、先搞清这题在考什么（四个暗点）

| 表面在问 | 实际在考 | 答砸的信号 |
|---|---|---|
| 项目是什么 | 你能不能**用 3 句话说清一个系统** | 讲了 2 分钟还在讲"我装了 Docker" |
| 几个人做的 | **你在团队里的真实位置**，有没有协作经验 | 含含糊糊，或把别人的活说成自己的 |
| 你负责哪部分 | 有没有**边界感**（知道自己做了什么、没做什么） | "都是我做的"但追问答不上细节 |
| 系统组成/原理/架构 | **技术深度**，以及是不是"跟着教程做的" | 只会说"用了什么"，说不出"为什么用" |

**一句话结论**：这题答完，面试官心里已经给你定了档。后面所有问题都在验证这个判断。

## 二、90 秒版（先背这一版，骨架全在这里）

> 我做过的最完整的一个项目，是在**一台 2 核 2G 的腾讯云轻量服务器**上，用 Docker Compose 搭的一套**双节点高可用 Web 集群**，加上一套配套的 LNMP 性能优化环境。
>
> **我一个人做的**，从选型、写编排、配 Nginx 和 MySQL 主从，到压测调优、故障演练、写复盘文档，全部是我。所以我对这套系统的每一行配置都能说出"不加会怎样"，但也清楚它的边界——它是单机上模拟出来的集群，不是真正的跨机高可用，这一点我后面会讲。
>
> **架构上**，我用**四个自定义 bridge 网络**在一台机器上切出两个逻辑节点：
> - `front` 172.20 只放负载均衡和两个节点的 Nginx；
> - `net-node1`、`net-node2` 各自承载本节点的 web、app、db 三层；
> - `net-db` 172.23 是主从复制专网，**只有两个 MySQL 能进**。
>
> 一共 **7 个业务容器**：1 个 LB、2 组 web/app、2 个 MySQL 主从。两个数据库**都不接 front 网络**，所以从入口根本看不到数据库端口——这是最小暴露面。
>
> **请求链路**是：公网 → 云安全组 → firewalld → LB 的 80 → upstream 轮询到某个节点 → 节点的 Nginx → `/api/` 反代到本节点 app → app 连主库。两个节点共用一份 Nginx 配置，靠给 app 加 **network alias**，让 `proxy_pass http://app:8080` 各自解析到自己那个 app。
>
> **技术上最有含金量的三件事**：被动健康检查的摘除时间从 6 秒压到 2 秒；MySQL GTID 主从的搭建和一次复制中断的定位；以及配套那套 LNMP 用索引和 Redis 把 QPS 从 12.6 提到 794。
>
> **最复杂的不是某个配置，是"让故障演练真的有意义"**——单机模拟集群，节点挂了要能真的被摘掉、主从断了要能真的被发现，这逼着我把每个"看起来正常"的地方都反过来验证了一遍。

## 三、3 分钟版（主说版，按六段走）

### 第 1 段 · 项目定位（15 秒）

> 这个项目其实**不是一个项目，是一次演进**。我先在单机上做了一个 LNMP 的博客站，把它压到单机能到的最快；然后发现它有三个单点——负载均衡没有、应用没有、数据库没有，于是演进成双节点集群。
>
> 所以它同时回答两个问题：**"单机怎么跑得快"** 和 **"单机挂了怎么办"**。

> ★ 为什么这样开场：一句话就把两个项目串成一条线，比"我有两个项目"高级。面试官会更愿意顺着"演进"往下问，而演进线是你最熟的部分。

### 第 2 段 · 团队与我的角色（20 秒）

> **人数上要说实话：一个人。** 从硬件选型到文档全是我的。
>
> 分四个阶段，我在每个阶段的角色不一样：
> 1. **设计阶段**我是架构——决定网络怎么分段、依赖怎么排、存储用什么。
> 2. **搭建阶段**我是实施——写 compose、写 Dockerfile、配 Nginx、搭主从。
> 3. **调优阶段**我是 DBA 兼性能工程师——看慢日志、加索引、上 Redis、压测。
> 4. **治理阶段**我是运维——做备份、告警、心跳、故障演练、写复盘。
>
> 一个人做的**代价**是没有 code review，所以我给自己定了个规矩：**每个改动都要有验证动作**——配置改完 `nginx -t`、备份做完解包比对、告警发完补一条测试消息。这也是我后来发现"告警其实一直在静默失败"的原因。

> ★ 这段是本题最容易被低估的地方。"一个人"是双刃剑：说得好 = 全栈能力 + 自驱；说得不好 = 玩具项目 + 没人验证。**主动交底代价，比强调"全是我做的"更能拿到分。**

### 第 3 段 · 硬件与软件架构（40 秒）

**硬件侧**：

| 项 | 配置 | 说明 |
|---|---|---|
| 云主机 | 腾讯云轻量，2 vCPU / 2 GB | 2 vCPU ≈ 1 物理核的 2 个超线程，所以并发能力很有限 |
| 系统 | OpenCloudOS（RHEL 8 血统，CentOS 系） | 包管理 dnf/yum，防火墙 firewalld，SELinux 默认开启 |
| 存储 | 系统盘 + 一块数据盘 `/data` | fstab 用 **UUID** 挂载并加 `nofail`，避免云盘没挂上导致开机进 emergency |
| 网络 | 公网 IP + 云安全组 | 安全组和 firewalld 是**两层**，只开 80 和受限的 SSH |
| 运行时 | Docker + Compose v2 | `daemon.json` 配镜像加速器 + `live-restore` |

**软件侧（7 个业务容器）**：

| 层 | 服务 | 镜像 | 网络（固定 IP） |
|---|---|---|---|
| 入口 | `lb` | nginx:1.27 | front `.10` |
| 节点1 | `node1-web` | nginx:1.27 | front `.11` + net-node1 `.11` |
| | `node1-app` | 自建 Python 镜像 | net-node1 `.12`，**alias `app`** |
| | `node1-db` | mysql:8.0（主） | net-node1 `.13` + net-db `.11` |
| 节点2 | 同构 | 同上 | front `.12` / net-node2 `.11 .12 .13` |
| 存储 | `db-node1`、`db-node2` | named volume | — |

> 容器之外还有一套 Zabbix（server + web + postgres + agent2）做监控，和一套 LNMP 做性能对比，**分时启动**，不同时跑——2G 内存跑不动全部。

> ★ 这段的杀伤力在**数字密度**。能随口报出 172.20/172.23、`max_fails=2`、mysql 8.0、OpenCloudOS，说明是真做过。但**报数字要留余地**：报一个，准备被挖三层。

### 第 4 段 · 工作流程（一个请求的完整旅程，40 秒）

```
① 用户浏览器 → 域名解析到公网 IP
② 云安全组放行 80（第一道门）
③ firewalld 放行 80（第二道门）
④ 到达 lb 容器，upstream web_cluster 按加权轮询选中 node1 或 node2
⑤ 该节点的 nginx 判断路径：
     /            → 返回本地静态文件（try_files）
     /api/        → proxy_pass http://app:8080（alias 解析到本节点 app）
     /health      → 转发给 app，验证"应用活着"
     /healthz     → nginx 自己返 200，验证"nginx 活着"
⑥ app 连数据库：写走主库 node1-db，读走 Redis 缓存（miss 才回源）
⑦ 主库的变更通过 binlog → GTID → 从库 IO 线程写 relay log → SQL 线程重放
⑧ 响应原路返回，LB 在 access log 里记下 up= / ust= / urt= / rt= 四个变量
```

**这四行日志变量是整套系统的"黑匣子"**：`up` 打到哪台、`ust` 上游状态码、`urt` 上游耗时、`rt` 总耗时。出事时不用猜，四个数一比就知道慢在哪一段。

### 第 5 段 · 三个核心原理（60 秒，最有含金量的部分）

**① 被动健康检查：为什么"节点死了"不能立刻知道**

> 开源 Nginx 没有主动探测，它靠**真实请求失败**来摘除：`max_fails` 次失败后，节点进入 `fail_timeout` 的摘除窗口。
>
> 关键在于**失败要等多久才算失败**。容器被 `docker stop` 后，它在网桥上的 veth 和 IP 直接消失，之后发给它的 SYN **既不会收到 RST，也不会收到任何响应，是静默丢弃**。所以 Nginx 不会"立刻知道连不上"，它只能一直等到 `connect_timeout` 超时。
>
> 于是摘除时间 = `max_fails × proxy_connect_timeout`。原来是 2×3s = 6 秒，我把超时压到 1 秒，变成 2×1s = 2 秒。**敢压到 1 秒的前提是**：所有容器在同一宿主机同一个 bridge，RTT 小于 1 毫秒，1 秒已经极宽松；如果后端跨机房，压这么低就是误杀健康节点。
>
> 而"切换期间用户不报错"靠 `proxy_next_upstream`：超时或 5xx 时**在同一个请求内**立刻重试另一个节点。所以用户体验是"慢了一下"，不是"报错了"。

**② 主从复制：三个线程 + 一个 GTID**

> 主库一个 **dump 线程**读 binlog 发给从库；从库一个 **IO 线程**收下来写 relay log；从库一个 **SQL 线程**重放 relay log。
>
> 这个结构决定了一个万能定位口诀：**IO 线程挂查网络和认证，SQL 线程挂查数据**。我实际遇到的就是 SQL 线程 `No`：我用带 GTID 历史的备份初始化从库，重放时发现"这个 GTID 我执行过"，直接停了。修法是 `mysqldump --set-gtid-purged=OFF` 重新初始化。

**③ 索引：为什么分页快了 1200 倍，分组只快 2.2 倍**

> InnoDB 是**聚簇索引**——数据和主键索引长在一起，二级索引的叶子存的是主键值，所以走二级索引要**回表**。
>
> 分页 `ORDER BY id LIMIT` 走主键，天然有序，加了索引后从全表扫描变成范围扫描，1200 倍提升。分组 `GROUP BY` 靠索引消掉了临时表和排序，但它本来就要扫全量，所以只有 2.2 倍。**减少回表 ≠ 减少扫描行数**，这两个优化点的收益天花板不一样，这是我做完 EXPLAIN 才想明白的。

> ★ 这三段是"能不能扛住三层追问"的分水岭。**讲原理时一定要带一个反例或边界**——只说"我配了 max_fails=2"是背的，说"压到 1 秒是因为同宿主机 RTT 小于 1 毫秒"才是懂的。

### 第 6 段 · 最复杂的点 + 边界交底（30 秒）

**最复杂的地方，不是某个配置，是"让故障演练真的有意义"。**

> 单机模拟集群有个天然陷阱：节点挂了，宿主机还在，网络没抖，时钟没漂。所以我做的每一件事都得反过来验证一遍：
> - 节点真挂了，LB 真的会在 2 秒内摘掉吗？→ 写计时脚本，`docker stop` 后连打 20 次，看日志时间戳。
> - 主从真断了，监控真的会告警吗？→ 手动 `STOP REPLICA`，看 `Seconds_Behind_Source` 和告警。
> - 备份真的能恢复吗？→ 解包比对，不是看"打包成功"。
>
> 这个习惯让我抓到了几个"看起来完全正常"的坑：告警脚本的路径少了一级，配合 `2>/dev/null`，**三次备份的告警从来没发出去过，而且不报错**；恢复演练用 `mysqladmin ping` 判断能不能导数据，它认证失败也返回 0，报告显示 **0 秒"恢复成功"**，其实一条数据都没进去。

**边界（主动说，不要等他问）：**

> 这套系统有三个我明确知道的短板：
> 1. **没有真正的机器级隔离**，容器走本机网桥，练不出跨机网络抖动、时钟漂移、磁盘 IO 竞争这些真故障；
> 2. **LB 和 Redis 是单点**，应用层高可用 + 数据库主从做到了，但入口和缓存没有冗余；
> 3. **没有配置管理和发布流程**，现在是 git pull + 重建镜像，生产要有灰度、回滚、审批。
>
> 这三条我写在文档里，不影响我把负载均衡、主从、监控的机制跑通——**机制是同一套，只是故障的"风味"不同**。

## 四、"一个人做的"怎么答（这题最容易翻车）

### 三种错误答法

| 答法 | 为什么错 |
|---|---|
| "就我一个人，全是我做的" | 听起来像独狼，且没有协作证据；紧跟一句"那你怎么保证质量"就答不上 |
| 含糊说"我们团队" | 追问"你负责哪块"就露；诚信是红线，不能碰 |
| 只讲技术不讲协作 | 面试官问人数的目的就是看协作，回避等于没答 |

### 推荐答法：诚实 + 转化 + 补位

> **一个人做的**。所以我没有"分工协作"的经验可以讲，但我有另外两样东西：
>
> **一是自己给自己当 reviewer 的机制**。没有第二个人看我的配置，我就用工具代替：`nginx -t` 校验语法、`docker compose config` 校验编排、`bash -n` 校验脚本、备份做完解包比对、告警发完补一条测试消息。**每个改动都必须有一个可执行的验证动作**，这是我一个人做项目逼出来的习惯。
>
> **二是主动去外部找反馈**。我把代码和复盘文档放在 GitHub 上，按"别人能不能照着跑起来"的标准写 README——这个过程本身就暴露了很多"我自己知道但没写下来"的隐含假设。
>
> 如果是在团队里，我最想补的是**变更评审**这一环，因为我踩的坑里有一半是"当时觉得没问题"的。

> ★ 这套答法的关键是**把"没有协作"翻译成"自我约束机制"**。实习生岗不会因为你一个人做项目扣分，但会因为你答不出"质量怎么保证"扣分。

## 五、追问防御表（12 条，按出现频率排）

| 追问 | 答法（30 秒内） |
|---|---|
| 「2G 内存怎么跑得下这么多容器？」 | **分时启动**，不是全跑。项目一 7 个 + Zabbix 4 个是分开的；每个服务都设了 `mem_limit`，MySQL buffer pool 压到 128–192M。全量合并我算过内存账要占 83%，没余量应对突发，OOM 会先杀主库，所以我选择不合并。 |
| 「为什么要 4 个网络，一个不够吗？」 | 一个网等于任何容器（包括被攻破的 web）都能直连 3306。现在两个 db 都不接 front，**从入口看不到数据库**；主从复制再单独走 net-db，不和业务抢带宽。这是最小暴露面。 |
| 「两个节点为什么共用一份 Nginx 配置？」 | 给两个 app 都加 network alias `app`，`proxy_pass http://app:8080` 各自解析到自己那个。配置只有一份，改一次两边生效，不会"改了一台忘另一台"。 |
| 「固定 IP 怎么扩缩容？」 | 固定 IP 是为了避开 DNS 解析时机（Nginx 启动就要解析 upstream，那时容器还没进 DNS，会直接退出）。代价就是弹性差，所以只适合小规模稳定编排；要弹性就改成变量 + `resolver 127.0.0.11 valid=10s`。 |
| 「Nginx 为什么不用主动健康检查？」 | 开源版没有，要主动探测得打 `nginx_upstream_check_module` 补丁或换 tengine，商业版是 Nginx Plus 的 `health_check`。更彻底的做法是把健康判断交给编排层——K8s 的 readinessProbe 不通过直接从 Endpoints 摘掉。 |
| 「你说不重试 POST，那用户下单失败怎么办？」 | 这是我**故意的取舍**。`proxy_next_upstream` 默认不重试非幂等请求，加 `non_idempotent` 会在超时时重发下单请求，可能产生重复订单。我宁可让它失败一次让用户重试，也不冒重复扣款的风险。读请求完全无感。 |
| 「主从延迟怎么监控？」 | 看 `Seconds_Behind_Source`（8.0.23 之后从 `Seconds_Behind_Master` 改名，这个改名坑我踩过）。但它是**粗粒度**的，大事务时会失真，所以关键路径我用"写后读主库"来规避，而不是靠延迟阈值。 |
| 「压测数字可信吗？」 | 有保留。**测量工具本身成了瓶颈**——压测机和应用在同一台 2C2G 上，工具自己也吃 CPU。所以 794 这个数字我理解为"架构改进的方向性证据"，不是生产容量承诺，我会主动说明这一点。 |
| 「这套搬到生产还差什么？」 | 三块：机器级隔离、入口和缓存的冗余（LB/Redis 单点）、配置管理和发布流程（灰度/回滚/审批）。另外监控要加业务指标，不能只看进程活着。 |
| 「你从中学到最重要的一件事？」 | **`Up` 不等于可用。** 容器 Up 了但 MySQL 还在初始化；主从 IO 线程 Yes 但 SQL 线程已经停了；备份脚本 exit 0 但告警根本没发出去。所以我现在判断任何"正常"，都要问一句"我是怎么知道的"。 |
| 「有写文档吗？给谁看？」 | 有，25 篇故障复盘按"现象→排除→根因→修法→验证"写，还有一份零基础版知识点全解。写给两个读者：**三个月后的自己**（会忘），和**要接手的人**（隐含假设必须显式化）。 |
| 「这题如果让你重做一遍，会改什么？」 | 三件事：① 一开始就用 `service_healthy` 而不是默认的 `depends_on`；② 备份脚本第一版就带"测试告警"，而不是等发现静默失败；③ 压测机和应用分离，否则数字没意义。**这三点都是踩了坑才懂的，所以我更愿意讲坑，而不是讲成果。** |

## 六、三个陷阱

1. **别一开口就讲 Docker 命令。** 这题要的是**系统**，不是操作。顺序永远是：定位 → 规模 → 架构 → 流程 → 原理 → 难点。讲了 2 分钟还没出现"几个容器、几个网络"，就已经输了。

2. **别把"6 秒→2 秒"说成"切换耗时"。** 它是**故障感知时间**（多久发现并摘除），切换本身是毫秒级的重试。说错会被追一句"那你 2 秒内用户拿到什么"。

3. **别回避"一个人"。** 面试官问人数，八成是实习生岗想看协作意识。**诚实说一个人 + 给出自我约束机制 + 说清想补的短板**，比含糊其辞安全得多。诚信问题一旦被发现，技术再强也救不回来。
