## 一、Linux（JD 第 1/2 条）

**L1. 服务器负载高，你怎么排查？**
要点：`uptime` 看 load（对比 CPU 核数，2C 机器 load>2 就是满载）→ `top` 按 1 看每核、Shift+M 按内存排 → 分 CPU 型（us 高查应用、sy 高查系统调用、wa 高查 IO）还是内存型（`free -m` 看 available、有没有进 swap）→ IO 型用 `iostat -x` 看 %util。实测：我 2C2G 机器上跑恢复演练前必看 `free -m` 的 available，防止把生产库挤爆。

**L2. 文件删了但磁盘没释放，为什么？**
要点：文件被进程占用时 `rm` 只删目录项，inode 和数据块还在，直到进程关闭 fd。`lsof | grep deleted` 找到进程；日志类场景重启进程或 `> file` 截断。这是我磁盘写满演练的核心考点。

**L3. 软链接和硬链接的区别？**
要点：硬链接是同一个 inode 的多个目录项，不能跨文件系统、不能对目录；软链接是独立文件存路径，可跨分区可指目录，源删了就悬空。

**L4. 怎么查看某端口被谁占用 / 连接状态？**
要点：`ss -tlnp | grep :80`（监听）、`ss -tan state time-wait | wc -l`（连接状态统计）。我排查过 nginx 容器 80 端口冲突和 TIME_WAIT 堆积。

**L5. sshd 安全加固改哪些项？**
要点：改端口、`PermitRootLogin prohibit-password`（禁密码只留密钥）、`PasswordAuthentication no`、`MaxAuthTries` 降、`ClientAliveInterval` 会话保活；改完必须 `sshd -t` 语法检查再 reload。实测：我用 `sshd -T` 核验过六项，五项达标。

**L6. cron 任务手动能跑、定时不跑，什么原因？**
要点：①环境变量——cron 的 PATH 极简，脚本里用绝对路径或 crontab 里显式设 PATH（我踩过）；②权限——cron 直接执行路径要 x 位，`bash x.sh` 能跑不代表 `./x.sh` 能跑；③`%` 要转义；④输出重定向到日志文件才能事后排查。

**L7. 服务器重启后服务没起来，怎么保证下次自动起？**
要点：systemd 服务 `systemctl enable`；容器加 `--restart unless-stopped`；验证要真重启——注意 `live-restore: true` 时 `systemctl restart docker` 容器根本不停，验证是假阳性。实测：我 reboot 后 4 容器全部自动拉起、HTTP 200、数据完好。

**L8. 一块新磁盘从接入到可用几步？**
要点：`lsblk` 确认设备 → `fdisk`/`parted` 分区 → `mkfs` 格式化 → `mount`（写 `/etc/fstab` 用 UUID 防盘符漂移）→ `df -h` 验证。fstab 写错会导致开机挂起，用 `mount -a` 先验证。

## 二、MySQL（JD 第 1/4 条）

**M1. 慢查询怎么优化？完整流程。**
要点：开慢日志（`long_query_time=0.5`）→ `mysqldumpslow` 定位 → `EXPLAIN` 看 type/key/rows/Extra（ALL=全表扫描）→ 按「等值在前、排序列收尾」建复合索引，深分页用子查询先定位主键 → 用 `EXPLAIN ANALYZE` 的服务端耗时验证，不用客户端计时（进程启动开销会污染）。实测 30 万行：深分页 133→0.11ms。

**M2. 备份策略怎么设计？怎么验证备份可用？**
要点：每日 `mysqldump --single-transaction` 全量（InnoDB 不锁表）+ gzip，保留 7 天，cron 凌晨低峰跑；心跳脚本检查备份文件年龄超 26 小时告警。**关键**：备份≠可用，定期恢复演练，核对表数量+行数+索引数。实测：8.3M 全量包，16 秒起临时库、17 秒恢复 30 万行一致。

**M3. 主从复制原理？挂了怎么修？**
要点：主库写 binlog → 从库 IO 线程拉取写 relay log → SQL 线程重放。`show slave status\G` 看两 Yes；SQL_Running=No 常见于主键冲突/表结构不一致，先 `Last_SQL_Error` 定位，跳过一个事务 `SET GLOBAL sql_slave_skip_counter=1` 或重建从库。实测：我搭过主从并恢复过一次复制中断。

**M4. 为什么索引能提速？有没有副作用？**
要点：B+ 树把 O(n) 全表扫变成 O(log n)，树高稳定（30 万到 3000 万行都是 3 层）；副作用：每个索引一棵树要维护，写入变慢、占空间；失效场景：对索引列做函数、`LIKE '%xx'` 左模糊、低区分度列。

**M5. 数据库磁盘满了怎么应急？**
要点：先止损——清 binlog（`PURGE BINARY LOGS`，别直接 rm）、清慢日志；扩容前找出大文件 `du`；预防靠监控告警（>80% 告警）+ 日志轮转。实测：我用 loop device 演练过磁盘写满的场景。

## 三、LNMP（JD 第 1/2 条）

**N1. Nginx 502 和 504 有什么区别？分别怎么处理？**
要点：502=后端返回非法响应/连接被拒（php-fpm 挂了、端口不对）→ `docker logs` 看 fpm 是否存活、`ss` 确认 9000 在听；504=后端超时（PHP 执行慢、`max_execution_time` 或 fastcgi timeout 太短）→ 优化慢 SQL 或调超时。502 查"死了没"，504 查"慢不慢"。

**N2. PHP-FPM 的进程模型？pm 参数怎么配？**
要点：master 管理多个 worker，`pm.max_children` 是上限，静态/dynamic/ondemand 三种模式。2G 小机器 8 个 worker、每个约 30M，上限给 384M；QPS 压测发现瓶颈就在 max_children——加机器先看 worker 是不是打满。

**N3. Nginx 负载均衡怎么配？故障节点怎么摘？**
要点：upstream 配轮询，被动健康检查靠 `proxy_connect_timeout` + `fail_timeout`——真实请求踩到坏节点就摘除一段时间。我把 connect_timeout 从 3s 调到 1s，故障感知 6s→2s，切换期请求零失败。主动探测需 tengine/Plus。

**N4. nginx 容器启动即退出，怎么排查？**
要点：先看状态——`Created` 是进程没跑过（常为端口占用），`Exited(1)` 才有日志；`docker logs` 看报错；nginx 配置错误会在日志里精确到行。实测：`log_format` 写进 server 块导致容器 Exited(1)，指令上下文错误。

**N5. 日志暴涨把磁盘写满，怎么治理？**
要点：分两个出口——容器 stdout 用 log driver 限额（10m×3，实测 40MiB 输入被卡在 28M）；挂载到宿主机目录的日志 docker 管不到，要 logrotate 按天轮转：nginx 发 USR1 重开文件，mysqld 没有重开信号只能 copytruncate。看到轮转文件出现不算成功，必须验证新日志写回原文件。

## 四、Redis（JD 第 1/3 条）

**R1. 缓存穿透、击穿、雪崩分别是什么？怎么防？**
要点：穿透=查不存在的数据打到库（空值缓存/布隆过滤器）；击穿=热点 key 过期瞬间并发打库（互斥锁/永不过期）；雪崩=大批 key 同时过期（TTL 加随机抖动/多级缓存）。

**R2. 你项目里缓存怎么设计的？怎么证明生效？**
要点：cache-aside——先读缓存，MISS 查库回填，TTL 60s；`?nocache=1` 强制回源做对照组。首页三条 COUNT 聚合 58ms→0.4ms，ab 压测 QPS 12.6→794（两组各跑两次偏差<3%）。**降级**：Redis 连不上直接查 MySQL，缓存不能成为单点。

**R3. 内存满了 Redis 怎么办？**
要点：`maxmemory` 限内存（我给 64m，2G 机器上不能让它自由生长）+ 淘汰策略 `allkeys-lru`；作为纯缓存场景关掉持久化 `--save ""` 省磁盘 IO；session 存 Redis 后 PHP 节点天然无状态，负载均衡不再需要 ip_hash。

**R4. Redis 为什么快？**
要点：纯内存操作 + 单线程无锁竞争（6.0 后 IO 多线程仅处理网络）+ IO 多路复用（epoll）+ 高效数据结构（SDS/跳表/压缩列表）。

## 五、Zabbix / 监控（JD 第 1 条）

**Z1. 监控体系怎么搭？监控什么？**
要点：分层——主机层（CPU/内存/磁盘/网络）、服务层（端口、进程）、业务层（MySQL 主从状态、缓存命中率）；告警必配恢复通知。实测：Zabbix 7.0 监控主机资源 + MySQL 复制状态，4 条触发器，钉钉 Webhook 推送，验证过告警产生与自动恢复。

**Z2. 触发器怎么写？告警风暴怎么防？**
要点：触发器是表达式，如 `last(/host/key)>#3:90` 型阈值 + 持续次数防抖；防风暴：依赖项（DB 挂了不再报每个应用的错）、告警升级、合理 severity 分级（severity 用 0-5 数字，别想当然）。

**Z3. 怎么判断一个服务"活着"？**
要点：进程在/端口通/健康检查通过是三件事——`mysqladmin ping` 认证失败也返回 0（第 24 坑）；健康检查必须打到业务层（能 SELECT 1 才算 MySQL 可用）。

## 六、综合场景 + 沟通（JD 第 4/5 条）

**S1. 半夜告警数据库连接数打满，你的处理顺序？**
要点：先止血后根因——`show processlist` 看谁占着（长事务/慢查询）→ kill 阻塞源 → 应用侧临时降并发/重启 fpm 释放连接 → 根因：慢 SQL、连接池没配、还是流量异常 → 复盘文档。口径：**先恢复业务，再找原因**。

**S2. 客户报"系统卡"，你怎么推进？**
要点：先问清范围（全部用户还是个别人、什么时候开始、改过什么）→ 自己复现 + 看监控曲线定时间点 → 分层排查（网络→网关→应用→数据库）→ 给客户时间线式反馈。**JD 第 5 条的答法**：我把它翻译成"文档化习惯"——每次故障我都留排错记录和复盘，这就是给客户的"定期总结回顾"的素材。

**S3. 变更前你做什么？**
要点：备份（改配置先 cp 原文件、改库前 mysqldump）→ 评估影响面 → 低峰执行 → 变更后验证（不止看配置，要验行为：轮转配完压 40MB 日志看是否真轮转）→ 可回滚。三个真实教训：log_format 上下文改错容器起不来、恢复脚本改密码变量导致 access denied、cron 脚本缺执行位——全是"变更后没验证到行为层"的变体。
