# 13-IDC运维版简历拷打手册

> 对应简历：`王纪运-运维工程师实习简历`（2026-11-19 版，无 Redis）
> 目标岗位：初级运维 / IDC 机房运维（佰内科技、联想云领类 JD）
> 每题：问法 → 30 秒口径 → 追问。背口径，追问看懂思路即可。

## 第一部分：个人优势四条的拷打

### Q1「你处理过哪些真实故障？讲一个最印象深刻的。」（必问，开场题）

**背**：我讲磁盘写满那次。告警显示磁盘使用率超阈值，我先 `df -h` 确认是根分区满了，再 `du -sh /*` 一层层往下找，定位到是日志文件持续增长。当时做了两件事：先手动清理和轮转日志恢复空间——这是止损；然后配了 logrotate 按天轮转加上限，防止复发——这是根治。事后我把整个过程写成排查手册。这个「先止损再根治」的思路我后来一直用。

**追问**：
- 「为什么磁盘满了不能直接 rm 删日志？」→ 文件被进程占用时 rm 只删目录项，空间不释放，要重启进程或截断文件 `> file`
- 「你怎么提前发现磁盘要满？」→ 监控告警（80% 阈值）+ 日志轮转上限，不让它有写满的机会
- 「如果日志是数据库的 binlog 能直接删吗？」→ 不能直接 rm，要用 `PURGE BINARY LOGS`，直接删会导致主从出问题

### Q2「你说习惯记录运行状态，具体怎么记录？」

**背**：两层。自动的：Zabbix 采集主机资源和数据库状态，超阈值告警推钉钉，我验证过告警产生和自动恢复的完整流程；手动的：每次故障处理后写复盘记录——现象、排查步骤、根因、修法、验证结果，累计 25 个案例、十多篇文档。复盘的价值是下次同类问题 5 分钟就能定位。

**追问**：「Zabbix 告警夜里响了你的处理流程？」→ 先看告警级别和具体指标 → ssh 上去看现场（top / df / 日志）→ 判断影响面 → 能快速修就修，不能就先重启服务止血 → 处理完记录并查根因。**先恢复业务再查根因**。

### Q3「能接受轮班（含夜班）和机房环境吗？」

**背**：可以接受。我理解机房运维的价值就在 7×24 有人响应，设备故障不挑时间。我的两个项目都是自己半夜处理过问题的——备份脚本失败、容器被 OOM 杀掉都是晚上发现的，习惯了带着问题入睡、起来先看监控。

**追问**：「大小周/做二休二怎么看？」→ 如实回答可以适应，学生阶段时间灵活。**不要犹豫**，这类 JD 犹豫=淘汰。

### Q4「对服务器硬件了解多少？」（简历上写了，必被问）

**背**：目前了解计算机硬件的基本组成——CPU、内存、磁盘、 Raid 卡、电源、网卡这些部件的作用；常见故障现象能判断，比如开机无显示查电源和内存、磁盘故障看 RAID 卡指示灯和系统日志。诚实说，我实操以系统层为主，硬件维护经验是从自己装机器、清灰换件积累的，服务器硬件架构是我最想深入学习的方向，这也是我投这个岗位的原因。

**追问**（硬件基础题，见第五部分速答）。

## 第二部分：项目经历拷打

### Q5「介绍一下你的集群项目，为什么是单台服务器？」

**背**：在一台 2C2G 云服务器上用 Docker 部署了双节点 Web 集群：Nginx 做负载均衡分发请求到两个 Web 节点，后端 MySQL 8.0 主从复制。配置了健康检查和故障摘除——把连接超时从 3 秒调到 1 秒后，坏节点的感知从 6 秒缩到 2 秒，切换期间用户请求零失败。用单台模拟双节点是因为成本限制，但负载分发、健康检查、故障切换的机制都是真实的，这台机器重启后全部服务自动拉起我也验证过。

**追问**：
- 「健康检查的原理？」→ 被动检查：真实请求打到坏节点超时，Nginx 在 fail_timeout 内不再给它派请求
- 「Nginx 自己挂了怎么办？」→ 它是单点，生产上用 keepalived + VIP 做主备，我的项目里这是明确的已知取舍
- 「怎么证明切换期间零失败？」→ 持续 curl 测试，配合两个节点的 access log 看请求转移

### Q6「主从复制是什么？断了怎么修？」

**背**：主库把数据变更写进 binlog，从库两个线程——IO 线程拉 binlog 存到本机 relay log，SQL 线程重放，实现数据同步。我搭主从时遇到过 SQL 线程中断（`Slave_SQL_Running: No`），用 `show slave status\G` 看 Last_SQL_Error 定位原因，处理后重新启动同步恢复。备份恢复演练我也做过：全量备份 8.3M 包含 30 万行数据，恢复到临时库核对行数完全一致。

**追问**：
- 「主从延迟是什么原因？」→ 从库单线程重放跟不上主库并发写入，大事务会放大延迟
- 「为什么备份要演练？」→ 备份文件存在不等于能恢复，没演练过的备份等于没有备份

### Q7「Linux 服务起不来，你的排查步骤？」（对应简历「故障排查」条）

**背**：四步。① 看状态——服务是没启动过还是启动后退出了，这两种情况查法不同；② 看日志——启动日志里的报错会精确到文件和行号，我遇到过配置文件指令写错位置导致服务直接退出的情况，日志一眼定位；③ 看依赖——端口被占用、依赖的数据库连不上都会起不来，`ss -tlnp` 查端口占用；④ 修完验证——不只确认进程在，还要确认业务真的能用，比如 curl 一下页面。

**追问**：「端口被占用怎么找到是谁？」→ `ss -tlnp | grep :端口` 直接显示进程名和 PID。

### Q8「慢查询优化怎么做的？」（简历写了 133→0.11ms）

**背**：流程是先让慢 SQL 现形，再分析，再验证。开慢查询日志定阈值收集 → `EXPLAIN` 看执行计划，全表扫描的 type 是 ALL，加索引后变成走索引 → 按「等值条件在前、排序列收尾」设计复合索引 → 用 `EXPLAIN ANALYZE` 的服务端耗时验证效果，30 万行数据上分页查询从 133ms 降到 0.11ms。验证时我特意避开客户端计时——容器进程启动开销就有 60 多毫秒，会把 0.1 毫秒的优化完全掩盖掉，这是我自己踩过的坑。

**追问**：
- 「索引为什么快？」→ B+ 树，全表扫描 O(n) 变成树查找，数据量涨 100 倍树高只加一两层
- 「索引有什么代价？」→ 每个索引都要维护，写入变慢、占空间
- 「什么情况索引失效？」→ 对索引列做函数运算、`LIKE '%x'` 左模糊、区分度太低

### Q9「日常维护具体做哪些事？」（对应「日常维护」条）

**背**：四类。备份——脚本每日自动备份数据库和代码，保留 7 天，失败发告警，另有心跳脚本检查备份文件是不是太旧；日志——按天轮转加大小上限，防止写满磁盘；资源——给每个服务设内存上限防止互相挤爆，配了重启自愈，服务器重启后不用人工干预；监控——Zabbix 持续采集，异常即告警。这些全部由脚本和定时任务自动执行，人工只处理异常。

**追问**：「重启自愈怎么实现的？」→ 容器配置 restart 策略 + 真机重启验证过，四个服务全部自动恢复。

## 第三部分：专业技能拷打

### Q10「看一下这台服务器的负载是否正常，你怎么操作？」

**背**：`uptime` 看 load，和 CPU 核数比——2 核机器 load 长期超过 2 就是满载；`top` 看谁在吃资源，按 CPU 或内存排序；`free -h` 看内存，重点看 available 而不是 free 列；如果是 IO 问题用 `iostat -x` 看磁盘利用率。先定位是 CPU、内存、磁盘 IO 哪类瓶颈，再深入查具体进程。

### Q11「收到告警：一台服务器 ping 不通了，你怎么办？」

**背**：分场景。如果只有一台：先确认网络层——从跳板机 ping、traceroute 看断在哪；网络通但服务不通就上 IPMI/带外或去机房本地登录看电源和系统状态。如果是机房断电类，会是一批机器同时异常，那就不是单机问题，先联系机房确认供电。原则是：**先判断是个例还是面上的问题，再决定动手方向**。

### Q12「服务器开不了机 / 频繁重启，你排查什么？」（硬件场景）

**背**：先看电源——电源灯、供电、PDU；再看指示灯——服务器面板上有健康状态灯，内存/硬盘故障都有对应标识；进系统前先看自检画面有没有报错；能进系统就看日志 `journalctl -b -1`（上一次启动的日志）找关机原因。内存和硬盘是最常见的两个故障源：内存故障表现为蓝屏或重启，硬盘故障在 RAID 管理里能直接看到掉盘。

### Q13「RAID 了解吗？RAID 1 和 RAID 5 的区别？」

**背**：RAID 是把多块盘组合起来提供冗余或性能。RAID 1 两块盘互为镜像，容量利用率 50%，坏一块数据不丢；RAID 5 至少三块盘，用分布校验实现容错，容量利用率 (n-1)/n，允许坏一块。系统盘常用 RAID 1 图省心，数据盘大容量用 RAID 5 或 RAID 6（允许坏两块）。坏盘后换新盘要等 RAID 重建完成，期间是最脆弱的窗口，不能再坏第二块（RAID 5 而言）。

### Q14「Windows 和 Linux 装系统你做过吗？」

**背**：Linux 熟练——装过 OpenCloudOS/CentOS 系，分区规划（/boot、swap、数据盘分开挂载）、网络配置、装机后基础加固（改 SSH 端口、禁 root 密码登录）都做过。Windows 装机经验来自个人电脑重装，服务器版（Windows Server）的服务配置接触少，但装机流程是相通的：做启动介质 → 分区 → 装系统 → 装驱动 → 配置远程管理。如实说，Linux 是强项，Windows 服务器需要上手熟悉，但我学东西很快——两个集群项目都是从零自学的。

### Q15「你在学校学的和这个岗位匹配的点是什么？」（软性问题）

**背**：计算机专业给了网络和操作系统的基础理论，而我把理论落成了两个完整项目——从装系统、配服务、写脚本到监控告警，全流程自己走通，遇到问题先查文档再动手验证。运维这个岗位的核心素质——动手、细心、遇事不慌有流程——我在 25 个故障复盘中已经练出来了。

## 第五部分：硬件与机房速答（背短句）

| 问题 | 一句话答案 |
|---|---|
| 服务器和 PC 的区别 | 冗余电源、ECC 内存、支持多路 CPU、7×24 设计、远程管理口（IPMI/iDRAC） |
| IPMI 是什么 | 服务器带外管理口，系统宕机也能远程开关机、看控制台 |
| 硬盘指示灯含义 | 绿常亮=正常，绿闪=读写中，黄/红=故障，按厂商手册为准 |
| 内存 ECC 是什么 | 纠错内存，单比特错误自动修正，服务器标配 |
| 机房冷热通道 | 冷通道进风、热通道排风，机柜按此布局，温度一般 22±2℃ |
| 上架流程 | 核对 U 位 → 装导轨 → 上架固定 → 接电接网 → 贴标签 → 登记 CMDB |
| 带外 vs 带内管理 | 带内走业务网络（系统挂了就管不了），带外走独立管理网络（不依赖系统） |

## 使用建议

1. 必背五题：**Q1（故障故事）、Q3（轮班态度）、Q4（硬件意愿）、Q7（排查步骤）、Q11（ping 不通处理）**——IDC 面试官最常问的就是这五个
2. Q1 的故障故事是全场的锚，讲顺了后面追问都在你的地盘上打
3. 所有数字（6s→2s、133→0.11ms、8.3M/300000、25 个复盘）与之前手册口径一致，别记岔
4. 软性问题的答案姿态：诚实 + 有流程感 + 学习意愿强——实习生的三张底牌
